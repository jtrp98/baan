## Scope

รับมติ037/038: ทำ Check แบบ metadata-only แยกจาก PrepareUpdate/InstallPreparedUpdate ที่ผู้ใช้สั่งเอง ครอบ AC-030-01..08 ตาม REQ-030/DES-007/release-trust; BE-019 รับผิดชอบ Host workflow, staging/trust/guards/cancellation และ failure-recovery adapter ส่วนการคืนสภาพแพ็กเกจจริงเป็น BE-020/BE-021 ห้ามเพิ่ม dependency ย้อนกลับจาก BE-019 ไปสองงานนี้ การเตรียมและตรวจ logic ด้วย injected fake ทำได้ตาม queue006; การเชื่อม release DB/trust จริงยังต้องมี prerequisite และ G-RELEASE-DB เดิม ไม่ถือว่ามติธุรกิจปิด technical gate

## Out of Scope

งานนอก outputs/AC/references ของ task นี้ การเลือกนโยบายธุรกิจหรือเซ็นอนุมัติแทนคน การเพิ่มหรือตัด frozen release scope และ speculative feature ห้ามแก้ข้ามเขต Owns ของ role ห้าม state-changing git หรือเรียก role ต่อเอง Shared SQL/deploy/publish, installer tests และการเปลี่ยนสถานะหุ่นต้องมีหลักฐานอนุญาตเฉพาะตาม gate ไม่ถือว่าได้สิทธิ์จากการรับแผน

## Expected Output

- update bridge แยก Check/Prepare/Install พร้อม trust/staging/stop-close/cancel guards และ failure-recovery adapter; ส่งต่องานแพ็กเกจให้ BE-020/BE-021

ส่ง artifact จริงในเขต Owns ของ role พร้อม references ที่ตรวจย้อนกลับได้ ไม่สร้างสำเนาเอกสารข้ามหมวด หากมีไฟล์เดิมให้ amend พร้อม Change Log วันที่ 2026-10-26

## Acceptance

คง AC-030-01..03: none=false/null/install_supported=false; checkไม่download/install/execute; errorไม่ขวางlocalในlease; AC-030-04 explicit Prepare เท่านั้น ตรวจ hash/manifest/registry/publisher pin ก่อนเก็บ staging ไม่ผ่านต้องไม่เก็บหรือติดตั้งและแจ้งเหตุผล; AC-030-05 ตรวจ staging ซ้ำกัน TOCTOU และปฏิเสธ artifact ผิด/เปลี่ยน/หมดอายุ/withdraw/downgrade พร้อมข้อความ; AC-030-06 ขอหยุดงานค้าง/หุ่นโดยไม่อ้างว่าหยุดสำเร็จ ผ่าน close guards และผู้ใช้ยืนยันอีกครั้งก่อน restart/install; AC-030-07 จัดการ installer failure ส่งต่อ recovery/repair ของ BE-020/BE-021 และรายงานสาเหตุ ต้องมีหลักฐานใช้เวอร์ชันเดิมต่อได้จริงก่อนนับผ่าน; AC-030-08 cancel/close ระหว่างเตรียมหรือก่อนติดตั้งต้องไม่ติดตั้ง staging ล้างหรือตรวจซ้ำก่อนใช้ครั้งถัดไป; fake/unit ไม่แทน trust/OS/installer/หุ่นจริง

แนบตาราง criterion/AC → วิธีตรวจ → expected/actual → evidence path หรือ source:line และข้อจำกัด งานเตรียมแบบ/คำตัดสินต้องมีรายการประเด็น ผู้ตอบ และผลกระทบที่ตรวจทานได้; ถ้ายังไม่มี AC association ให้ตรวจตาม references โดยไม่สร้าง AC เอง งาน implementation ส่งคำสั่ง/exit code และผล checks ตามส่วนที่เปลี่ยน แยก automated logic, UI, hardware และ installer evidence ห้ามอ้างผ่านเมื่อไม่ได้ตรวจหรืออ้าง task นี้ปิด AC ก่อน QA ตรวจ เกินสองรอบแก้ให้หยุดส่งคนตัดสิน
