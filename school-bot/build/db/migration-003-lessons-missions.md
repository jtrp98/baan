## สิ่งที่เพิ่ม

| ตาราง | เก็บอะไร | คีย์และทางอ่าน |
|---|---|---|
| `SchoolBotLessonMissionAttempt` | รอบภารกิจหนึ่งรอบต่อแถว ผูกโรงเรียน นักเรียน ห้อง ณ เวลาเริ่ม และกิจกรรมใน revision ที่เริ่ม มีสถานะการรับเวลาเริ่มและสถานะความคืบหน้าแยกกัน คะแนนและ `SubmissionId` เป็นตัวเลือก | PK `SchoolBotLessonMissionAttemptId` เป็น `int4` identity บริการใช้ `(SchoolId, AttemptKey)` กับ hash เพื่อตรวจการส่งซ้ำ |
| `SchoolBotLessonMissionAccessEvent` | เหตุการณ์เปิด–ปิดของครูและเปิดคืนอัตโนมัติแบบเพิ่มแถว `StageKey` ว่างคือทั้งเทอม เก็บเวลาจากบริการและผู้กระทำ | PK `SchoolBotLessonMissionAccessEventId` เป็น `int4` identity บริการตรวจคำสั่งซ้ำด้วย `(SchoolId, Origin, EventKey)` การเปิดคืนใช้ `Origin = 'auto_reopen'` และ `EventKey` ของคำสั่งปิดเดิม การอ่านเหตุการณ์ล่าสุดเรียงตาม PK หลังกรองขอบเขต |

DDL เพิ่มสองตาราง ใช้ PK แบบ `int4` identity และมีเฉพาะดัชนีที่ PostgreSQL สร้างให้ PK ตามแนวทาง [มติ 044](../../shared/decisions/decisions-044.md) การตรวจค่าซ้ำและการอ้างอิงข้ามตารางอยู่ที่บริการตามรายการด้านล่าง

ใช้คำของ SchoolBot ได้แก่ `SchoolId`, `LearnerId`, `ClassroomId` และใช้ `timestamptz` สำหรับเวลา ชื่อและความหมายของรหัสจากระบบภายนอกใช้ที่ส่วนเชื่อมต่อ

## สมมติฐานสำหรับตรวจ

- ใช้ `ActivityKey` เป็น `StageKey` และเผยแพร่แผนที่พร้อม revision หลักสูตร แต่ละ Level ต้องชี้สาย `CurriculumKey` ที่แน่นอน เมื่อจัดลำดับใหม่ให้คง key เดิม รอบภารกิจเก็บ `ActivityId` ของฉบับที่เริ่มและอ่านหลักสูตร ด่าน Level และเทอมจากกิจกรรมฉบับนั้น งาน Arm/Block อ้าง `SubmissionId` เดิมเมื่อมีงานส่ง
- การเริ่มจริงต้องทราบ `ClassroomId` ที่ตรวจสอบได้ ทั้งการเริ่มออนไลน์และการใช้สิทธิ์ออฟไลน์ เก็บรหัสห้อง ณ เวลาเริ่มลง `ClassroomId` เพื่อให้ผลย้อนหลังและการเปิดคืนมีขอบเขตเดิมเมื่อเด็กย้ายห้อง [การจับคู่รหัสห้องเดิม](../../../../target/sb-web-school-robot/backend/src/ServiceSchoolBot.Infrastructure/Repositories/Databases/SchoolAssessmentAuthority.cs)
- สิทธิ์ออฟไลน์เป็นหลักฐานลงนามที่ตรวจซ้ำได้ เก็บรหัสสิทธิ์กับหลักฐานเวลาที่ผ่านการตรวจรูปแบบใน `StartEvidence` โดยงดเก็บ token ดิบ `StartedAtLowerBound` และ `StartedAtUpperBound` เป็นช่วงเวลาอ้างอิงจากเซิร์ฟเวอร์ กรณีออนไลน์ใช้ค่าเดียวกันทั้งสองฝั่ง หากเวลาไม่พอให้เก็บงานเป็น `needs_review`
- เก็บ `CompletionEvidence` เฉพาะข้อมูลที่ใช้ตรวจ เช่น คำตอบหรือ reference ไปยังงานส่ง เกณฑ์ retention, สิทธิ์อ่านผล และ masking ต้องครอบข้อมูลเด็กในตารางใหม่ก่อนใช้จริง

## กติกาที่ Backend ต้องบังคับ

1. ตรวจ Level 1–6, เทอม 1/2, โรงเรียน ห้อง ผู้เรียน และการอ้างกิจกรรมจาก revision ที่เผยแพร่ ตรวจช่วงเวลาให้มีทั้งคู่และเรียงถูกเมื่อรับการเริ่ม ตรวจ `StartStatus` และ `ProgressState` ตามสัญญา `FinishRequestHash` คู่กับ `FinishReceivedAt` ส่วนคะแนนต้องมีทั้งคะแนนที่ได้และคะแนนเต็มเมื่อเปิดใช้คะแนน และดาวอยู่ในช่วง 0–3 เมื่อเปิดใช้ดาว
2. ทุกเส้นทางที่เขียนสองตารางใช้ `pg_advisory_xact_lock` ด้วย namespace เดียวกันและ `SchoolId` ที่บริการยืนยันแล้ว ใน transaction แบบ `READ COMMITTED` ให้ได้ lock ก่อนอ่านและตรวจคำขอซ้ำ จึงครอบคลุม UUID เดียวกันที่ส่งมาพร้อมกันแม้คนละห้องหรือคนละเทอมในโรงเรียนเดียว ตั้ง `OccurredAt` จากเวลาเซิร์ฟเวอร์หลังได้ lock และให้การปิดเทอมมีผลเหนือการเปิดรายด่าน
3. ถ้ารับ `AttemptKey` ซ้ำ ให้เทียบ `StartRequestHash` หรือ `FinishRequestHash` ตามชนิดคำขอภายใต้ transaction ค่าตรงคืนใบรับเดิมจากรหัสรอบและเวลารับครั้งแรก ค่าต่างส่ง conflict แยกการอ่านสถานะล่าสุดจากการอ่านใบรับ การจบรอบบันทึกลงแถวเดิมหลังตรวจตัวตนและ revision การพบรอบที่เคยเริ่มและรับแล้วต้องนับแม้ผู้เรียนทำเสร็จหรือออกกลางด่าน
4. คำสั่งเปิด–ปิดของครูตรวจ `(SchoolId, Origin, EventKey)` และ `RequestHash` ก่อนเพิ่มแถว ตรวจประวัติการปิดที่มีผล ณ เวลาเริ่มก่อนรับรอบ แล้วเปิดคืนเฉพาะเหตุการณ์ปิดที่ยังมีผลกับด่านและห้องเมื่อหลักฐานบอกว่าเริ่มก่อนปิด การเปิดคืนต้องอ้างเหตุการณ์ `teacher` ที่ `IsOpen = false` ภายในโรงเรียนและขอบเขตเดียวกัน ใช้ `EventKey` เดิมและเก็บ `ReopenedByAttemptKey` ของรอบแรกที่ทำให้เปิดคืน หากพบแถวเปิดคืนเดิม ให้ใช้แถวเดิมและรับผลของแต่ละรอบตามสิทธิ์ของตน
5. คงเหตุการณ์เปิด–ปิดแบบเพิ่มแถว การเปิดคืนทำผ่านเหตุการณ์ใหม่ การเปลี่ยนผลของ Attempt บันทึกผู้กระทำและเวลาใน `SchoolBotAuditEvent` เดิม และคงรหัสรอบที่จำเป็นต่อการตรวจซิงก์ซ้ำตามนโยบายข้อมูลผู้เรียน

## ตรวจรับและย้อนกลับ

- หลังเจ้าของตรวจร่าง ให้ใช้ snapshot ที่ได้รับอนุญาตหรือฐานทดสอบแยกเพื่อเทียบ PK แบบ `int4` identity ทั้งสอง ชนิดและ nullability จากนั้นตรวจการเขียน UUID เดียวกันพร้อมกันทั้งในห้องเดียวและคนละห้องของโรงเรียนเดียว การใช้ UUID เดียวกันต่างโรงเรียน และการเปิดคืนหนึ่งครั้งเมื่อมีสองรอบซิงก์พร้อมกัน
- ชุดเพิ่มตารางเป็น transaction เดียว ใช้ชื่อใหม่ใน `public` และไม่ backfill ให้ตรวจ catalog ว่าชื่อทั้งสองยังว่างก่อนเริ่มและตรวจ scaffold แบบ database-first หลังติดตั้งในสภาพแวดล้อมที่อนุญาต
- ไฟล์ย้อนกลับใช้เฉพาะก่อนเริ่มเก็บข้อมูล ให้เจ้าของยืนยันว่าตารางมาจาก Migration 003 และหยุด writer ก่อนรัน สคริปต์จะล็อกและตรวจรูปแบบ PK กับความว่างของทั้งสองตารางก่อนถอน เมื่อเริ่มเก็บผลแล้วให้หยุดเปิดใช้ฟีเจอร์และเก็บตารางไว้เพื่อแก้ต่อ

ผู้ใช้แจ้งในแชตวันที่ 2026-11-05 ว่า «รันแล้ว» และส่งผล catalog สองแถวจากฐานชื่อ `SchoolBot` เวลา 23:10:32 น. ตามเวลาไทย (`2026-11-05T19:10:32.829306+03:00` ตามผล query) ชื่อ environment ว่าเป็นฐานทดสอบหรือฐานจริงยังไม่ได้ระบุ

ตรวจเทียบชื่อ ลำดับ ชนิดข้อมูล การรับ `NULL` ค่า default และ identity ของทุกคอลัมน์แล้วตรงกับ Rev 8 ทั้งสองตารางเป็น `relkind = r` โดย Attempt มี 20 คอลัมน์ และ AccessEvent มี 13 คอลัมน์ ตารางละหนึ่ง PK `int4 GENERATED ALWAYS AS IDENTITY` และหนึ่ง B-tree index ที่ `primary = true` จาก PK พบดัชนีเพิ่มเติม 0 ตัวและ comment 0 รายการ
