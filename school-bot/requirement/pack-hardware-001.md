# ชุดเกณฑ์ตรวจรับหุ่นและข้อมูลอุปกรณ์

> แก้ล่าสุด 2026-11-02 · แก้โดย spec · ขอโดย ผู้ใช้ (เรียบเรียงตามกติกาเอกสารใหม่ ความหมายไม่เปลี่ยน)

ชุดนี้รวมเกณฑ์ของ [REQ-014 (ค้นหาและเชื่อมต่อหุ่น)](req-014.md), [REQ-015 (โปรไฟล์หุ่นหกข้อต่อ)](req-015.md), [REQ-019 (อัปโหลดท่าไปบอร์ด)](req-019.md), [REQ-021 (ขอหยุดหุ่นและยกเลิกงานค้าง)](req-021.md), [REQ-024 (การเชื่อมต่อขาดและคำสั่งล้มเหลว)](req-024.md), [REQ-031 (ติดตั้งและดูแลแอปบน Windows)](req-031.md) และ [REQ-032 (ติดตั้งแอปบน macOS)](req-032.md) เพื่อเตรียมตรวจการเชื่อมต่อ ดาวน์โหลด ขอหยุด และควบคุมหุ่นจริงบนแพลตฟอร์มเป้าหมาย โดยบันทึกรุ่น firmware, calibration และผู้รับรองให้ตรวจย้อนกลับได้


คำย่อในเอกสาร: OS = Operating System หรือระบบปฏิบัติการ; HID = Human Interface Device; VID/PID = รหัสผู้ผลิตและรหัสผลิตภัณฑ์ของอุปกรณ์; PWM = Pulse Width Modulation
## เงื่อนไขก่อนทดสอบ

ผู้ใช้ยังไม่อนุญาตทดสอบอุปกรณ์จริงตาม [มติ 038 (ผู้อนุมัติเนื้อหา rubric และสิทธิ์ทดสอบอุปกรณ์)](decisions-038.md) งานหุ่นจึงใช้ dry-run/fake bridge จนมีคำสั่งอนุญาตเป็นลายลักษณ์อักษร ยังไม่มีรุ่นหุ่นที่ยืนยัน ชื่อ zide และ VID/PID 0483:5750 จาก source ไม่ยืนยันยี่ห้อ รุ่น หรือ firmware จึงยังกรอกผล Actual ไม่ได้

[ตารางวิธีตรวจ 8 เกณฑ์](pack-hardware-001-cases.md) แยกวิธีตรวจ Expected/Actual หลักฐานและผู้รับรอง โดยคงเกณฑ์เดิมทุกข้อ

## เกณฑ์และอำนาจอนุญาต

| เกณฑ์ | ค่าที่เสนอ | สถานะ/ที่มา |
|---|---|---|
| Stop latency (user trigger → physical rest) | ≤ 5,000 ms | ยังไม่ยืนยัน: ตั้งจาก host drain 5 s ปัจจุบัน (INTEGRATION.md) เป็นจุดตั้งต้นให้คนขึงเข้มขึ้น |
| Unplug → สถานะ lost | ไม่เสนอค่า | ผูกกับความถี่ discovery (GAP-08 ของ arch/SA-003) — รอค่าจาก arch แล้วให้คนยืนยัน |
| Partial download → หยุดชุดถัดไป | ไม่มีค่าตัวเลข (พฤติกรรมตาม [AC-019-03 (หยุดดาวน์โหลดเมื่อชุดแรกผิดพลาด)](req-019.md)) | ยืนยันแล้วในระดับพฤติกรรม; วิธีพิสูจน์ต้องมีหุ่นจริง |
| Emergency stop อิสระ | วิธี+เกณฑ์: ______ | ยังไม่ยืนยัน: ต้องกำหนดวิธีฉุกเฉินที่ไม่พึ่งซอฟต์แวร์ (เช่น ตัดไฟ/สวิตช์เฉพาะ) + ผู้รับรอง |
| Calibration 6 ข้อต่อ | ID/direction/PWM endpoints/ช่วงกายภาพ/โหลด: ______ | ตามรูปโปรไฟล์หก servo ([REQ-015 (โปรไฟล์หุ่นหกข้อต่อ)](req-015.md)); ค่าจริงต้องวัด; bounds ของ engine ไม่ใช่ safe travel |
| สิทธิ์สั่งหุ่น | **ยังไม่อนุญาตทดสอบอุปกรณ์จริง** (มติผู้ใช้ 2026-10-24 — มติ 038: ทุกงาน robot ใช้ dry-run/fake bridge ต่อจนมีคำสั่งอนุญาตเป็นลายลักษณ์อักษร) · ผู้ออกคำสั่งอนุญาตเมื่อถึงเวลา: ______ · วันที่/ขอบเขต: ______ | มติ 2026-10-24 แล้ว (สถานะคง "ไม่อนุญาต"); ทุกการทดสอบหุ่นจริงบล็อกต่อ |

## ยังไม่ยืนยัน

- Stop latency ไม่เกิน 5,000 ms เป็นเพียงค่าที่เสนอจาก host drain 5 วินาที ต้องให้ผู้ใช้หรือทีมอุปกรณ์ยืนยันเกณฑ์กายภาพ
- arch ต้องระบุความถี่ค้นหาอุปกรณ์และเวลาถึงสถานะ lost ก่อนให้มนุษย์ยืนยัน ไม่เสนอค่าในชุดนี้
- วิธี emergency stop ที่ไม่พึ่งซอฟต์แวร์ เช่น ตัดไฟหรือสวิตช์เฉพาะ พร้อมเกณฑ์และผู้รับรองยังรอระบุ
- รุ่นหุ่น board, firmware, calibration หกข้อต่อ และผู้มีอำนาจออกคำสั่งอนุญาตทดสอบจริงยังรอผู้ใช้หรือทีมอุปกรณ์กรอก bounds ของ engine ไม่ใช่ระยะเคลื่อนที่ปลอดภัย

## หลักฐาน

- hardware-survey-001 (หลักฐานและแผนสำรวจอุปกรณ์): engine เริ่มด้วย dry-run; native HID/Serial เป็น Windows-only และ Darwin ปฏิเสธ; CHECK_FW silence ไม่เกิน 1,500 ms; transport deadline 4 วินาที; pacing 200 ms ต่อคำสั่ง; Serial ใช้ COM1–COM9999 กับ baud allowlist; ดาวน์โหลดได้ 1–8 กลุ่มต่อคำขอ
- `INTEGRATION.md:71–80`: host drain 5 วินาทีก่อน stop เป็นค่าจากโค้ดเดิม ไม่ยืนยัน physical rest งานนี้ไม่ได้ตรวจโค้ดปัจจุบันซ้ำ
- BA-003 (เตรียมเกณฑ์ตรวจหุ่น) ตอบ GAP-05 (ขาดชุดตรวจรับหุ่นจริงและผู้รับรอง) ต้องมีข้อมูลและคำยืนยันก่อน QA-005/006/007 (ตรวจหุ่นจริงและแพลตฟอร์ม) จึงจะตัดสินเกณฑ์กายภาพได้ กรณี PF-HW (กรณีทดสอบฮาร์ดแวร์) ยังเป็นการเตรียมขั้นตอน
- GAP-08 (ความถี่ค้นหาอุปกรณ์และการตรวจพบการขาดการเชื่อมต่อ) เป็นงาน arch/SA-003 (สัญญาหุ่นและ transport)
