## ข้อกำหนดที่ยืนยัน

- คะแนนลงเป็นช่องย่อย (`Pgtassessment` / รายการใน `PgtgradeDetail.ScoreData`) ต่อกิจกรรม/คาบ ตามที่แมพไว้ หนึ่งคาบแมพได้หลายช่องข้ามหลายวิชา (คำชี้แจงใน decisions-020)
- ไม่เปลี่ยนโครงสร้างระบบเกรดเดิม (ไม่เพิ่ม/แก้ตารางหรือคอลัมน์ PGGradeDB)
- SchoolBot เป็นผู้เชื่อมและบันทึกคะแนนลงระบบเกรดเอง; API ทุกเส้นอยู่ฝั่ง school-bot (`target/school-bot-v2/web` ตาม decisions-010) ไม่รอทีม academic เพิ่ม API
- มีหน้า mapping สำหรับแมพตัวชี้วัด/กิจกรรมของหลักสูตรกับวิชาและช่องคะแนนใน SchoolBright; ตอนส่งคะแนนส่งตาม mapping นั้น
- ส่งเมื่อครูกดยืนยันเท่านั้น (decisions-020) และถ้าคะแนนปลายทางถูกครูแก้หลังรอบก่อน ให้หยุดแสดงรายการชน แล้วให้ครูเลือกทับหรือคงค่าเดิมรายคน
- ปัดคะแนนเป็นจำนวนเต็มก่อนส่ง และแสดงค่าที่ปัดใน preview

## ผลต่อมติเดิม

- มตินี้แทนข้อความใน decisions-011 / data-model ที่ว่า SchoolBot "ไม่มีสิทธิ์เขียนเกรดทางการ" สำหรับขอบเขตช่องคะแนนย่อยที่แมพไว้เท่านั้น
- ข้อเสนอ SA ที่ให้ปัดตกการเขียน PGGradeDB ตรง ผู้ใช้ตัดสินแล้วว่าให้ SchoolBot เขียนเอง — ความเสี่ยงที่ SA ระบุยังต้องแก้ในแบบ ไม่ถูกยกเลิกโดยมตินี้

## ความเสี่ยงที่ SA ต้องปิดใน contract (จาก source-review-004)

- `ScoreData` เป็น JSON ทั้งก้อน: ต้องแก้เฉพาะรายการที่ SchoolBot ดูแล ไม่ทับช่องที่ครูกรอก และกันเขียนชนด้วย lock/ตรวจค่าเดิม เพราะไม่มี unique/concurrency token ใน mapping
- คะแนนรวม/เกรดอาจคำนวณจาก `GetScore100`/ฟิลด์รวม หรือ DB function `getstudentgradebysid`; ต้องพิสูจน์ว่าแก้ช่องย่อยแล้วระบบเดิมคำนวณใหม่เอง หรือ SchoolBot ต้องคำนวณตามสูตรเดิม โดยไม่เปลี่ยนโครงสร้าง
- `PgtgradeEdit` override และรหัสผลพิเศษ (รอผล/ขาดสอบ ฯลฯ) ห้ามทับหรือแปลงเป็นศูนย์
- ตรวจสิทธิ์ครูรายวิชา/ห้อง/ล็อกฝั่ง server และบันทึก audit (แหล่งคะแนน เวอร์ชัน ผู้ยืนยัน) ทั้งฝั่ง SchoolBot และ `PgtgradeAuditLog` ถ้าเหมาะ
- การเขียนข้าม DB (School + PGGradeDB) ไม่ atomic; ต้องมี outbox/idempotency ตาม DES เดิม
- SQL/การเข้าถึงเขียน PGGradeDB ต้องผ่าน DBA และมนุษย์อนุมัติก่อนรันตามกติกาเดิม
