## ขอบเขตและของเดิมที่ใช้ต่อ

Desktop เข้า API ผ่าน Go/Wails bridge และ Gateway ตามเดิม เว็บ Admin ใช้ BFF และ staff assertion เว็บครูใช้ session และตรวจการมอบหมายห้องที่ฝั่งบริการ เลือกใช้ `CurriculumKey`, `LessonKey` และ `ActivityKey` ที่มีอยู่สำหรับอ้างอิงหลักสูตรที่เผยแพร่ เก็บข้อมูลแผนที่ของบทเรียนเป็นส่วนที่ Admin จัดเอง และให้หนึ่งด่านอ้างกิจกรรมที่เผยแพร่ได้หนึ่งรายการ ด่าน Lab เชื่อมงานส่งและผลตรวจเดิมผ่าน project revision กับ mission/criteria ที่ตรงกับด่าน ส่วน Quiz ฝึกเรียนใช้สัญญาคำตอบและกติกาตรวจของตัวเองเพื่อรักษาสัญญาข้อสอบแบบมีเวลาเดิม [Desktop bridge](../../../../../target/sb-web-school-robot/app/desktoplearning.go) · [หลักสูตร](../../../../../target/sb-web-school-robot/backend/src/ServiceSchoolBot.Domain/Curriculum/SchoolBotCurriculumRecords.cs) · [การอ้างภารกิจ Lab](../../../../../target/sb-web-school-robot/backend/src/ServiceSchoolBot.Domain/Curriculum/ProjectActivityReference.cs) · [Teacher authorization](../../../../../target/sb-web-school-robot/backend/src/ServiceSchoolBot.Application/Services/Implementations/Assessment/TeacherRunService.cs)

## ข้อมูลและกติกา

| ข้อมูล | คีย์และกติกา |
|---|---|
| แผนที่เผยแพร่ | `level` (1–6), `term` (1/2), `revision`, `stages[]` เรียงด้วยลำดับที่ Admin ตั้ง แยกจากหมายเลขที่ UI วาดบนพื้นหลัง แต่ละ stage มี `stage_key` คงที่และ `activity_ref` เดียวพร้อม revision ของเนื้อหา |
| นโยบายด่าน | `completion_rule` เป็น `complete`, `submit`, `teacher_approval` หรือ `score_threshold` · `require_pass_for_next` ระบุว่าด่านนี้ขวางด่านถัดไปหรือไม่ · `scoring` เป็น `none` หรือกติกาคะแนนพร้อมเกณฑ์ของด่าน · ดาวเป็นผลที่ตั้งเพิ่มได้เมื่อด่านมีคะแนน |
| สิทธิ์ห้อง | ใช้ `school_id` กับ `classroom_id` จากตัวตนและการมอบหมายที่บริการตรวจแล้ว ผูกกับ `level` และ `term` หรือ `stage_key` เก็บ revision สถานะ พร้อมเหตุการณ์เปิด ปิด หรือเปิดคืนและผู้กระทำ |
| รอบภารกิจ | `attempt_id` ฝั่ง client ใช้ซ้ำเมื่อ retry, รหัสนักเรียนและห้อง ณ เวลาเริ่ม, `stage_key`, revision ที่เริ่ม, ลำดับเหตุการณ์เริ่มและจบ, หลักฐานกิจกรรมและผลที่บริการรับแล้ว รอบหนึ่งใช้กติกาของ revision ที่เริ่ม การเผยแพร่ฉบับใหม่ไม่เขียนทับผลเดิม |
| ผลที่ UI อ่าน | แยก `availability` (`available`, `prerequisite`, `term_closed`, `stage_closed`, `content_unavailable`) ออกจาก `progress` (`not_started`, `in_progress`, `submitted`, `awaiting_teacher`, `passed`, `not_passed`) และ `sync` (`synced`, `pending`, `needs_review`) · `score` และ `stars` เป็น optional · ข้อผิดพลาดโหลดความคืบหน้าอยู่ต่างจากผล `not_started` |

- ก่อนเผยแพร่ ตรวจ Level/เทอม ลำดับซ้ำ การอ้างกิจกรรม และความเข้ากันได้ของเงื่อนไข เช่น `score_threshold` ต้องมีคะแนนและเกณฑ์ที่อยู่ในช่วง `teacher_approval` ต้องมีทางส่งหลักฐานเข้าคิวครู ใช้ revision check กัน Admin แก้ทับกัน
- ระหว่างเริ่มใหม่ การปิดเทอมขวางด่านในเทอมนั้น แม้ด่านจะเปิดอยู่ การเปิดด่านของครูยังใช้เงื่อนไขก่อนหน้าที่ Admin ตั้งไว้ ใช้ลำดับเดียวกันข้ามเทอมเมื่อตั้งให้ด่านสุดท้ายของเทอมเป็นเงื่อนไขของด่านถัดไป
- ด่าน `complete` ใช้การทำจบที่นิยามตามกิจกรรม `submit` ใช้ใบรับงาน `teacher_approval` ใช้ผลอนุมัติของครูที่มีสิทธิ์ และ `score_threshold` ใช้คะแนนที่บริการคำนวณหรือรับจากตัวตรวจงานที่เชื่อถือได้ ตรวจ Quiz จากคำตอบกับเนื้อหาเวอร์ชันเดิม ค่าคลาดเคลื่อนสไลเดอร์และวิธีให้คะแนนใช้ config ของโจทย์
- Phase 1 แสดงและเก็บผลใน School Bot ผูกบัญชีที่ล็อกอินผ่าน SchoolBright คะแนนภารกิจใช้แยกจากเส้นทางส่งเกรดเดิม

## การเริ่มออฟไลน์และการเปิดคืน

1. **ดาวน์โหลดล่วงหน้า** บริการออกสิทธิ์ออฟไลน์ที่ตรวจสอบย้อนหลังได้ ผูกบัญชี อุปกรณ์ ห้อง ด่าน revision และช่วงสิทธิ์ แอปแคชเนื้อหาและฐานเวลาอ้างอิงจากเซิร์ฟเวอร์ Go Host เขียนเหตุการณ์เริ่มและผลแบบทนต่อแอปปิดก่อนแจ้งว่าบันทึกสำเร็จ ส่งคิวด้วย `attempt_id` และรหัสเหตุการณ์เดิมเสมอ
2. **ครูสั่งปิด** บริการตรวจว่ามีรอบที่รับเหตุการณ์เริ่มแล้วในห้องและขอบเขตนั้นหรือไม่ ถ้ามี ส่ง `ALREADY_STARTED` ถ้ายังไม่มี เก็บเวลาปิดและ revision จากเซิร์ฟเวอร์ การเริ่มออนไลน์และคำสั่งปิดใช้ขอบเขตการเขียนเดียวกันเพื่อให้เห็นลำดับเดียว
3. **ซิงก์ผล** ตรวจตัวตน สิทธิ์ออฟไลน์ เวอร์ชันและหลักฐาน บันทึกเริ่ม/ผลและการเปิดคืนในธุรกรรมเดียว หากเวลาที่เริ่มอยู่ก่อนการปิดที่มีผล ให้รับผลและยกเลิกเฉพาะเหตุการณ์ปิดที่เกี่ยวข้องกับด่าน/เทอมของห้องนั้น คืนใบรับเดิมเมื่อส่งซ้ำ ถ้าคีย์เดิมมากับข้อมูลคนละชุดให้คืน conflict
4. **การเปรียบเทียบเวลา (ร่างเชิงตรรกะที่ผู้ใช้ยืนยัน)** เก็บเวลาฝั่งเซิร์ฟเวอร์คู่กับช่วงเวลาส่ง–รับจากนาฬิกา monotonic ของ Host ใช้เวลา monotonic จาก boot เดียวกันคำนวณช่วงเวลาที่เป็นไปได้ของการเริ่ม โดยเผื่อความคลาดเคลื่อน และเทียบกับเวลาปิดของเซิร์ฟเวอร์ ถ้าขอบบนของเวลาเริ่มอยู่ก่อนเวลาปิดจึงเปิดคืนได้ ถ้าเริ่มตั้งแต่เวลาปิดขึ้นไป การซิงก์รอบนั้นไม่เปิดคืน ถ้าช่วงเวลาทับกัน ฐานเวลาขาดหลัง reboot หรือข้อมูลไม่สอดคล้อง ให้เก็บงานไว้และแสดง `needs_review` เพื่อให้ผู้มีสิทธิ์ตรวจสอบเวลาเริ่มก่อนเปลี่ยนสิทธิ์ห้อง เวลา wall clock ของเครื่องใช้ประกอบการตรวจได้ สิทธิ์ออฟไลน์ยืนยันขอบเขตที่ออกให้ ส่วนความน่าเชื่อถือของเวลาเริ่มขึ้นกับหลักฐานจากเครื่อง

## ขอบเขต API ที่เสนอ

| ผู้ใช้ | ความสามารถ | การตรวจที่ boundary |
|---|---|---|
| นักเรียน | อ่านแผนที่และผลตามบัญชี ดาวน์โหลดเนื้อหาและสิทธิ์ เริ่มออนไลน์หรือซิงก์รอบออฟไลน์ | ยืนยัน session/device/learner จาก transport จำกัดขนาดผลและชนิดคำตอบ เช็ก replay กับข้อมูลเดิม และตรวจคะแนนซ้ำตาม revision |
| Admin | อ่านและแก้แผนที่ฉบับร่าง เผยแพร่ revision | ใช้ staff assertion และ revision precondition เดิม ตรวจ schema และการอ้างกิจกรรมข้ามหลักสูตร |
| ครู | อ่านผลตามห้อง เปิด/ปิดเทอมหรือด่าน ตรวจและอนุมัติงานที่กำหนด | ใช้ teacher assignment จากระบบ ตรวจสิทธิ์ซ้ำตอนเขียน และคืนสถานะล่าสุดเมื่อ revision เปลี่ยน |

เพิ่ม transport ผ่าน gRPC ของ School Bot และ Gateway ตามโครงเดิมเมื่อยืนยัน payload และ schema แล้ว ร่างนี้ใช้ชื่อเชิงสัญญา การเลือกรูปแบบตารางจริงและคำสั่งเปลี่ยน schema ต้องตรวจเทียบฐานแบบ database-first และผ่าน gate ก่อนใช้ [กฎ Backend](../../../../../target/sb-web-school-robot/backend/AGENTS.md) · [Gateway Learning Controller](../../../../../target/sb-api-gateway/src/ApiGateway.API/Controllers/ServiceSchoolBot/LearningController.cs)

## กรณีทดสอบที่ต้องยืนยัน

| ID | กรณี | ผลที่คาด |
|---|---|---|
| CT-01 | เผยแพร่ Level ที่มี 20 ด่าน กระจาย 2 เทอม พร้อม Quiz, Arm และ Block | Desktop เรียงด่านตามที่ตั้งและเปิดกิจกรรมถูกประเภท |
| CT-02 | ด่านไม่มีคะแนนกำหนดผ่านเมื่อครูอนุมัติ | ส่งแล้วรอตรวจ เมื่ออนุมัติจึงผ่านและเปิดด่านถัดไปถ้าตั้งให้รอผ่าน |
| CT-03 | ห้อง A ปิดเทอม ขณะที่ห้อง B เปิด | นักเรียนห้อง A เริ่มไม่ได้เมื่อสถานะปิดมีผล ห้อง B ยังเริ่มได้ตามสิทธิ์ |
| CT-04 | มีเหตุการณ์เริ่มที่ซิงก์แล้ว ครูพยายามปิดด่านหรือเทอม | คืน `ALREADY_STARTED` โดยผลเดิมยังอยู่ |
| CT-05 | เริ่มออฟไลน์ก่อนปิด แล้วส่งผลซ้ำหลังเน็ตกลับ | รับผลครั้งเดียว เปิดคืนเฉพาะขอบเขตที่ขัดกับการเริ่ม และคืนใบรับเดิมเมื่อซ้ำ |
| CT-06 | เริ่มหลังปิด หรือช่วงเวลาเริ่มทับเวลาปิด | กรณีหลังปิดไม่เปิดคืน กรณีเวลาทับให้เก็บงานและขึ้น `needs_review` |
| CT-07 | แอปปิดก่อนส่งผล สลับบัญชี แล้วกลับบัญชีเดิม | คิวของบัญชีเดิมยังอยู่ อื่น ๆ เข้าถึงผลหรือคิวข้ามบัญชีไม่ได้ |
| CT-08 | Admin เผยแพร่ revision ใหม่ขณะยังมีรอบออฟไลน์ | ตรวจรอบเดิมด้วย revision ที่เริ่ม และอ่านผลเดิมได้ |
