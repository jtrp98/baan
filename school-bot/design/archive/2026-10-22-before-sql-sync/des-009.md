## สูตรคะแนนช่อง

ทุก source มี earned/max จาก authoritative assessment/attempt
และ policy revision ที่แน่นอน; max > 0, 0 <= earned <= max
quiz ใช้คะแนนสูงสุดของ attempt ที่ submit แล้วตามค่าเริ่ม (decisions-024)
ผลของการสอบซ่อมยังไม่มีมติ: learner ที่มี retake attempt → blocked
RETAKE_RULE_NOT_CONFIGURED (DES-010)

normalized = Σ(weight_bps/10000 × earned/max)
raw_target = normalized × target_max
integer_target = floor(raw_target + 0.5)

คำนวณด้วย decimal ไม่ใช่ binary float
ปัด half-up ตามมติ decisions-023 / BR-050-05: x.5 ขึ้นไปปัดขึ้น
ต่ำกว่า x.5 ปัดลง (7.5 → 8, 7.4 → 7); ใช้ได้เพราะคะแนนไม่ติดลบ
ปัดครั้งเดียวต่อช่องหลังรวมน้ำหนัก ไม่ปัดราย source
(ก่อน OQ-016 มี source เดียว ตาม DES-008)

หาก integer_target เกิน target_max ให้ปฏิเสธ
ไม่ clamp ไม่เปลี่ยนคะแนนเต็มปลายทางเอง
missing/ungraded/error ไม่กลายเป็นศูนย์ (ต่างจาก DES-011 ที่นับ 0 เฉพาะการเลื่อน Level)
quiz ที่ policy ไม่นับคะแนนส่งออกไม่ได้

preview แสดงคะแนนก่อนปัด หลังปัด คะแนนเต็ม น้ำหนัก แหล่งผล
และผลปลายทางเดิม รวมผลพิเศษ/override ที่เกี่ยวข้อง

## Lock และ optimistic check

ก่อนเขียน ตรวจ teacher assignment, enrollment, period,
header/column close state, settings และ soft-lock protocol เดิม
ค่าที่ไม่รู้ความหมายให้ fail closed

PG transaction ต้อง lock grade/header/settings/assessment/detail
และ override rows ที่เกี่ยวข้องในลำดับคงที่ตาม adapter ที่ DBA ตรวจ
ตรวจ expected identity/token กับ snapshot อีกครั้งก่อน mutation
ใช้ CAS ที่ฐานข้อมูล ไม่ใช่ read-compare-write แยก transaction

ถ้า token เปลี่ยนแม้คะแนนกลับมาเท่าเดิม ให้ conflict
ห้ามถือว่า old == new พิสูจน์ว่าไม่มี concurrent edit

### กลไกกันชนกับ writer เดิม (xmin) — ข้อเสนอ SA

ฝั่ง SchoolBot: snapshot เก็บ xmin ของ PgtgradeDetail (และ row อื่นที่เขียน)
ณ เวลา preview; ตอน apply ใช้ SELECT ... FOR UPDATE แล้ว UPDATE โดยมีเงื่อนไข
pk ตรงและ xmin ตรงค่า snapshot ร่วมกับ before_document_hash
affected rows = 0 → conflict ของนักเรียนคนนั้น
xmin เป็น system column จึงไม่เปลี่ยน schema; เปลี่ยนทุกครั้งที่ row ถูก update
และเป็น transaction id ที่วนรอบได้ จึงใช้เป็น CAS ระยะสั้นภายในอายุ preview เท่านั้น
ไม่ใช่ version ทางธุรกิจหรือ permission token
SQL จริงให้ DBA เขียนและตรวจ

ฝั่ง writer เดิม: row lock ของ SchoolBot ไม่ป้องกันครูที่เปิด sheet เก่า
แล้วบันทึกทับหลัง SchoolBot commit — ปลอดภัยเฉพาะเมื่อ writer เดิม
ใช้ expectedRowVersions (xmin) เป็นเงื่อนไขเขียนจริง หรือ merge รายช่อง
โดยไม่ทับช่อง SchoolBot

## Atomicity / outbox / replay

หน่วย atomic ที่เสนอ: นักเรียนหนึ่งคน ครอบคลุมช่องทั้งหมดที่เลือก
ใน PGGradeDB เดียวกัน
ไม่อ้าง atomic ทั้งห้องหรือข้าม School DB ↔ PGGradeDB

1. School transaction ตรวจ preview แล้วบันทึก confirmation,
   ScoreExport, outbox รายคน, idempotency result และ audit พร้อมกัน
2. worker claim outbox ด้วย lease+Version และ serialize ต่อ
   SchoolId/grade context/learner
3. ตรวจสิทธิ์ครู (DES-012) และเงื่อนไขปัจจุบันก่อนเริ่ม PG transaction
4. PG transaction ตรวจ receipt เดิม, lock/CAS (xmin), merge owned cells,
   คำนวณด้วยสูตรที่ผ่าน G-PARITY และเขียน durable receipt/audit พร้อมคะแนน
5. School transaction บันทึก receipt และ applied/audit
6. crash หลังข้อ 4 ก่อนข้อ 5 ต้องอ่าน receipt เพื่อ reconcile
   ไม่เขียนคะแนนซ้ำ

ข้อเสนอ receipt: ใช้ PgtgradeAuditLog เดิม โดย
Application="SchoolBot", MethodName="ScoreExport.Apply";
Parameter มี versioned JSON ของ operation key, payload hash,
source/preview refs, actor, target IDs และ before/after hashes
SEmp = sEmp ของครูผู้ยืนยันจริง (P ของ session ตาม DES-012)
ไม่ใช่ service identity แทนครู; session ที่ไม่มี P employee ยืนยันไม่ได้

GradeAuditLogId เป็น int8 ส่ง API เป็น decimal string
ไม่ใช้ K และไม่เพิ่ม unique index ใน PGGradeDB

เพราะไม่มี unique receipt key ที่ยืนยันได้:
SchoolBot writers ทุก instance ต้องใช้ transaction-scoped
operation lock เดียวกันก่อนค้น/เพิ่ม receipt
DBA ต้องรับรอง lookup, retention, permissions และ isolation
receipt ต้อง commit พร้อม score mutation ใน PG transaction เดียว

หากใช้ receipt นี้ไม่ได้:
outbox เพียงอย่างเดียวไม่ให้ exactly-once
timeout ที่ผลไม่แน่นอนต้องเป็น unknown/reconciling
ห้าม retry blind และห้ามใช้คะแนนเท่ากันเป็นหลักฐานว่าเราเป็นผู้เขียน

เมื่อ conflict ระหว่าง worker:
rollback นักเรียนคนนั้น หยุดงานที่ยังไม่เริ่มใน export
คงผลของคนที่ commit แล้ว แสดง partial outcome ตามจริง
สร้าง preview ใหม่เฉพาะส่วนที่เหลือและให้ครูตัดสิน/ยืนยันใหม่
ไม่ rollback คะแนนที่สำเร็จด้วยการเขียนทับย้อนหลังอัตโนมัติ

## Idempotency และ audit

request key เดิม/body เดิมคืน resource เดิม
key เดิม/body ต่างคืน IDEMPOTENCY_CONFLICT
หนึ่ง preview ยืนยันได้เป็น export เดียว แม้ใช้ key คนละค่า
replay หลังผลถูกแก้โดยครูต้องคืน receipt เดิม ไม่ apply ซ้ำ

SchoolBotAuditEvent บันทึก create-preview, confirm, resolve,
apply, reconcile, conflict, skip และ deny; Actor ตามรูปแบบใน DES-012
รายละเอียดคะแนนอยู่ snapshot ที่จำกัดสิทธิ์ ไม่ใส่ใน Reason แบบเปิด
รักษา audit/idempotency tombstone ตาม data-contract-rules
retention ต้องไม่ทำให้ replay ที่ไม่แน่นอนกลับไปเขียนใหม่

## ทางเลือกและการตรวจ

เลือก SchoolBot adapter + explicit preview + outbox/receipt + xmin CAS
ปัดตกเรียก service score-record เดิม เพราะผู้ใช้ตัดสินแล้ว (decisions-023)
และ draft contract ไม่มี operation key/durable receipt
ปัดตก replace ScoreData จาก preview เพราะทับช่องครู
ปัดตกส่ง GetScore100 ตรง เพราะข้ามสูตร/override
ปัดตก retry จาก outbox อย่างเดียว เพราะ crash window ข้าม DB
ปัดตก automatic submit เพราะอาจล็อกทั้งใบ
ปัดตกสร้างสูตรจากชื่อฟิลด์/proto comment แทน parity

ต้องทดสอบก่อนเปิดจริง: G-PARITY และ G-COEXIST ครบ,
teacher edit ก่อน/หลัง preview, ABA change, legacy blind writer,
duplicate rows/identifiers, override เกิดพร้อม export, midpoint 7.5→8 และ 7.4→7,
missing score, หนึ่งวิชาไม่มีสิทธิ์, สิทธิ์ถูกถอนระหว่าง preview–apply,
crash ทุก commit boundary, lease takeover, receipt replay หลังครูแก้คะแนน
