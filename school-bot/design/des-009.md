## สูตรคะแนนช่องและการป้องกัน LearnerId ชนกัน

ทุก source มี earned/max จาก authoritative assessment/attempt และ policy revision ที่แน่นอน; max > 0, 0 <= earned <= max
quiz ใช้คะแนนสูงสุดของ attempt ที่ submit แล้วตามค่าเริ่ม (decisions-024)
ผลการสอบซ่อม Test ใช้คะแนนสูงสุดระหว่างครั้งจริงกับครั้งซ่อม ไม่มีเพดาน (ยืนยันตาม [decisions-025](../requirement/decisions-025.md) และ [decisions-026](../requirement/decisions-026.md))

**การป้องกัน `LearnerId` ของครูชนกับนักเรียน (`sEmp == sId`)**:
- `learner_ids` ใน `ScorePreview` ต้องเป็นสมาชิกนักเรียนใน roster ของห้องเรียน (`TUser.sID` จาก School DB) เท่านั้น
- เมื่อดึงผลจาก `SchoolBotSubmission` ต้องกรองเฉพาะแถวที่ผูกกับ `SchoolBotProject` ซึ่งมี `OwnerKind = 'student'` และ `OwnerId = LearnerId` เท่านั้น (และใน schema ปัจจุบันไม่อนุญาตให้ `ProfileKind = 'employee'` สร้าง `Submission` หรือ `Attempt` — ทาง A ยืนยันแล้วตาม [decisions-032](../requirement/decisions-032.md); ห้ามผล Cloud ของ employee รวม Guest import ตาม [กฎผลเรียน](learning-rules-032-034.md))

normalized = earned/max ของ source เดียว
raw_target = earned/max × target_max
integer_target = floor(raw_target + 0.5)

คำนวณด้วย decimal ไม่ใช่ binary float ปัด half-up ตามมติ decisions-023 / BR-050-05: x.5 ขึ้นไปปัดขึ้น ต่ำกว่า x.5 ปัดลง (7.5 → 8, 7.4 → 7) ปัดครั้งเดียวต่อช่องจาก source เดียวตาม decisions-032/033; ทุกช่องคำนวณจาก earned/max เดิม ไม่ใช้ผลปัดของอีกช่อง

หาก integer_target เกิน target_max ให้ปฏิเสธ ไม่ clamp ไม่เปลี่ยนคะแนนเต็มปลายทางเอง missing/ungraded/error ไม่กลายเป็นศูนย์ (ต่างจาก DES-011 ที่นับ 0 เฉพาะการเลื่อน Level) quiz ที่ policy ไม่นับคะแนนส่งออกไม่ได้

## Snapshot และการยืนยัน

Preview ผูก SchoolId, principal, course run, mapping (`id` + `update_date`), policy revision, roster, source result (`id` + `update_date`), writer/calculator version, target context/locks/settings, raw old cell values, destination row identity/`xmin` (ของ PGGradeDB) ณ เวลาอ่าน

SnapshotHash เป็น SHA-256 ของ canonical snapshot ที่ server สร้าง; เสนอ preview อายุ 15 นาที เป็น technical bound และเป็นเพดานอายุของ `xmin` ที่ใช้ CAS ใน PGGradeDB
ยืนยันต้องใช้ `preview_id` + `snapshot_hash` + `If-Match` (opaque `ETag` จาก `UpdateDate` ของ `SchoolBotScorePreview` ตาม [decisions-030](../requirement/decisions-030.md)) ไม่รับคะแนนใหม่หรือ destination IDs ใหม่ในคำสั่งยืนยัน

## การรักษาช่องครูและผลพิเศษ (บังคับในโค้ดตาม decisions-029)

เนื่องจากใช้บัญชี DB เดิมต่อ PGGradeDB โค้ด adapter ต้องบังคับอย่างเคร่งครัด:
- ระบุช่องด้วยคู่ AssessmentId + ScoreIdentifier ภายใต้ grade context ต้องพบตรงกันหนึ่งรายการและตรงกับ `SchoolBotGradeSlot` ที่ active; duplicate/ambiguous ให้หยุด ห้ามเลือก array index จาก Ordinal
- อ่าน ScoreData ล่าสุดใน transaction แล้วเปลี่ยนเฉพาะ Score ของช่องที่มี ownership ถูกต้อง; รักษารายการอื่น unknown properties ลำดับรายการ และผลพิเศษ
- ไม่มี detail/header/assessment ที่ต้องใช้: ให้ TARGET_NOT_READY ห้ามสร้าง implicit zero rows
- พบ PgtgradeEdit ที่เกี่ยวข้อง หรือผลพิเศษที่ไม่ใช่ none: block นักเรียนคนนั้น ห้าม clear override/แปลงผลพิเศษเป็นศูนย์

## Lock และกลไกกันชนกับ writer เดิม (xmin ของ PGGradeDB)

- ตารางของ SchoolBot DB ใช้ `UpdateDate` (`clock_timestamp()`) เป็น optimistic concurrency token ([decisions-030](../requirement/decisions-030.md))
- ตารางปลายทางใน **PGGradeDB** (`PgtgradeDetail` ฯลฯ) คงการใช้ system column **`xmin`** เป็น CAS ระยะสั้นภายในอายุ preview เพื่อกันชนกับ writer เดิม: ตอน apply ใช้ `SELECT ... FOR UPDATE` แล้ว `UPDATE` โดยมีเงื่อนไข PK ตรงและ `xmin` ตรงค่าใน snapshot ร่วมกับ `before_document_hash`; affected rows = 0 → conflict ของนักเรียนคนนั้น
- เกณฑ์ผ่าน G-COEXIST และ G-PARITY (inventory trigger/function, fixtures ที่ปิดบังข้อมูลส่วนบุคคล, เทียบผลกับระบบเดิม 100%) คงตามสัญญาเดิมทุกข้อ

## Atomicity / outbox / replay ข้าม DB (SchoolBot DB ↔ School DB ↔ PGGradeDB)

หน่วย atomic: นักเรียนหนึ่งคนใน PGGradeDB เดียวกัน ไม่อ้าง atomic ทั้งห้องหรือข้าม SchoolBot DB ↔ School DB ↔ PGGradeDB ([decisions-027](../requirement/decisions-027.md)):
1. ก่อน confirm: re-check สิทธิ์ครูรายวิชา/roster/term จาก **School DB** และสถานะ target ใน **PGGradeDB** ผ่าน connection แยก แล้วเปิด **SchoolBot DB transaction** ตรวจ `UpdateDate` ของ `ScorePreview` (`If-Match`), บันทึก `ScoreExport`, `ScoreOutbox` รายคน (`UQ_SchoolBotScoreOutbox_OperationKey`, `UQ_SchoolBotScoreOutbox_Export_Item`), `Idempotency` และ `AuditEvent` พร้อมกัน (และตรวจใน application ว่าทุกแถวอยู่ `SchoolId` เดียวกันตาม `db/review-005.md` (memory))
2. Worker claim `SchoolBotScoreOutbox` ใน **SchoolBot DB** ด้วย lease + `UpdateDate = clock_timestamp()` (`CreateBy/UpdateBy = null` ตาม [decisions-028](../requirement/decisions-028.md)) และ serialize ต่อ `SchoolId`/grade context/learner
3. Worker **re-check สิทธิ์ครู (DES-012) และเงื่อนไขปัจจุบันจาก School DB** และตรวจ `SchoolBotLicense` active ใน SchoolBot DB ก่อนเริ่ม PGGradeDB transaction
4. **PGGradeDB transaction**: ใช้ transaction-scoped operation lock, ตรวจ receipt เดิมใน `PgtgradeAuditLog`, lock/CAS (`xmin`), merge เฉพาะช่องที่เป็นเจ้าของ, คำนวณด้วยสูตรที่ผ่าน G-PARITY และ INSERT durable receipt ลง `PgtgradeAuditLog` (`Application="SchoolBot"`, `MethodName="ScoreExport.Apply"`, `SEmp` = `sEmp` ของครูผู้ยืนยัน) พร้อมคะแนนใน transaction เดียว
5. **SchoolBot DB transaction**: บันทึก `ReceiptId`, `ReceiptHash`, `State='applied'` และ `AuditEvent`
6. Crash หลังข้อ 4 ก่อนข้อ 5: worker อ่าน receipt ใน `PgtgradeAuditLog` เพื่อ reconcile ลง SchoolBot DB โดยไม่เขียนคะแนนซ้ำ; เมื่อเกิด conflict ของนักเรียนคนใดให้ rollback คนนั้น หยุดแถวที่ยังไม่เริ่ม คงผลคนที่สำเร็จ และให้ครู resolve/confirm เฉพาะส่วนที่เหลือ
