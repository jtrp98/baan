# DES-011 — ระบบเสนอเลื่อน Level และครูยืนยันทั้งห้อง — Rev4

อ้าง REQ-048 (BR-048-01..06, AC-048-01..04); decisions-020:31, decisions-024..030;
DES-010 (คะแนนรวม), DES-012 (สิทธิ์); [db/review-005.md](../db/review-005.md); REQ-037/039 เป็นฐานเดิม

## ขอบเขตและ Placement

Level เป็นระดับหลักสูตร ไม่ใช่การเลื่อนชั้น/ย้ายห้องในทะเบียนนักเรียน ระบบเสนอจากค่าเฉลี่ยคะแนนรวมของห้อง ครูยืนยันทั้งห้องเท่านั้น ไม่เขียน CompassStudentLevelScore หรือทะเบียนชั้นเรียนเดิม ไม่เลื่อนนักเรียนเป็นรายบุคคล หน้าครูอยู่ web-system (BR-048-05); หน้าตั้งเกณฑ์อยู่ admin ส่วนกลาง

- ตาราง `SchoolBotLevel`, `SchoolBotLevelPromotionPolicy`, `SchoolBotCourseRun`, `SchoolBotLevelProposal`, `SchoolBotIdempotency` และ `SchoolBotAuditEvent` อยู่บน **SchoolBot DB (`10.0.0.128:9499`)** ตาม [decisions-027](../requirement/decisions-027.md)
- การอ่านรายชื่อนักเรียนในห้อง (roster), ข้อมูลสิ้นเทอม/เทอมถัดไป (`TTerm`) และสิทธิ์ครูรายวิชา (`TplanCourseTeacher`) อ่านจาก **School DB** ผ่าน connection แยกด้วย**บัญชี DB เดิม** ([decisions-029](../requirement/decisions-029.md))

## Policy (มติ decisions-024)

- เกณฑ์ (threshold) เป็นข้อมูลราย Level ที่ admin ส่วนกลางตั้ง (staff role `level_policy_admin` ตาม DES-012) ค่าเริ่ม 70.000000 ช่วง 0..100 เก็บเป็น revision immutable; proposal อ้าง revision ที่ใช้
- เงื่อนไข "สูงกว่าเกณฑ์" = strict `>` (เท่ากับเกณฑ์ไม่ผ่าน, AC-048-04)
- ประเมินตอนสิ้นเทอม มีผลเทอมถัดไปทั้งห้อง; ไม่ถึงเกณฑ์: อยู่ Level เดิมอีกเทอม และแสดงส่วนที่ขาด
- ค่าเฉลี่ยนับนักเรียนทุกคนใน roster; กิจกรรมที่ไม่ส่ง/ไม่มีผลนับ 0 (ใช้เฉพาะการเลื่อน Level; ส่งคะแนนไม่แปลงเป็น 0 ตาม DES-009)

ยังต้องยืนยัน:
- สูตรรวมยืนยันแล้วตาม decisions-034 ใช้ policy ที่ freeze ตาม [กฎผลเรียน](learning-rules-032-034.md); ขาด policy ที่ใช้ได้คืน 409 POLICY_NOT_CONFIGURED
- แหล่ง roster ของห้อง ณ สิ้นเทอม (สมมติฐาน — ยังไม่ยืนยัน: `TstudentClassroomHistory` ตาม source-review-004) และวันสิ้นเทอม/เทอมถัดไปจากข้อมูลเทอมเดิม — SA ตรวจ source ก่อน build
- สิทธิ์ยืนยันเมื่อ CourseRun ผูกหลายวิชา: ข้อเสนอ SA = ครูรายวิชาคนใดก็ได้ของ `PlanCourseIds` ของ CourseRun (DES-012) โดย `If-Match` (`UpdateDate`) และ `ux_schoolbot_levelproposal_confirmed_per_run` กันยืนยันซ้ำ

## การคำนวณ, Snapshot และการป้องกัน LearnerId ชนกัน

- **การป้องกัน `LearnerId` ครูชนกับนักเรียน (`sEmp == sId`)**: สมาชิกที่นำมาคำนวณ `total` และ `average` ต้องมาจาก roster นักเรียน (`TUser.sID`) ของห้องเรียนใน School DB เท่านั้น และเมื่อดึงผลจาก `SchoolBotSubmission` ต้องกรองเฉพาะแถวที่อ้าง `SchoolBotProject` ที่ `OwnerKind = 'student'` เท่านั้น (อ้าง [db/proposal-learnerkind.md](../db/proposal-learnerkind.md))
- `total` รายคน = คะแนนรวมหลักสูตร 0–100 ตาม `ScoringPolicy` revision และ `formula_version` (DES-010) โดยกิจกรรมที่ไม่มีผลใช้ 0; ผล expired ที่ตรวจเสร็จตาม042เข้า selection และสูตรเดิม ไม่ถือว่าขาดผลเพราะไม่กดส่ง คง roster, strict threshold, snapshot/recheck และการยืนยันทั้งห้องเดิม
- `average = Σ total / member_count`; `eligible = average > threshold`; `gap` (เมื่อไม่ผ่าน) = `threshold − average`
- proposal เก็บ roster และผลของทุกคนเป็น immutable snapshot รวม source result refs (`id` + `update_date`), scoring policy revision, `formula_version`, promotion policy revision/threshold, current/target curriculum, average, gap, effective context และ hash

{threshold:DecimalString,reason:T1000} + If-Match (`ETag` ของ `SchoolBotLevel` ตาม [decisions-030](../requirement/decisions-030.md))
201 {id:K,revision:N,level_update_date:D} (+ ETag ของ Level)

POST /v2/course-runs/{id}/level-proposals
{} → 201 ProposalView (+ ETag จาก `UpdateDate`)
ใช้ได้เมื่อ `CourseRun.Lifecycle = closing|closed`; ไม่งั้น `409 TERM_NOT_ENDED`

GET /v2/level-proposals/{id} → 200 ProposalView (+ ETag)

ProposalView={
id:K,update_date:D,course_run_id:K,target_curriculum_id:K,
eligible:B,average:DecimalString|null,threshold:DecimalString,
gap:DecimalString|null,
member_count:integer>=0,complete_count:integer>=0,
snapshot_hash:H,effective_at:D,reason_codes:T64[],
state:proposed|promoted|retained|max_level|stale,
successor_run_id:K|null
}

state ตอนสร้าง:
- eligible และมี Level ถัดไป → `proposed` (รอครูยืนยัน)
- eligible แต่เป็น Level สูงสุด → `max_level` (เรียน Level เดิม)
- ไม่ eligible → `retained` ทันทีตามมติ (ไม่ต้องรอครู) และสร้าง successor Level เดิม

POST /v2/level-proposals/{id}/confirm
{snapshot_hash:H} + If-Match (`ETag`)
201 {proposal_id:K,successor_run_id:K,update_date:D,state:"promoted"} (+ ETag)

POST /v2/level-proposals/{id}/decline
{snapshot_hash:H,reason:T1000} + If-Match (`ETag`)
200 {id:K,update_date:D,state:"retained",successor_run_id:K} (+ ETag)

## Transition และการ Re-check ข้าม DB ก่อน Commit

- เนื่องจากไม่มี transaction เดียวครอบ SchoolBot DB กับ School DB ([decisions-027](../requirement/decisions-027.md)): ก่อน `POST /level-proposals` และก่อน `confirm`/`decline` ต้องอ่านและ **re-check สิทธิ์ครูรายวิชา, roster นักเรียน และข้อมูลเทอมถัดไป (`NYear`/`NTerm`) จาก School DB** รวมทั้ง re-check `SchoolBotLicense` active, source results, policy revisions และ current/target curriculum ใน SchoolBot DB
- เปลี่ยนแม้หนึ่งส่วนให้ `409 PROPOSAL_STALE` ต้องเสนอใหม่; เทอมถัดไปยังไม่มีใน School DB → `409 NEXT_TERM_NOT_AVAILABLE` ไม่สร้าง successor
- ชั้น application ตรวจว่า `CourseRun`, `LevelProposal` และ `SuccessorRun` อยู่ `SchoolId` เดียวกัน (คู่กับ single-column FK ชี้ PK ตาม [db/review-005.md](../db/review-005.md))
- `confirm`/`decline`/`retained` บันทึก `LevelProposal` (`UpdateDate = clock_timestamp()`), `successor CourseRun`, `AuditEvent` และ `Idempotency` ใน **SchoolBot DB transaction เดียว** (บังคับ `ux_schoolbot_levelproposal_confirmed_per_run`, `ux_schoolbot_levelproposal_successor_unique` และ `ux_schoolbot_courserun_one_successor`)
