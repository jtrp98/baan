# REQ-021 — การยืนยันตัวตนและสิทธิ์เรียก API (API Authentication & Authorization)

ตัดสินใจ 2026-09-29 (OQ-1, OQ-29 — ผู้ใช้ตอบทั้งหมด): ทุก endpoint ของ backend timetableai ต้องมี `[Authorize]` ด้วยวิธีเดียวกับ `BypassAcademic.aspx.cs` — token JWT ที่ระบบ SB ออก ส่งทาง `Authorization: Bearer` verify ด้วย `token_secret` ตัวเดียวกับระบบ SB · ต้องตรวจโรงเรียนใน request ให้ตรงกับโรงเรียนใน token และตรวจว่าผู้เรียกมีสิทธิ์เมนูของหน้านั้น ตามสิทธิ์ใน `TMenuPermission` (MenuID: 401 `/timetable` + `/timetable/[year]`, 402 `/manage-timetable`, 403 `/settings`, 404 `/create-class-period`, 422 `/subject-settings`) · **ไม่มี endpoint ยกเว้น** · as-built ยังไม่มี authorization ใด ๆ (D1) จึงเป็น target · ผู้ใช้อนุมัติ breaking change (ผู้เรียกที่ไม่มี token ได้ 401 รวม localhost ตอนพัฒนา) · `token_secret` ที่ถูก commit ใน repo (D49) ผู้ใช้เลือกไม่ rotate — เป็นความเสี่ยงที่ผู้ใช้รับ ยังต้องผ่านรอบ `security` (design.md DES-018)

*เพิ่ม 2026-10-02 (session date — ดู Change Log) · ผู้ใช้ตอบใน chat ส่งต่อโดย coordinator — BA ไม่ได้ถามเอง · บันทึกโดย `system-analyst` ใน design.md Rev 18 (DES-018 §43.2b ข้อ 1 และข้อ 4 (a)–(e), BR-74 (ข), BR-76 (ก), BR-88; design.md ระบุวันที่ผู้ใช้เลือกเป็น 2026-10-01):*

- **ความล้มเหลวของการโหลดข้อมูลที่ Generate/Save ต้องใช้ (ผู้ใช้เลือก "SA-Q19 = ทางเลือก A"):** เมื่อการโหลดข้อมูลที่จำเป็น (required) ล้มด้วยเหตุใดก็ตามที่ไม่ใช่ 401 — **รวม HTTP 200 ที่ `status !== 1`** — หน้ายังดูได้ · Generate/Regenerate, การบันทึกตาราง และปุ่ม Save ของหน้าตั้งค่าเงื่อนไขระบบ ถูกบล็อก · Generate ที่รออยู่ถูกยกเลิก · ทางกู้คืน = reload หน้า **จนกว่า UX-004 จะได้รับการเซ็น** · ข้อมูลที่จำเป็นของ Generate: class-period, setting, subject-settings, get-all-by-year, teacher-group (และ load ของเส้นทาง restore) · (การแยกชั้น required/ไม่บังคับรายละเอียดอยู่ใน design.md §43.2b ข้อ 3 — เป็นงานเชิงเทคนิคของ SA)
- **401 = หน้า SessionExpired เท่านั้น** — ไม่มี toast/Alert/ข้อความ error อื่นเพิ่ม
- **สถานะผู้เรียกและโรงเรียน (ผู้ใช้รับ "SA-Q20 (ก) และ (ข)"):** (ก) admin ที่ไม่ active หรือถูกลบ = ถูกปฏิเสธ (ข) ผู้ใช้ทั่วไปต้องอยู่ในโรงเรียนที่ active และไม่ถูกลบ — ไม่เช่นนั้นได้ 403 ที่ endpoint ที่มีการตรวจสิทธิ์ และ endpoint เมนู Sidebar ตอบ 200 โดยทุกเมนูอ่านไม่ได้ → Sidebar ปิดทั้งหมดเป็นสถานะ "ไม่มีสิทธิ์" (noPermission) · **"active"/"ถูกลบ" อยู่ที่คอลัมน์ใดและค่า null หมายถึงอะไร ยังไม่ยืนยัน → OQ-39** (ห้ามเดา) · *เพิ่ม 2026-10-02 (OQ-39 = SA-Q21 **ปิดแล้ว 2026-10-02** — ผู้ใช้ตอบใน chat ผ่าน AskUserQuestion ของ orchestrator · วันที่ผู้ใช้ให้):* **โรงเรียนผ่าน** เมื่อ `TCompany.isActive != false` และ `TCompany.cDel != true` · **admin ผ่าน** เมื่อ `TAdmin.active != false` และ `TAdmin.del != true` · **ไม่ใช้ `TAdmin.IsActive`** · ค่า null = active / ไม่ถูกลบ · (คำตอบตามตัวอักษรอยู่ในแถว OQ-39)

**Acceptance criteria:**

- AC-060 *(target)* — คำขอที่ไม่มี token หรือ token ไม่ผ่านการ verify/หมดอายุ ได้ 401 ทุก endpoint (ไม่มี endpoint ยกเว้น)
- AC-061 *(target)* — คำขอที่โรงเรียนใน request ไม่ตรงกับโรงเรียนใน token ได้ 403 และฟิลด์ผู้บันทึก/ผู้แก้ไข (audit) ถูกกำหนดจาก `user_id` ใน token ไม่ใช่ค่าที่ client ส่งมา
- AC-062 *(target)* — ผู้เรียกที่ไม่มีสิทธิ์เมนู (`TMenuPermission`) ของหน้าที่ endpoint นั้นสังกัด ได้ 403; การเขียนต้องมีสิทธิ์เขียน การอ่านต้องมีสิทธิ์อ่านตามที่ระบบ SB กำหนด; endpoint ที่ไม่อยู่ในตารางจับคู่หน้า↔เมนูได้ 403
- AC-063 *(target)* — frontend ส่ง `Authorization: Bearer` ในทุกการเรียก API ของโมดูล (รวมการเรียกแบบ fire-and-forget); 401 พาผู้ใช้ไปหน้า session หมดอายุเดิม และ 403 แสดงเป็นความล้มเหลวที่ผู้ใช้เห็น (ข้อความให้ `uxui-designer`)
- AC-064 *(target — ผู้ใช้ยืนยัน 2026-09-30, OQ-35 / design.md D53)* — การแสดงเมนู timetableai ใน Sidebar ผูกกับสิทธิ์ MenuID 401/402/403/404/422 เดียวกับสิทธิ์ API · ผู้ใช้ที่ไม่มีสิทธิ์เมนูใด **เห็นรายการเมนูนั้นเป็นสถานะปิดใช้งาน (disabled)** — ไม่ซ่อน และไม่ใช่ให้กดเข้าไปแล้วได้ 403 · รูปแบบการแสดงสถานะปิดให้ `uxui-designer`
  - *เพิ่ม 2026-09-30 (ผู้ใช้ตอบ OQ-38):* (1) **ระหว่างกำลังโหลดสิทธิ์เมนู** — รายการเมนู timetable ทุกรายการเป็น **disabled** พร้อม spinner เล็กที่หัวกลุ่มเมนู (fail-closed) (2) **เมื่อตรวจสิทธิ์ไม่สำเร็จ** (401/403/error ใด ๆ) — รายการเป็น **disabled** พร้อมไอคอนเตือนและ tooltip บอกให้ผู้ใช้ reload หน้า · **ไม่ retry อัตโนมัติ** · ต้อง**แยกแยะได้จากสถานะ "ไม่มีสิทธิ์"** · หน้าตา/ถ้อยคำ tooltip = `uxui-designer`

## Constraints & Assumptions

- โมดูลทำงาน**รายปีการศึกษาเท่านั้น** ไม่รองรับภาคเรียน — โครงสร้างข้อมูลฝั่งโมดูลไม่มี term (design.md §18.3) — **as-built fact ณ 2026-09-21; อยู่ระหว่างเปลี่ยนแปลงตาม REQ-012 (ยืนยันธุรกิจแล้ว รอ system-analyst amend design.md)**
- ทุกกติกาถูกบังคับที่ app layer เท่านั้น (ฐานข้อมูลฝั่งโมดูลไม่มี FK/unique/check) — การแก้กติกาใด ๆ ต้องคงจุดบังคับเดิม ห้ามย้ายไปพึ่ง constraint ระดับฐานข้อมูลโดยไม่แก้ design ประกอบ (design.md DES-001 Fallback)
- การคำนวณทั้งหมดอยู่ฝั่ง client (browser, main thread) — backend เป็น CRUD ล้วน ไม่มี solver/AI/job ฝั่ง server (DES-005, DES-006)
- การบันทึกไม่เป็น atomic (ไม่มี DB transaction — D29) และ save ตารางแจ้งผลเท็จ (D26) — เป็นข้อเท็จจริง as-built ที่บันทึกไว้ การแก้เป็นการตัดสินใจตาม design.md §32.1 ข้อ 2–3
- **Auth (ยืนยัน 2026-09-29 — OQ-1):** ~~สมมติฐานว่ามี gateway คุม auth~~ ถูกแทนที่ด้วยการตัดสินใจ: API ของโมดูลต้องมี `[Authorize]` ด้วยวิธีเดียวกับ `BypassAcademic.aspx.cs` (JWT + `token_secret`) · ก่อนมี design + implement, backend as-built ยังไม่มี authorization ใด ๆ (D1) — **ยังเป็น blocker ก่อน production** · กลไกปิดแล้ว (OQ-29, 2026-09-29): Bearer JWT + `token_secret` เดียวกับ SB + สิทธิ์ตามเมนูและ `TMenuPermission` (MenuID 401/402/403/404/422) ไม่มี endpoint ยกเว้น · ผู้ใช้อนุมัติ breaking change 401 · *2026-10-02:* กติกาสถานะ admin/โรงเรียน (AC-071/AC-072) ขยายขอบเขต breaking เกินการอนุมัติ 2026-09-29 — **ยังไม่ได้รับทราบ (OQ-40)** · คอลัมน์และความหมาย null ของ "active"/"ถูกลบ" ยังไม่ยืนยัน (OQ-39) — ระหว่างรอ design.md ใช้คอลัมน์ที่ resolver ใช้อยู่เป็น fallback เชิงเทคนิค (สมมติฐาน — ยังไม่ยืนยัน)
- **`token_secret` (ความเสี่ยงที่ผู้ใช้รับ 2026-09-29):** SA รายงาน (D49) และผมยืนยันว่ามีคีย์ `Token_Secret` ใน `sb-api-academic-timetable-ai/AITimeTableBackend/appsettings.json` บรรทัด 13 (ไม่ได้บันทึกค่า) — ผู้ใช้ตัดสินใจ **"ปล่อยไว้แบบนี้"** ไม่ rotate/ย้ายไป secret store: ใครอ่าน repo ได้ปลอม token ของ SB ได้ · ผู้ใช้ไม่มีสิทธิ์ rotate เอง (เป็นการกระทำของเจ้าของระบบ SB) · ความเสี่ยงนี้เป็นของ DES-018 และยังต้องผ่านรอบ `security` (Critical/Important = ประตูมนุษย์)
- **`BACKEND_URL` (ตัดสินใจชั่วคราว 2026-09-29 — OQ-4):** production ชี้โดเมน dev (`dev-service-academic-timetable-ai.schoolbright.co` — D17) ต่อไปก่อน ไม่ต้องมีวิธี override ในตอนนี้ · ความเสี่ยง: production ใช้ backend/ข้อมูลของ dev · ต้องทบทวนเมื่อมี prod backend · **ข้อมูลใน DB (ผู้ใช้ยืนยัน 2026-09-30):** DB ที่โมดูลใช้อยู่ตอนนี้ (production frontend → backend dev, R32) **ไม่มีข้อมูลโรงเรียนจริง มีแต่ข้อมูลทดสอบ** · ต้องยืนยันซ้ำก่อนมีข้อมูล production (ยังไม่มีวันที่)
- **`nCourseIntensity` (ยืนยันเจตนา 2026-09-29 — OQ-2):** ต้องบังคับใช้จริง (ปัจจุบัน as-built เก็บอย่างเดียว — D12) · ระดับ 0/1/2 และสูตรหนัก/เบายืนยันแล้ว (OQ-30 ปิด 2026-09-29, design.md DES-019) · **เกณฑ์ "หนักเกิน" (ผู้ใช้ยืนยัน 2026-09-30 — OQ-34):** class-day ที่จำนวนคาบหนักเกิน ⌈คาบหนักทั้งสัปดาห์ ÷ วันที่มีคาบ⌉ ของห้องนั้น — T_c คำนวณต่อห้องเรียนจากกริดของห้องนั้นเองในตารางนั้น (ผู้ใช้ชี้แจง 2026-09-30) · `ConsecutiveHeavy` เฉพาะระดับ 2 · ระดับ 0 ไม่แสดงข้อเสนอแนะ · (design.md BR-78 ใช้เกณฑ์เดียวกันเป็นเป้าหมาย L1 ของ solver — การผูกนั้นเป็นการตีความเชิงเทคนิคของ SA) · หมวด {พื้นฐาน, เพิ่มเติม} = `TCourseGroup` (ผู้ใช้ตอบ 2026-09-29 — design.md Rev 10 SA-Q16) · ส่วน Class Continuity ยืนยันแล้วว่าต้องบังคับจริง (REQ-015, 2026-09-23)
- เอกสารนี้ครอบคลุมโมดูล timetableai (7 routes) **บวก integration ขาออกไป `/academic` ตาม REQ-019** (ส่งตารางผ่าน API ของ Service Academic — design.md §41) · ส่วนอื่นของระบบ `/academic` (หน้าจอ/ข้อมูลของระบบนั้นเอง), OCR/kruai import และ menu/notification service ยังอยู่นอกขอบเขต (design.md §22 — หมายเหตุ Rev 5)
