# ประเมินการใช้ schema เดิมกับภารกิจบทเรียน F3

Rev 1 · 2026-11-05 · วิเคราะห์โดย นายช่าง · ขอโดย ผู้ใช้ · ข้อเสนอสำหรับตรวจ physical schema

เทียบ [สัญญาระบบ F3](lessons-missions-contract.md) กับ [DDL 32 ตาราง](../../../build/db/schoolbot_db.sql) และ [ผลเทียบ catalog เดิม](../../../build/db/dba-095-schema-parity.md) ตรวจจากไฟล์ใน workspace โดยไม่มีการอ่าน catalog สดหรือทดลอง transaction กับฐานข้อมูล

## สิ่งที่ใช้ของเดิมได้

| ส่วน | Mapping และเงื่อนไข |
|---|---|
| เนื้อหาด่านและกติกาผ่าน | ใช้ `SchoolBotCurriculum` จัด revision ของเนื้อหา ใช้ `SchoolBotLesson` และ `SchoolBotActivity` อ้างกิจกรรมเดิม เสนอให้เก็บ metadata ของด่านในส่วนที่แยกชื่อไว้ใน `Activity.Config` เช่น เทอม ลำดับบนแผนที่ เงื่อนไขผ่าน การขวางด่านถัดไป และตัวเลือกคะแนน ต้องตรวจ schema ของ config ตามชนิดและเก็บข้อมูลเดิมของ `project-v1` หรือแบบสอบไว้ครบ |
| รหัสด่านคงที่ | ใช้ `ActivityKey` ได้เมื่อหนึ่งกิจกรรมเป็นหนึ่ง node ในแผนที่และมีการคง key ข้าม revision ใช้ `SchoolBotActivityId` และ `CurriculumId` ของฉบับที่เล่นเพื่ออ้าง snapshot ถ้าต้องนำกิจกรรมเดียวไปวางหลายด่าน ให้เพิ่ม `stage_key` แยกจาก key กิจกรรม |
| การเลือกแผนที่ที่เผยแพร่ | ใช้ revision หลักสูตรเดิมได้หากแต่ละ Level มีสายหลักสูตรที่ระบุชัดว่าเป็นแผนที่ภารกิจ และการเผยแพร่แผนที่เดินพร้อมหลักสูตร `Revision` ใช้เทียบภายใน `CurriculumKey` เดียว จึงห้ามเลือกเลข revision สูงสุดข้ามหลายหลักสูตรโดยอัตโนมัติ ถ้าต้องเผยแพร่แผนที่รายเทอมแยกจากหลักสูตร หรือเลือกหลายสายต่อ Level ให้มี record สำหรับแผนที่เผยแพร่โดยเฉพาะ |
| งาน Arm Lab / Block Lab | ใช้ `SchoolBotMission`, `SchoolBotCriteria`, `SchoolBotProjectRevision`, `SchoolBotSubmission` และ `SchoolBotAssessment` เป็นแหล่งงานและผลตรวจเดิม รอบภารกิจอ้าง `SubmissionId` ได้เมื่อการส่งงานเกิดขึ้นและตรวจว่า learner, mission และ revision ตรงกัน |
| สิทธิ์ผู้ใช้และการตรวจย้อนหลัง | ใช้การตรวจตัวตนและสิทธิ์ครูเดิม ใช้ `SchoolBotAuditEvent` สำหรับบันทึกว่าใครทำอะไร ใช้ `SchoolBotIdempotency` สำหรับ replay ใบตอบกลับของ API ตามช่วงที่ตั้งได้ ส่วนตัวตนรอบที่ซิงก์แล้วต้องตรวจจากข้อมูลรอบที่เก็บถาวร |

## ช่องว่างที่กระทบการตรวจรับ

| ข้อกำหนด | ข้อจำกัดของตารางเดิม | ทางเลือกที่ตรงกับสัญญา |
|---|---|---|
| CT-03–06 เปิด–ปิดด่านและเทอมรายห้อง รวมเปิดคืนจากผลออฟไลน์ | `SchoolBotCourseRunActivity` มี `CourseRunId`, `ActivityId`, `OpensAt`, `ClosesAt` สำหรับหน้าต่างกิจกรรมของรอบเรียนเดิม `SchoolBotCourseRun.NTerm` เป็นเทอมปีการศึกษา โครงนี้ไม่มีเหตุการณ์ปิดรายเทอมของแผนที่หรือคีย์เชื่อมการเปิดคืนกับคำสั่งปิดเดิม `AuditEvent.Reason` เป็นข้อความสูงสุด 1,000 ตัวและ DDL ไม่มีข้อบังคับ uniqueness สำหรับ `RequestId` | เพิ่มตารางเหตุการณ์สิทธิ์ห้องแบบ append-only ผูกโรงเรียน ห้อง Level เทอม และด่านเมื่อเป็นรายด่าน คีย์อ้างคำสั่งปิดเดิมและป้องกันการเปิดคืนซ้ำ ต้องจัดลำดับเริ่ม/ปิด/ซิงก์ใน transaction เดียวกันตามขอบเขตห้องและเทอม |
| CT-02, CT-05–08 รอบภารกิจแบบไม่มีคะแนน เริ่มออฟไลน์ ซิงก์ซ้ำ และตรวจตาม revision เดิม | `SchoolBotAttempt` บังคับ `CourseRunId`, `ActivityId` และ `MaxScore` มี snapshot ของการสอบตามโค้ดปัจจุบัน ส่วน `SchoolBotSubmission` บังคับ `ProjectRevisionId` จึงใช้ได้เฉพาะเมื่อมีงานส่ง ทั้งสองตารางไม่มี client UUID ของรอบสำหรับกันซิงก์ซ้ำระยะยาว | เพิ่มตารางรอบภารกิจให้เก็บ UUID, ห้อง ณ เวลาเริ่ม, revision ที่เริ่ม, หลักฐานเวลาและสถานะตรวจ, ผลและคะแนนแบบ nullable และ `SubmissionId` เมื่อมีงานส่ง ตรวจ UUID และ hash ของคำขอใน transaction ที่ล็อกต่อโรงเรียน โดยรองรับการเริ่มและจบเป็นคนละเหตุการณ์ |
| สิทธิ์เริ่มออฟไลน์และ Quiz ฝึกเรียน | DDL เดิมไม่มีสิทธิ์เริ่มออฟไลน์ที่ผูกด่านกับอุปกรณ์และ revision ส่วนคลังข้อสอบปัจจุบันตรวจเพียง `single_choice` และ `boolean` | พิจารณาใช้สิทธิ์ออฟไลน์แบบลงนามและเก็บรหัสสิทธิ์/หลักฐานบนรอบเมื่อซิงก์ ใช้ตารางสิทธิ์เพิ่มเฉพาะเมื่อมี requirement ค้นสิทธิ์ที่ออกแต่ยังไม่ได้ใช้หรือถอนสิทธิ์รายใบ ส่วนโจทย์ฝึกเรียนต้องมี config และ validation แยกจากสัญญาคลังข้อสอบเดิม |

## ข้อสรุปสำหรับ BAAN

ใช้ DDL เดิมเป็นฐานของเนื้อหาและงานส่งได้ ส่วนการเปิด–ปิดพร้อมประวัติและรอบออฟไลน์ควรมีข้อมูลถาวรแยกเพื่อให้ทดสอบ CT-03–08 ได้โดยรักษาสัญญาการสอบเดิม ข้อเสนอขนาดเล็กคือ **สองตารางใหม่** สำหรับเหตุการณ์สิทธิ์ห้องและรอบภารกิจ โดยตั้งอยู่บนสมมติฐานว่าเผยแพร่แผนที่พร้อม revision หลักสูตรและออกสิทธิ์ออฟไลน์แบบลงนามได้ ถ้าต้องแยกการเผยแพร่รายเทอมหรือมีนโยบายถอนสิทธิ์รายใบ ให้ประเมิน delta เพิ่มตามเงื่อนไขนั้น

การยืนยัน physical schema ต้องกำหนดคีย์กันซ้ำ วิธีจัดการ concurrency และตัวอย่างข้อมูลเก่าที่ต้องอ่านได้ก่อนนำไปใช้ [ร่าง Migration 003](../../../build/db/migration-003-lessons-missions.md) ใช้ PK แบบ `int4` identity และตรวจความซ้ำในบริการตามที่ผู้ใช้กำหนด รอผู้ใช้ตรวจและยังไม่มีผลยืนยันฐานจริง
