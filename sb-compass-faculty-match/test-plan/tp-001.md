## Test Strategy Summary

- **ไม่มี automated test framework** เหมือนกับ `sb-compass` — ทุก verification step เป็น code
  reading + manual/exploratory testing + acceptance-criteria worked examples
- **ไม่พบ `test-pyramid.yaml`** ในเรโปนี้ — ไม่มี floor ให้เทียบ บันทึกเป็นช่องว่างใน
  `## Unresolved Open Questions`
- โมดูลนี้มีสอง codebase: **`ClassOnlineWeb`** (C#, .NET Framework 4.8 — ฝั่งนักเรียน/การคำนวณ) และ
  **Curriculum Service** (FastAPI/Python ใหม่ — ฝั่งนำเข้า/อนุมัติหลักสูตร) — ระบุกำกับไว้ทุก test
  item ว่าอยู่ฝั่งไหน เพราะ `## Database Ownership Boundary` ห้ามข้ามเส้นเขียน/อ่านของแต่ละฝั่งเด็ดขาด
  ซึ่งเป็นจุดที่ต้องตรวจแยกเป็นพิเศษ
- 8 phases ของ `plan.md` (Contract Version 8) — Module E, F, G, I-a, H, I-b (+ Target Major Rules
  amendment), Entitlement Wiring, K — ครอบคลุมทั้งหมดยกเว้นรายการที่ยังบล็อกด้วย OQ ต่าง ๆ ซึ่ง
  ระบุไว้ต่อ phase และสรุปรวมใน `## Unresolved Open Questions`

### REQ-001 — นำเข้า PDF และแปลงเป็นข้อความ

**Level**: endpoint เดี่ยว (manual — อัปโหลดไฟล์ทดสอบจริง) + code reading

**Test cases**:

1. อัปโหลด PDF หลักสูตรจริง → ต้องเก็บทั้ง**ไฟล์ต้นฉบับ**และ**ข้อความที่แปลงแล้ว**แยกกัน (ตรวจย้อนหลัง
   ได้ว่าผลวิเคราะห์มาจากฉบับไหน)
2. **`conversion_status` — 3 ค่า**: `'ok'` (แปลงสำเร็จ + ข้อความหลัง trim ≥ 200 ตัวอักษร) ต้องเรียก
   AI ต่อ · `'empty'` (แปลงสำเร็จแต่ < 200 ตัวอักษร — ส่วนใหญ่คือ PDF สแกน) ต้อง**ห้ามเรียก AI**
   เข้าคิวพร้อมข้อความแนะนำ OCR/กรอกมือ · `'failed'` (markitdown throw/ไฟล์เสีย) ต้อง**ห้ามเรียก AI**
   เก็บ error ลง `conversion_note` — ทดสอบทั้ง 3 กรณีด้วยไฟล์ทดสอบจริง (PDF ข้อความปกติ, PDF สแกน
   ภาพล้วน, ไฟล์ที่ไม่ใช่ PDF)
3. **spike PRE-F08 (BE-004)** — ทดสอบแปลง PDF จริงของ KMUTT อย่างน้อย 3 ฉบับ รายงาน conversion rate
   ('ok'/'empty'/'failed') กลับมา — นี่คือ test item ที่ `plan.md` เขียนไว้เป็น task ของตัวเองแล้ว
   (ไม่ใช่แค่ QA verification แต่เป็นงาน implement ที่ผลลัพธ์ต้อง evidence กลับมา)
4. sandbox/process แยกไม่มี network ออก, จำกัดขนาดไฟล์ + timeout, ตรวจ MIME/magic bytes ฝั่งเซิร์ฟเวอร์
   — ทดสอบด้วยไฟล์ขนาดใหญ่เกิน limit และไฟล์ที่ตั้งชื่อ `.pdf` แต่เนื้อหาไม่ใช่ PDF จริง (magic bytes
   ไม่ตรง) ต้องถูกปฏิเสธก่อนเข้า pipeline
5. **ไฟล์ซ้ำ (`ux_cpsource_sha`)** — อัปโหลดไฟล์เดิมซ้ำในมหาวิทยาลัยเดียวกัน → ต้องแจ้งว่าไฟล์นี้เคย
   เข้าแล้วเมื่อไหร่โดยใคร ไม่ใช่ error เฉย ๆ และไม่ใช่เงียบ ๆ สร้างซ้ำ
6. จังหวะการอัปเดตไม่ผูกรอบปี — นำเข้า/แก้ไขเมื่อไหร่ก็ได้ (ไม่มี business rule ที่บังคับ schedule —
   ทดสอบว่าไม่มี constraint ที่ปฏิเสธการอัปโหลดนอกช่วงเวลาใด ๆ)

### REQ-002 — AI วิเคราะห์หลักสูตร

**Level**: endpoint เดี่ยว + code reading (ส่วนที่เรียก AI จริงบล็อกที่ PRE-F01 — ดูด้านล่าง)

**Test cases**:

1. **หนึ่งเอกสารหลายสาขา** — แยกเอกสารเป็นส่วนต่อสาขาก่อนเรียก AI (ตัดที่ขอบเขตหัวข้อ markdown
   `#`/`##` เท่านั้น ห้ามตัดกลางตาราง — ถ้าหัวข้อเดียวยังยาวเกิน ตัดที่ขอบเขตย่อหน้า) — ทดสอบด้วย
   เอกสารทดสอบที่มีตารางยาวคร่อมขอบเขตที่ควรตัด ยืนยันว่าไม่ตัดกลางตาราง
2. **กติการวมผลจากหลายชิ้น (deterministic)**: น้ำหนักกลุ่มสาระที่โผล่หลายชิ้น → ใช้ค่ามากสุด · มิติ
   RIASEC ที่โผล่หลายชิ้น → ค่าเฉลี่ยปัดเป็นจำนวนเต็มที่ใกล้ที่สุด (`.5` ปัดขึ้น) · ข้อความบรรยาย →
   ต่อกันตามลำดับ · cluster ที่เสนอ → union ไม่ใช่ intersection — ทดสอบด้วยเอกสารที่ถูกตัดเป็น 2+
   ชิ้นจงใจ (บังคับให้ยาวเกิน) แล้วตรวจผลรวมตามกฎแต่ละข้อ
3. **`analysis_status = 'ai_incomplete'`** ต้องถูกตั้งทุกครั้งที่ต้องตัดชิ้น — ตรวจว่าค่านี้ถูกตั้ง
   แม้ AI จะตอบสำเร็จทุกชิ้น (เพราะการตัดชิ้นเองคือเงื่อนไข ไม่ใช่ผลของ AI)
4. **validate ผล AI แบบ exact-match** — 8 ชื่อกลุ่มสาระ canonical ต้องตรงเป๊ะหลัง trim เท่านั้น (ห้าม
   fuzzy match) · น้ำหนัก ∈ {1,2,3} หรือคำไทย (น้อย/ปานกลาง/มาก) · `dimension_code` ∈ {R,I,A,S,E,C} ·
   `desired_level` ∈ 1-5 จำนวนเต็ม · `cluster_code` ∈ 11 code — ทดสอบด้วย mock AI response ที่มี
   ค่าไม่ตรง exact (เช่น "คณิตศาสตร์ " มีช่องว่างท้าย, "คณิต" แบบย่อ) → ต้องถูกปฏิเสธไม่ใช่เดา
5. แถวที่ validate ไม่ผ่าน → ทิ้งแถวนั้น แต่ `ai_raw_response` ต้องถูกเก็บไว้เสมอ — ตรวจว่าไม่มีการ
   ทิ้งข้อมูลดิบทั้งที่ควรเก็บไว้ให้คนตรวจอ่าน
6. `faculty_group_id` ไม่ผ่าน validate → ปล่อยเป็น `NULL` ให้คนกรอกเอง **ไม่ปฏิเสธทั้งก้อน** (ต่างจาก
   field อื่นที่ปฏิเสธทั้งแถว)
7. **ผลลัพธ์เป็นภาษาไทยเสมอ** แม้เอกสารต้นทางเป็นภาษาอังกฤษ (หลักสูตรนานาชาติ) — ทดสอบด้วยเอกสาร
   ภาษาอังกฤษ 1 ฉบับ
8. **AI ล้มเหลว/ตอบไม่ครบ** — retry ไม่เกิน 2 ครั้ง พร้อม backoff, ครั้งสุดท้ายล้ม → สร้าง intake
   ตามปกติพร้อม `ai_error` และ `analysis_status='ai_incomplete'` ห้ามเดาแทน ห้ามเติมค่า default
   ห้าม error ให้ผู้ใช้ปลายทางเห็น (เด็กไม่มีทางเห็น flow นี้อยู่แล้วเพราะยังไม่ approved)
9. **เรียก AI ครั้งเดียวตอน import แล้ว cache** — เด็กเปิดหน้าจอกี่ครั้งก็ต้องอ่านผลที่เก็บไว้ ห้ามเรียก
   AI ใหม่ทุกครั้ง — ตรวจโดย code review ว่าฝั่งอ่านผล (ทั้ง Program Matching และ RIASEC) ไม่มี
   code path ที่เรียก AI เลย
10. **ห้ามส่งข้อมูลเด็กออกไปหา AI เด็ดขาด** — สิ่งที่ส่งออกได้มีแค่ข้อความจากเอกสารหลักสูตร ตรวจ
    request payload ที่ส่งจริงไปยัง `glm-5.2` ว่าไม่มี field ใดเกี่ยวกับนักเรียน (ชื่อ/คะแนน/ผล
    แบบทดสอบ/ชื่อโรงเรียน)
11. **บล็อกจริง — PRE-F01**: การเรียก `glm-5.2` จริง (BE-008) เขียน+ทดสอบไม่ได้จนกว่าจะมี API key —
    ดู `## Unresolved Open Questions`

### REQ-004 — คนกรอกมือเมื่อ AI อ่านไม่ออก

### Import Rules — dedup/replace/retire (ต่อเนื่องจาก REQ-001/002/003)

**Test cases** (อิง `## Import Rules` ข้อ 8-10):

1. **`dedup_key`** — คำนวณตามลำดับ 4 ขั้นตอนเป๊ะ (trim/ยุบช่องว่าง → ตัดอักขระ `.,()−/ ` → ตัดคำนำหน้า
   เช่น "หลักสูตร"/"สาขาวิชา"/"สาขา"/คำลงท้าย "บัณฑิต"/"วศบ" ฯลฯ ซ้ำจนไม่มีให้ตัด → lowercase ละติน)
   — ทดสอบด้วยชื่อสาขาที่เขียนต่างกันแต่ควรได้ `dedup_key` เดียวกัน เช่น "วิศวกรรมคอมพิวเตอร์" ·
   "วิศวกรรมศาสตรบัณฑิต สาขาวิชาวิศวกรรมคอมพิวเตอร์" · "วศ.บ. วิศวกรรมคอมพิวเตอร์"
2. การชนกันของ `dedup_key` **ไม่ merge อัตโนมัติ** — ระบบตั้ง `matched_program_id` เป็นข้อเสนอเท่านั้น
   ต้องให้คนตัดสินใน `resolution` ('new'/'replace'/'discard')
3. **`'replace'` ต้องไม่ทำให้สาขา approved เดิมหายไปจากผลของเด็กระหว่างรอตรวจ** — เด็กยังเห็นข้อมูล
   ชุดเดิมจนกว่าจะกดอนุมัติชุดใหม่ — ทดสอบด้วยสาขาที่ approved อยู่แล้ว อัปโหลดเอกสารใหม่ทับ (ยังไม่
   กดอนุมัติ) แล้วยิง Program Matching ยืนยันว่ายังได้ชุดเดิม
4. การสลับข้อมูลของ `'replace'` เกิด**ตอนกดอนุมัติเท่านั้น** ในทรานแซกชันเดียว (ลบชุดเก่า → เขียนชุดใหม่
   → อัปเดต metadata) — ห้ามเขียนทับข้อมูล approved ก่อนคนกดอนุมัติ
5. สาขาที่หายไปจากเอกสารฉบับใหม่ → **ห้ามลบอัตโนมัติ** คงสถานะเดิมไว้จนกว่าคนจะสั่ง `retired` เอง

### REQ-003 — ต้องมีคนอนุมัติก่อนเปิดให้เด็กเห็น

**Test cases**:

1. **สถานะ**: `pending_review` → `approved` → `retired` (ย้อนกลับได้เฉพาะกรณีคนสั่งถอนอนุมัติเอง) —
   ยืนยันว่าสาขาที่ไม่ใช่ `approved` **เด็กไม่เห็นเลย** ไม่ใช่เห็นแบบเทา/พร้อมป้ายเตือน
2. **เงื่อนไขก่อนกดอนุมัติได้ — 6 ข้อ ต้อง fail-closed ฝั่งเซิร์ฟเวอร์** (ไม่ใช่แค่ disable ปุ่มหน้าจอ):
   (1) มีแถวน้ำหนักกลุ่มสาระอย่างน้อย 1 แถว (2) ทุก `subject` เป็น 1 ใน 8 canonical เป๊ะ (3) ทุก
   `weight` ∈ {1,2,3} (4) มีแถว cluster อย่างน้อย 1 แถว ทุก `cluster_code` ∈ 11 code (5)
   `behavior_profile` ไม่ว่าง (6) มีแถว RIASEC profile **อย่างน้อย 3 แถว** ทุก `desired_level` ∈ 1-5
   — ทดสอบยิง endpoint อนุมัติตรงโดยข้ามเงื่อนไขแต่ละข้อทีละข้อ (เช่น สาขาที่มีแถวน้ำหนักแต่มีแค่ 2
   มิติ RIASEC) → ต้องถูกปฏิเสธทุกกรณีที่ไม่ครบ
3. **คนตรวจแก้ผลของ AI ได้ทุกอย่าง** (กลุ่มสาระ/น้ำหนัก/cluster/กลุ่มคณะเดิม/ข้อความบรรยาย/ระดับมิติ
   RIASEC) — แถวที่แก้ต้องตั้ง `is_manual = true`
4. **แถว `is_manual = true` ห้ามถูกเขียนทับโดยการ import รอบถัดไป** เว้นแต่คนสั่งเองใน resolution
   `'replace'` — ทดสอบด้วยแถวที่แก้ไว้แล้ว อัปโหลดเอกสารใหม่ทับ (ไม่ใช่ replace) ยืนยันว่าแถว manual
   ยังอยู่ไม่หาย
5. `reviewed_by`/`reviewed_at` ต้องมาจาก SSO subject ห้ามเป็น `NULL` เมื่อ `status = 'approved'`
6. **นำเอกสารฉบับใหม่เข้ามา → ต้องกลับไปสถานะรอตรวจอีกครั้ง** ไม่ใช่เปิดให้เด็กเห็นทันที (สำหรับ
   ข้อมูลชุดใหม่ — ชุดเก่าที่ approved ยังแสดงตามปกติ ดู Phase 2 test 3)

### ตัวตน — SchoolBright Staff Session (ปิด OQ-F08 แล้ว 2026-09-15)

**Test cases**:

1. ทุก action ยึด**ตัวตนจาก session ฝั่งเซิร์ฟเวอร์เท่านั้น** — ห้ามรับ user id/role จาก client — ทดสอบส่ง
   `user_id` ปลอมใน body/header แล้วยืนยันว่า server ใช้ค่าจาก Staff session แทน ไม่ใช่ค่าที่ส่งมา
2. **ทดสอบ Staff Auth Middleware (BE-013, ปลดบล็อก OQ-F08)**:

### REQ-012 — แบบทดสอบ RIASEC แบบผสม (Likert + Ranking)

**Level**: endpoint เดี่ยว + code reading ของสูตร (คำนวณด้วยมือเทียบผลจริง)

**Test cases**:

1. **บังคับตอบครบ 100%** — ทั้ง Likert และบล็อกเรียงลำดับ ก่อนส่งได้เสมอ **ต้องปฏิเสธการส่งที่ไม่ครบ
   เด็ดขาด** (400) — นี่คือกฎเดิมที่ยืนยันซ้ำแล้ว **ไม่ใช่การอนุญาตให้ส่งไม่ครบ** — ดู
   `## Regression-Risk Flag` ด้านล่าง สำหรับเหตุผลที่ข้อนี้สำคัญเป็นพิเศษ
2. block เรียงลำดับ — คำตอบต้องเป็น **permutation ของ 1..k เป๊ะ** (k = จำนวนตัวเลือก active ของ
   block, 5 ≤ k ≤ 7) — ห้ามเสมอ ห้ามข้ามเลขอันดับ ห้ามจัดอันดับแค่บางตัว — block ที่ส่งมาไม่ใช่
   permutation ที่ถูกต้อง → **ปฏิเสธคำขอทั้งคำขอ (400)** ห้ามรับบางส่วน — ทดสอบด้วย payload ที่มี
   อันดับซ้ำ/อันดับขาด/อันดับเกิน k
3. `"Answers"`/`"RankAnswers"` เก็บเป็น `"<id>:<value>"` คั่นด้วย comma — ตรวจ format ที่เขียนจริง
4. **ทุกครั้งที่ส่งคำตอบ = `INSERT` แถวใหม่ ไม่ใช่ `UPDATE`** — ทดสอบส่ง 2 รอบติดกัน ยืนยันว่ามี 2
   แถวในตาราง ไม่ใช่แถวเดียวที่ถูกทับ
5. **สูตร `LikertLevel(r)`** — ค่าเฉลี่ยของคำตอบที่ตอบแล้วของมิติ r โดยข้อ reverse-scored ใช้ `6−answer`
   — ทดสอบด้วยชุดคำตอบที่คำนวณมือได้ล่วงหน้า รวมกรณีมีข้อ reverse-scored ปนอยู่
6. **สูตร `RankLevel(r)`** — `rankScore(o) = 1 + 4×(k−rank_o)/(k−1)` (อันดับ 1 → 5.0, อันดับสุดท้าย →
   1.0) เฉลี่ยของทุกตัวเลือก o ที่ `DimensionCode = r` จากทุก block ที่ตอบครบ — ทดสอบด้วยชุดคำตอบ
   คำนวณมือ ยืนยันว่าอันดับ 1 ได้ 5.0 พอดี อันดับสุดท้ายได้ 1.0 พอดี ระยะห่างเท่ากันทุกช่วง
7. **`studentLevel(r) = (W_LIKERT×LikertLevel + W_RANK×RankLevel)/(W_LIKERT+W_RANK)`**, `W_LIKERT =
   W_RANK = 1` — ตัดพจน์ของรูปแบบที่ไม่มีค่าออกจากทั้งตัวตั้งและตัวหาร (มีเฉพาะ Likert →
   `studentLevel = LikertLevel`) — ทดสอบทั้ง 3 กรณี: มีทั้งสองรูปแบบ, มีเฉพาะ Likert, มีเฉพาะ ranking
8. **`"ReverseScored"` อยู่กับ Likert เท่านั้น** — ตาราง `TCompassRiasecRankOption` ต้อง**ไม่มี**
   คอลัมน์นี้เลย (ตรวจ schema) — ตัวเลือกของ ranking ห้ามมี reverse-scored
9. มิติที่ไม่มีค่าเลยทั้งสองรูปแบบ → **ไม่มีค่า ตัดออกจากการคำนวณ ไม่ใช่ 3**
10. **ไม่ปัดเป็นจำนวนเต็มก่อนนำไปเทียบ** — ตรวจว่าค่าที่เก็บ/ใช้คำนวณต่อยังเป็นทศนิยม (ปัด 1 ตำแหน่ง
    เฉพาะตอนแสดงผล)

เคยมีข้อเสนอ (ที่ผู้ใช้**ปฏิเสธไปแล้ว**) ให้อนุญาตส่งคำตอบไม่ครบได้ เพื่อให้เกณฑ์ Confidence เดิม
("ตอบน้อยกว่า 50%") มีทาง trigger — `plan.md`'s Change Log ระบุตรง ๆ ว่า **"Any assumption in earlier
drafts/discussions that partial submission would be allowed is now known-wrong and must not be
implemented"** ซึ่งหมายความว่า `backend-engineer` ที่เคยเห็น draft เดิม หรือที่เขียนตาม "สามัญสำนึก"
ของฟีเจอร์ Confidence-based-on-completion อาจสร้างการรองรับ partial submission โดยไม่ตั้งใจ —
`qa-engineer` ควรตรวจ **BE-028 โดยเฉพาะ** ด้วยความระมัดระวังเป็นพิเศษว่า:

1. ไม่มี code path ใดที่ยอมรับ `AnsweredCount < ActiveItemCount` แล้วยัง insert แถวผลลัพธ์สำเร็จ
2. ไม่มี field/parameter ใดที่ทำหน้าที่ "ส่งแบบร่าง"/"บันทึกความคืบหน้า" ที่ทำให้ผลไม่ครบถูกบันทึกไว้
   เป็นผลสุดท้าย
3. Confidence mechanic (BE-029b) อ้าง `ConsistencyScore` เท่านั้น ไม่อ้าง completion % เลยแม้แต่จุดเดียว

## Cross-Module Dependencies

**Phase 1 (Module E) ↔ `sb-compass` Phase 1 (Module A)**: ทั้งสองแตะ `CompassScoreService.cs` ไฟล์
เดียวกัน — `sb-compass/plan.md` Phase 1 (BE-001 เพิ่ม `AggregateByCanonicalSubjectWeighted`) ต้อง
เสร็จก่อน (หรือพร้อมกับ) โมดูลนี้ Phase 1 (BE-001 ย้าย `GetSubjectAveragesAsync`) — `plan.md`'s
coordination note ระบุให้ sequence กับ `sb-compass` Phase 1 ไม่ใช่รันขนาน — **ทดสอบ Phase 1 ของ
เอกสารนี้ควรตรวจว่าเมธอดที่ย้ายมาเรียก `AggregateByCanonicalSubjectWeighted` จริง ไม่ใช่เมธอดเดิม
ที่ยังไม่ถ่วงน้ำหนัก** ซึ่งจะทำไม่ได้จนกว่า `sb-compass` Phase 1 เสร็จ

**Phase 8 (Module K) ↔ `sb-compass` Phase 3 (Module C, REQ-017 `"StddevScore"`)**: **นี่คือ cross-
module dependency ที่ใหญ่ที่สุดของทั้งสองโมดูล** — Module K's T-Score formula (test REQ-013 ด้านบน)
**เขียนโค้ดได้แล้วและทดสอบ logic ด้วยข้อมูลจำลอง (mock `"StddevScore"` values) ได้เต็มรูปแบบ** แต่
**ไม่สามารถทดสอบ end-to-end ด้วยข้อมูลจริงได้จนกว่า `sb-compass` Phase 3 จะ deploy และรัน recompute
จริง** — แนะนำแบ่งการทดสอบเป็นสองรอบ:
1. **รอบ unit/mock** (ทำได้ตอนนี้): ทดสอบสูตร T-Score/AcademicFit/InterestFit/CombinedScore ด้วยค่า
   `"StddevScore"` ที่ตั้งขึ้นเอง (NULL/0/ค่าจริง) ตามที่ระบุใน Phase 8 test cases ข้างต้น
2. **รอบ end-to-end** (ทำได้เมื่อทั้งสองโมดูล deploy แล้ว): ยืนยันว่า T-Score ที่คำนวณจริงจากข้อมูล
   นักเรียนจริง + `"StddevScore"` จริงจากตาราง `TCompassLevelSubjectStat` ให้ผลลัพธ์ที่สมเหตุสมผล
   (ไม่ error, gate ของ REQ-017 ทำงานถูกต้องกับผลจริง)

**Phase 5 (Module H) ↔ Phase 8 (Module K)**: BE-022 (ตัวกรองชั้นแรก) ขึ้นกับผลจาก BE-052 (Module K's
read endpoint) — Phase 5 ทดสอบเต็มรูปแบบไม่ได้จนกว่า Phase 8 จะมี endpoint คืนผล cluster จริง — และ
**ยังมีคำถามที่ยังไม่ปิดว่า `CompassPathCatalog.RankPaths` (กลไก 8-path เดิม) จะถูกเลิกใช้ทั้งหมด
หรือเก็บไว้เป็น fallback** (`plan.md` ระบุว่าต้องยืนยันกับ `system-analyst` ก่อน) — ถ้ายังไม่ยืนยัน
`qa-engineer` ไม่ควรสมมติทางใดทางหนึ่งเวลาออกแบบ test case ของ BE-022
