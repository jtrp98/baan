# REQ-008 — 5. Flow ปลายทางตามประเภทเคส

> Budget ≤ 4 KB (`policies\documentation.md` §4) · เขียนโดย `business-analyst` · ไฟล์นี้ = 1 REQ + AC ของมัน · สถานะอยู่ที่ `requirement\index.md` เท่านั้น

- **QA** → ตอบเร็วจากความรู้เดิม ปิดเคสได้ ไม่เข้า Backlog
- **BUG** → เช็คว่าเป็นปัญหาที่รู้ต้นตอแล้วหรือไม่ ถ้าไม่ใช่และเกิดซ้ำ ต้องรวบเป็นเรื่องใหม่ แล้วคำนวณลำดับความสำคัญตาม SLA (**ความรุนแรง × จำนวนโรงเรียนที่แจ้งเรื่องเดียวกัน** — แก้ 2026-08-18 จากเดิม "× ระดับสัญญาลูกค้า" ดู § 2b) + ผลกระทบที่อาจลามไปเมนูอื่น
- **FEATURE** (เดิมเรียก REQUEST ในเอกสารต้นฉบับ) → เช็คว่ามีฟีเจอร์/คำขอเดิมตรงกันหรือไม่ ถ้าไม่มีเก็บเป็นคำขอใหม่ ไม่รีบจัดคิวทำทันที รอการจัดลำดับจาก PM — เคสที่จำแนกเป็น FEATURE เริ่มต้นเป็นสถานะ "ขอเข้ามา" (pending/request) เสมอ PM เป็นคนตัดสินใจว่าจะ **คอนเฟิร์มเป็นงานที่ต้องทำแน่นอน** หรือปฏิเสธพร้อมเหตุผล — REQUEST จึงเป็นสถานะของ FEATURE ไม่ใช่ประเภทเคสแยกที่ AI ต้องจำแนกเอง
- **TASK** (งานจิปาถะ/แก้ระบบเดิม เช่น ลบ/เพิ่ม/ย้ายข้อมูล) → ส่งตรงเข้า Dev ได้เลยเหมือน BUG ทั่วไป **ไม่ต้องผ่าน safety override gate** เพราะความเสี่ยงจริงอยู่ที่การจำแนกว่าเป็น BUG หรือไม่เท่านั้น (ยืนยันกับผู้ใช้แล้ว — ดู § Change Log)

**Acceptance criteria:**
- AC-008.1: เคส QA ถูกตอบเร็วจากความรู้เดิมและปิดได้ โดยไม่เข้า Backlog
- AC-008.2: เคส BUG ที่ไม่ตรงกับปัญหาที่รู้ต้นตอแล้วและเกิดซ้ำ ถูกรวบเป็นเรื่องใหม่ และคำนวณลำดับความสำคัญตามสูตร REQ-003 พร้อมผลกระทบที่อาจลามไปเมนูอื่น
- AC-008.3: เคส FEATURE เริ่มต้นด้วยสถานะ "ขอเข้ามา" (pending/request) เสมอ และ PM เป็นผู้ตัดสินใจคอนเฟิร์มเป็นงานที่ต้องทำแน่นอน หรือปฏิเสธพร้อมเหตุผล
- AC-008.4: เคส TASK ถูกส่งตรงเข้า Dev เหมือน BUG ทั่วไป โดยไม่ต้องผ่าน safety override gate
