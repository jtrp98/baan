## ปัญหาที่ร่างนี้แก้

เมื่อ BE-001/BE-002 เปิดใช้ ทุก call ที่โดน 401/403 ต้องกลายเป็นความล้มเหลวที่ผู้ใช้เห็น (AC-063) — ปัจจุบัน UI ทุกจุดกลืนผลลัพธ์พวกนี้เป็นความเงียบ

## ขอบเขต

- ข้อความและช่องทางแสดงผลของ 401/403 ในทุกหน้าของโมดูล (5 เมนู: `/timetable`, `/timetable/manage-timetable`, `/timetable/settings`, `/timetable/create-class-period`, `/timetable/subject-settings` และ flow ปลายทาง `manage-teaching-schedule` — MenuID 401/402/403/404/422 ตาม §43.2a)
- กติกา mapping message key ฝั่ง frontend

## ไม่อยู่ในขอบเขต

- การแสดงเมนู Sidebar ตามสิทธิ์ (D53 → DES-022 §47, AC-064 — ผู้ใช้ยืนยัน 2026-09-30) — แยกเป็น **UX-006** (ทำไมแยก: คนละพื้นผิว/คนละสถานะ — เมนูปิดเป็น component ของ Sidebar ที่ไม่มีข้อความ 401/403 ให้ผู้ใช้; UX-004 ครอบคลุมข้อความเมื่อ API ตอบ 401/403)
- การส่ง Bearer ครบทุก call + proxy ส่งต่อ 401/403 (งานวิศวกรรมของ FE-001) · ข้อความ error ระดับ backend (`Unauthorized`/`SchoolMismatch`/`Forbidden` — ของ BR-72..74)

## ข้อกำหนด UI

### 401 (VR-18 — ไม่มี/เสีย/หมดอายุ)

- พาผู้ใช้ไป **หน้า SessionExpired เดิม** (`SessionExpiredScreen` §16) — ไม่เพิ่มหน้าจอใหม่
- ข้อความเดิมในหน้าเป็น hardcoded Thai ("ไม่พบข้อมูลการเข้าสู่ระบบ") — เสนอย้ายเข้า `messages/th|en.json` โดยไม่เปลี่ยนความหมาย (งานวิศวกรรมของ task ที่รับ)

### 403 (VR-19 SchoolMismatch / VR-20 Forbidden)

- copy เดียวสำหรับทั้งสองเหตุ (ไม่เปิดเผยเหตุผลภายในแก่ผู้ใช้ปลายทาง):
  - TH: **"ไม่มีสิทธิ์ใช้งานเมนูนี้"**
  - EN: **"You don't have permission for this menu."**
- ช่องทางตามประเภท action (ใช้ของเดิมทั้งหมด):
  | บริบท | ช่องทาง |
  |---|---|
  | ปุ่ม/action (ลบตาราง, toggle สถานะ, ลบกลุ่มครู, set-times) | `toast.error` แบบข้อความข้างบน |
  | บันทึกฟอร์ม (settings, subject-settings, teacher group) | `Alert variant="danger"` เดิมของหน้า |
  | โหลดข้อมูลหน้า/ส่วน | สถานะ error/ว่างของพื้นที่นั้นพร้อมข้อความ — ห้ามหน้าว่างเงียบ |
- ทุกจุดห้ามตีความ 401/403 เป็น `{status}` ธุรกิจปกติ (design §43.2) — engineering: proxy ต้องส่งต่อ HTTP status จริง
- ข้อความ 403 ต้องปรากฏทุกครั้งที่ action โดน — รวม fire-and-forget ที่เคยกลืนผล (`catch(() => {})`) ซึ่งจะแก้คู่กันใน UX-005

## สิ่งที่ต้องการการตัดสินของคน

- ถ้อยคำ TH/EN ข้างบนเป็นข้อเสนอ (placeholder ของ §43.2) — เซ็นหรือแก้ ณ ตอนเซ็น
- copy 403 ยังเป็น draft รอเซ็นของผู้ใช้ตามเดิม (ไม่เปลี่ยนโดยการตัดสิน D53/OQ-35)

## การปรับให้สอดคล้องกับเมนูปิด (UX-006 / DES-022)

D53 ตัดสินแล้ว: ผู้ไม่มีสิทธิ์อ่านเห็นเมนูเป็น disabled จึง **ไม่ควรกดเข้าหน้าแล้วโดน 403 ผ่านการคลิกเมนู** — แต่ 403 ยังเกิดได้ในกรณีต่อไปนี้ ดังนั้นข้อความ 403 ข้างบนยังจำเป็นทุกจุด:

| กรณี | ผลต่อ UX-004 |
|---|---|
| เข้าด้วย URL ตรง / bookmark / ลิงก์ภายใน (การแสดงเมนูไม่ใช่ขอบเขตความปลอดภัย — DES-022 §47.1) | หน้าโหลดแล้ว API ตอบ 403 → ใช้ช่องทาง "โหลดข้อมูลหน้า/ส่วน" ด้านบน (สถานะ error ของพื้นที่ + "ไม่มีสิทธิ์ใช้งานเมนูนี้" + ลิงก์ "กลับหน้าหลัก") |
| ผู้มีเฉพาะสิทธิ์อ่าน (เมนูเปิด แต่ปุ่มเขียนถูก 403 ตาม BR-75) | ใช้ช่องทาง "ปุ่ม/action" และ "บันทึกฟอร์ม" ด้านบนตามเดิม — เมนูเปิดไม่รับประกันสิทธิ์เขียน (การซ่อน/ปิดปุ่มเขียนอยู่นอกสัญญา DES-022) |
| สิทธิ์ถูกถอนขณะใช้งาน (เมนูยังเปิดจากผลที่โหลดตอนโหลดหน้า) | โดน 403 ที่ action/การโหลด → ข้อความเดิม · เมนูอัปเดตเมื่อผู้ใช้ reload หน้า (ผลอยู่ในหน่วยความจำ ไม่ refetch; ห้าม cache ลง localStorage — BR-89 Rev 14) |
| Sidebar ตรวจสิทธิ์ไม่สำเร็จ (`checkFailed`: 401/403/5xx/network/timeout/ผิดรูป/ขาด MenuID → ปิดทั้งหมด) | **ไม่แสดงข้อความ 401/403 จาก Sidebar และไม่เริ่ม flow SessionExpired จาก Sidebar** (DES-022 §47.3 Rev 14) — Sidebar แสดงเพียงไอคอนเตือน + tooltip ให้ reload (UX-006); **ไม่ใช่ "ไม่มีสิทธิ์"** · 401 ให้หน้าที่เปิดอยู่จัดการตามหัวข้อ 401 ข้างบน · "ไม่มีสิทธิ์" ของ Sidebar มาจาก 200 + `isRead:false` เท่านั้น (UX-006 `noPermission`) |

- ข้อความต้องไม่ขัดกัน: หน้าที่เปิดด้วย URL ตรงซึ่งเมนูของมันแสดงปิดอยู่ ต้องแสดง 403 copy เดียวกับข้างบน (ไม่เพิ่ม copy พิเศษว่า "เมนูถูกปิด") + ลิงก์ "กลับหน้าหลัก" (ผู้ใช้ตัดสิน 2026-09-30)
- ยังไม่มีการเปลี่ยนแปลงกติกา "ห้ามหน้าว่างเงียบ" — ผู้ที่ถึงหน้าด้วย URL ตรงต้องเห็นเหตุผล ไม่ใช่กริด/ฟอร์มว่าง

## Decided by user 2026-09-30 (ตอบในแชต — ยังเป็นร่าง ไม่มีผู้เซ็น)

- **403 ระดับหน้า (เข้าด้วย URL ตรงโดยไม่มีสิทธิ์) ต้องมีลิงก์ "กลับหน้าหลัก"** (EN "Back to home") ต่อท้ายข้อความ "ไม่มีสิทธิ์ใช้งานเมนูนี้" ในสถานะ error ของพื้นที่หน้า · ปลายทาง = หน้าหลักเดิมของระบบ (frontend ยืนยันเส้นทางจริง) · ใช้กับ 403 ระดับหน้าเท่านั้น — toast/Alert ของ action และฟอร์มไม่มีลิงก์ · เป็นการเพิ่ม UI จึงมีผลหลังเซ็น (ข้อจำกัดหัวไฟล์ "FE-001 ใช้ทางเดิมจนกว่าจะเซ็น" ยังใช้กับช่วงก่อนเซ็น) · เป็นลิงก์ข้อความตามสไตล์ Clickable ของ design system (สี `Text/Web/Clickable`, ขีดเส้นใต้) โฟกัสด้วยคีย์บอร์ดได้
