1. **โดยโครงสร้าง — การเลือก attempt** `[vitest]` (มีอยู่แล้ว `solver-intensity.test.ts:290` `isAttemptBetter`; เพิ่ม `[vitest-ใหม่]`): ทุกคู่ (shortfall, violations) ที่ shortfall ต่างกัน ตัวที่ shortfall น้อยกว่าชนะเสมอไม่ว่า violations เท่าใดและไม่ว่า L · ลำดับ attempt ใดก็ได้ ตัวที่ถูกเลือกมี shortfall = min · หลัง FE-008 ต้องรันซ้ำ เพราะการนับ violation เปลี่ยนไปใช้ฟังก์ชันใหม่
2. **โดยโครงสร้าง — ไม่มีการปฏิเสธ/backtrack เพราะ intensity** `[อ่านโค้ด]`: penalty ของ intensity ใช้ใน value ordering เท่านั้น ไม่อยู่ในเงื่อนไข domain/ตัดทางเลือก/backtrack · `validateDrop` ไม่อ้าง intensity · `[vitest-ใหม่]`: ช่องที่ penalty > 0 ยังอยู่ใน domain (ถูกเลื่อนลำดับ ไม่ถูกตัด)
3. **เชิงประจักษ์ — L0 vs L1 vs L2** `[vitest-ใหม่]` (integration ของ solver ใน jsdom) — BR-80(4) Rev 15 (TP-Q3 ปิด): solver รับ **RNG ที่ฉีดได้** (ค่าเริ่มต้น `Math.random`) · test ฉีด RNG แบบกำหนดได้ (ลำดับตายตัวหรือ PRNG ที่มี seed ใน test) ตัวเดียวกันให้การรัน L0, L1, L2 ของข้อมูลชุดเดียวกัน (ไม่ต้อง `vi.spyOn(Math, "random")` อีก) · ชุด fixture อย่างน้อย: ข้อมูลที่วางครบได้, ข้อมูลที่รู้ว่าค้าง, ข้อมูลแน่น (ใกล้เต็ม) × seed หลายค่า · บันทึก `nShortfallTotal` ของ L0/L1/L2 ต่อ (ชุด, seed) · log shortfall ทุก attempt → attempt ที่ apply น้อยสุด (AC-017) · **ความสามารถทำซ้ำ:** RNG เดียวกัน + ข้อมูลเดียวกัน + L เดียวกัน → ผลกริดเท่ากันทุกครั้ง · **ค่าเริ่มต้น:** เรียก solver โดยไม่ส่ง RNG → ใช้ `Math.random` (spy ถูกเรียก) — production ไม่เปลี่ยน · `[อ่านโค้ด]`: ไม่ persist seed ไม่แสดงผู้ใช้ · ไม่มี `Math.random` ตรงในเส้นทางสุ่มของ solver อีก

**การตีความผลชั้น 3 (BR-80(4) — R34):** ผลที่ L1 หรือ L2 เหลือคาบค้าง (shortfall) **มากกว่า** L0 บน (ชุด, RNG) เดียวกัน **ไม่ใช่ defect อัตโนมัติ** และไม่ทำให้ test ของ FE-008 fail โดยตัวมันเอง — `qa-engineer` บันทึกเป็น **finding ส่ง `system-analyst`** พร้อมชุดข้อมูล, seed, shortfall ทั้งสามระดับ · ห้าม engineer/QA ปรับ solver, AC หรือใช้ทางแก้ที่ design เตรียมไว้ (attempt แรกใช้ลำดับแบบ L0) จนกว่าจะ amend · สิ่งที่**เป็น** defect: ชั้น 1 หรือชั้น 2 ผิด (ภายในการ Generate ครั้งเดียว attempt ที่ถูกเลือกไม่ใช่ shortfall น้อยสุด หรือ intensity ตัด domain/backtrack/ปฏิเสธ) · ดังนั้น test ชั้น 3 เขียนเป็นการเก็บผล + assert เฉพาะความสามารถทำซ้ำ ไม่ assert `L1 ≤ L0`

ข้อจำกัดที่ต้องรู้: value ordering เปลี่ยนเส้นทางค้นหา จึงไม่รับประกันทางคณิตศาสตร์ว่า shortfall ของ L1 ≤ L0 บนลำดับสุ่มเดียวกัน — สัญญารับประกันเชิงโครงสร้างเท่านั้น (ชั้น 1–2) · หน่วย violation ตอน shortfall เท่ากัน = จำนวนแถว `lstRecommendations` จากกริดของ attempt (TP-Q7 ปิด — S4-A, S4-D) ไม่กระทบ R34 เพราะใช้หลัง shortfall เสมอ

### S12-C ยกเลิก Generate ที่รออยู่ (AC-069 — ข้อ 4 (c)) `[vitest-ใหม่]`

### S12-D ไม่ retry อัตโนมัติ + reload กู้คืน (AC-070 — ข้อ 4 (e)) `[vitest-ใหม่]`

- หลัง F1/F2/F3/F4 ของแต่ละ L ที่ทดสอบ: เดินเวลา (fake timers ≥ 60 วินาที) + dispatch `focus`/`visibilitychange` + re-render จาก state อื่น → จำนวน request ของ load ที่ล้ม = **1** ต่อ page load
- **reload กู้คืน:** unmount แล้ว mount ใหม่ (จำลอง full page load) โดย load ตอบสำเร็จ → ปลดบล็อก และ Generate/Save ทำงาน (request `set-all`/`setting/set` = 1 เมื่อกด)
- `[อ่านโค้ด]` + grep: ไม่มีปุ่ม/control/ถ้อยคำ "ลองใหม่" ที่เพิ่มใหม่ (UX-004 ยังไม่เซ็น) · ไม่มี `setInterval`/retry loop ใน load เหล่านี้

### S12-E ความผูกพันกับบริบท + abort `[vitest-ใหม่]`

- load ของบริบท A (ปี/ตารางที่ restore) ล้ม → เปลี่ยนเป็นบริบท B ที่ load สำเร็จ → B **ไม่ถูกบล็อก** · response ล่าช้าของ A (ล้ม) ที่มาถึงหลัง B สำเร็จ → B ยังไม่ถูกบล็อก · response ล่าช้าของ A (สำเร็จ) ไม่ปลดบล็อกของ B ที่ล้ม
- abort ที่ระบบ/ผู้ใช้ยกเลิกเอง (unmount, เปลี่ยนตาราง) → ไม่ toast และไม่ถือเป็น "ล้ม" ของบริบทใหม่
- load ไม่บังคับ (รายการปี, หลักสูตรใน modal, ชื่อครู, ระดับชั้น) ล้มด้วย F1 → toast เท่านั้น · Generate/Save **ไม่ถูกบล็อก** (control ของขอบเขต)
- *(2026-10-04 — key ตาม §43.2b ข้อ 5.6)* **เปลี่ยนโรงเรียน** ใน page instance เดิม (ปี + `selectedTimetableItem` เดิม): (b) ผลล้มของกริดโรงเรียน A ไม่บล็อกโรงเรียน B · (ก) gate `setting/get` ล้มของ A ไม่บล็อก B ที่สำเร็จ · (ค) `restoreLoadFailed`/`periodLoadFailed` ของ A ไม่บล็อก restore ของ B ที่สำเร็จ · control: B ล้ม → บล็อก · `selectedTimetableItem` = โครงคาบ ไม่ใช่ตารางที่ restore — ตารางที่ restore เปลี่ยนได้ด้วย full page load เท่านั้น (ไม่ทดสอบการเปลี่ยนใน instance เดิม)
