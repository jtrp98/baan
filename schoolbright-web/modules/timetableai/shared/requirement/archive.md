## Overview

Timetable AI คือโมดูลจัดตารางสอน (teaching schedule / class timetable) รายปีการศึกษาของโรงเรียนในระบบ School Bright ผู้ใช้ (ฝ่ายวิชาการ/admin โรงเรียน) กำหนด "กติกา" ของปีให้ครบ — คาบเรียน (bell schedule), เพดานการสอนของครู, กติกาวิชา, กลุ่มครู/ครูที่ปรึกษา — แล้วให้ระบบจัดตารางอัตโนมัติโดยไม่ผิดกติกา จากนั้นปรับมือได้ (ลาก/สลับ/ล็อก) และบันทึกเป็นตารางสอนของปีนั้น เปิด/ปิดใช้งานและลบได้

ข้อเท็จจริงตั้งต้นที่ยืนยันแล้วจาก code (design.md §1, §28.1): ระบบ**มีอยู่และทำงานจริงแล้ว** — เอกสารนี้จึงเป็นการ normalize ของที่มีอยู่เป็นข้อกำหนดอ้างอิง ไม่ใช่ requirement ใหม่ · ตัวจัดตารางอัตโนมัติคือ **constraint solver (Constraint Programming) ที่รันใน browser ของผู้ใช้** — ไม่มี AI/LLM/ML ฝั่ง server คำว่า "AI" เป็น positioning ของผลิตภัณฑ์ · ทุกกติกาถูกบังคับที่ **app layer เท่านั้น** (ฐานข้อมูลฝั่งโมดูลไม่มี FK/unique/check ใด ๆ)

**ขอบเขตทางกายภาพ:** 5 routes หลัก — `/timetable`, `/timetable/create-class-period`, `/timetable/manage-timetable`, `/timetable/subject-settings`, `/timetable/settings` — บวก 2 หน้าปลายทางของ flow จริง `/timetable/[year]` และ `/timetable/manage-teaching-schedule` (design.md §0) · ระบบตารางเก่า `/academic` (TSchedule + Service Academic + AI import) เป็นอีกระบบหนึ่ง (backend คนละตัว) — **ตั้งแต่ 2026-09-23 เป็นปลายทางการส่งตารางของ REQ-019** (ผู้ใช้ยืนยัน, ปิด OQ-11; design.md §41 DES-016) จึงไม่ได้อยู่นอกขอบเขตทั้งหมดอีกต่อไป · ส่วนอื่นของ `/academic` (UI/หน้าจอของระบบนั้นเอง, AI/OCR import) ยังไม่อยู่ในขอบเขตของโมดูลนี้ (design.md §22) · ความสัมพันธ์ระยะยาวของสองระบบยังเปิดอยู่ที่ OQ-7

## Target Users & Roles

- **ผู้ดูแลระบบโรงเรียน / ฝ่ายวิชาการ** — ผู้ใช้กลุ่มเดียวของโมดูล: ตั้งกติกา สร้าง/แก้ไข/จัดการตาราง ผ่านเมนู "Teaching Schedule" (การเห็นเมนูคุมจากเมนูฝั่ง server — inject เมื่อผู้ใช้อยู่กลุ่ม Academic id "22"; ฝั่ง client ไม่มีการเช็ค role — design.md §1, §10) · **target (ผู้ใช้ยืนยัน 2026-09-30 — OQ-35):** เมนูผูกกับสิทธิ์ MenuID 401/402/403/404/422 — ไม่มีสิทธิ์ = เห็นเป็น disabled (AC-064)
- **ไม่มี role แยกระดับภายในโมดูล** — ทุกคนที่เข้าถึงเมนูได้ ทำได้ทุกอย่าง (as-built, design.md §10 — การกำหนดสิทธิ์รายบทบาทเป็นคำถามเปิดของเจ้าของผลิตภัณฑ์)
- **สิทธิ์เรียก API (ตัดสินใจ 2026-09-29 — OQ-1/OQ-29, design.md DES-018)** — ทุก endpoint ของ backend ต้องมี `Authorization: Bearer` token ที่ระบบ SB ออก (verify ด้วย `token_secret` ตัวเดียวกับระบบ SB), โรงเรียนใน request ต้องตรง `NCompany` ของ token และผู้เรียกต้องมี **MenuID เฉพาะของ timetableai** — ไม่มี endpoint ยกเว้น · as-built ยังไม่มี authorization ใด ๆ (D1) จึงเป็น target · **MenuID ที่ทราบ: 401 `/timetable`, 402 `/manage-timetable`, 403 `/settings`, 404 `/create-class-period`, 401 `/timetable/[year]` (ใช้เมนูเดียวกับ `/timetable`), 422 `/subject-settings`** (ผู้ใช้ให้มา 2026-09-29) — API ของแต่ละหน้าต้องมีเมนูที่ตรงกับหน้านั้น · `/timetable/[year]` = 401 (เมนูเดียวกับ `/timetable`), 422 = `/timetable/subject-settings` · สิทธิ์อ่าน/เขียนตาม `TMenuPermission` ของ SB (OQ-29 ปิดแล้ว) · ผลกระทบ: ผู้เรียกที่ไม่มี token (รวม localhost ตอนพัฒนา) จะได้ 401 — **ผู้ใช้อนุมัติ breaking change นี้แล้ว 2026-09-29**

## Core Features

> ที่มาทุกข้อ: `_docs/module/timetableai/design.md` (อ้าง section / BR / D / DES กำกับรายข้อ) — สถานะการตัดสินของทุก REQ เป็น **`as-built (code-confirmed)`** ยังไม่ใช่การยืนยันทางธุรกิจ

### REQ-001 — ปีการศึกษาเป็นศูนย์กลางของโมดูล

โมดูลทำงานรายปีการศึกษา: ทุกหน้าเข้าถึงผ่านการเลือกปี ตารางและกติกาทุกชนิดผูกกับ (โรงเรียน, ปี) การแสดงปีเป็น พ.ศ./ค.ศ. ตาม locale ของ UI (ข้อมูลเก็บ numberYear ค่าเดียว) (design.md §4 F12, BR-1, §19-9)

**Acceptance criteria:**

- AC-001 — หน้า `/timetable` (hub) แสดงรายการปีการศึกษาเรียงใหม่ → เก่า และเข้ารายการตารางของปีใดก็ได้ผ่านปุ่ม Manage
- AC-002 — การตั้งค่า/กติกา/ตารางทุกชนิดอ่านและเขียนภายใต้ (nSchoolID, nYear) ของ route ปัจจุบันเสมอ — *as-built exception ที่ทราบ:* หน้า manage-timetable โหลดรายการ template คาบโดยไม่ส่ง nYear จึงเห็น template ข้ามปีได้ (D8 — บันทึกตามข้อเท็จจริง ปัจจุบันยังไม่มีมติให้แก้)

### REQ-002 — เงื่อนไขระบบรายปี (เพดานครู, ครูที่ปรึกษา, ความหนักตาราง)

ต่อ (โรงเรียน, ปี) ผู้ใช้ตั้งได้: เพดานคาบ/วันต่อครู โดยมีลำดับความสำคัญ **ค่ารายคน > ค่ารวม (หักตัวยกเว้น) > ไม่จำกัด** (BR-8) · จำนวนคาบต่อเนื่องไม่หยุดพัก (มีผลเสมอ เว้นแต่ครูนั้นมีค่ารายคนทับ — BR-9) · กติกาครูที่ปรึกษา (ใช้ทุกคน / ยกเว้นบางคน / เฉพาะประถม / ม.ต้น / ม.ปลาย) ใช้กรอง "ครูคนในมีสิทธิ์สอนห้องใด" (BR-10) · ความหนักตาราง `nCourseIntensity` — **as-built: บันทึกได้แต่ไม่มีส่วนใดอ่านใช้** (D12) · **target (ยืนยัน 2026-09-29 — OQ-2/OQ-30, design.md DES-019):** ต้องบังคับใช้จริงแบบ **soft** เป็นค่า**ต่อตารางเรียน** (ปัจจุบันเก็บต่อ (โรงเรียน, ปี) ใน `Tbl_Setting` — ย้ายที่เก็บต้องผ่านประตู schema confirmation) ระดับ **0 = ไม่กระจาย · 1 = พยายามกระจายวิชาหนัก · 2 = พยายามสลับหนัก-เบา** ต่อห้องเรียนต่อวัน · "วิชาหนัก" = อยู่กลุ่ม (พื้นฐาน, เพิ่มเติม) และหน่วยกิตสูงกว่าค่าเฉลี่ยของวิชากลุ่มนั้นในแผนเดียวกัน (เท่าค่าเฉลี่ย = เบา) ที่เหลือ = เบา · ระบบคำนวณเท่านั้น ไม่มีให้กรอกความหนักต่อวิชาเอง (design.md §5.2, §11, DES-007)

**Acceptance criteria:**

- AC-003 — ลำดับความสำคัญของเพดาน (รายคน > รวม−ยกเว้น > ไม่จำกัด) ถูกบังคับทั้งตอน Generate และตอนวางมือ
- AC-004 — ค่าที่บันทึกโหลดกลับมาครบถ้วน; ปีที่ยังไม่เคยตั้งค่าตอบ default object ทันทีโดยไม่ error (design.md §17-6/8)
- AC-054 *(target — schema ยืนยันแล้ว 2026-09-29: คอลัมน์ `Tbl_Timetable.nCourseIntensity` เดียว · หมวด {พื้นฐาน, เพิ่มเติม} อ่านจาก **`TCourseGroup`** (ผู้ใช้ตอบ 2026-09-29 — บันทึกโดย `system-analyst` ที่ design.md Rev 10 SA-Q16 ปิด, DES-019 BR-77) · กติกาจับคู่ค่า `sCourseGroupDesc` ("ขึ้นต้นด้วย พื้นฐาน/เพิ่มเติม") เป็นข้อเสนอเชิงเทคนิคของ SA บนข้อมูลข้อความอิสระต่อโรงเรียน — ยังไม่ได้ตรวจกับข้อมูลจริง (ส่ง `system-analyst`) · รอ DDL โดย devops)* — เมื่อ `nCourseIntensity` ของตารางเป็น 1 หรือ 2 ตัวจัดตาราง**พยายาม**กระจายวิชาหนักตามระดับต่อห้องเรียนต่อวัน แต่การกระจายไม่ได้**ต้องไม่ทำให้วิชาค้างเพิ่มและไม่ปฏิเสธการวาง/สลับมือ**; เป็น 0 = ไม่มีผลต่อการจัด
  - *เพิ่ม 2026-09-30 (ผู้ใช้ยืนยัน design.md Rev 13 DES-019 BR-80/BR-81a):* หลังการวาง/สลับ/ย้าย/ลบด้วยมือแต่ละครั้งที่สำเร็จ ระบบคำนวณ T_c ใหม่ต่อห้องเรียนจากกริดปัจจุบัน แล้วแสดง**คำเตือนแบบไม่บล็อก**เฉพาะ (ห้องเรียน, วัน) ที่**เพิ่งกลายเป็นละเมิด** (ละเมิดหลังการแก้ แต่ไม่ละเมิดก่อน — **รวมคู่ที่ละเมิดเพราะ T_c ลดลงหลังการแก้** ไม่ใช่เฉพาะคู่ที่เกิดจากคาบที่วาง) · คู่ที่ละเมิดอยู่แล้วก่อนการแก้ไม่เตือนซ้ำ · ระดับ 1 → `HeavyDayOverThreshold` · ระดับ 2 → `HeavyDayOverThreshold` หรือ `ConsecutiveHeavy` · ระดับ 0 → ไม่มีคำเตือน · คำเตือนไม่ปฏิเสธการกระทำและไม่เปลี่ยนกริด · หน้าตา/ถ้อยคำ = `uxui-designer` (UX-003)
- AC-055 *(target)* — หลัง Generate/บันทึก ระบบสรุปค่าความเข้มข้นต่อตาราง: จำนวนวิชาหนัก/เบาต่อวันของทุกห้อง และ**ชี้ห้องและวันที่หนักเกินพร้อมข้อเสนอแนะ** · ตารางที่สร้างก่อนมีฟีเจอร์นี้ไม่มีค่า (ไม่ backfill) · ~~เกณฑ์ "หนักเกิน" ยังไม่กำหนด (ให้ SA/UX เสนอ — ดู OQ-30)~~ · *2026-09-30 — ผู้ใช้ยืนยัน (OQ-34):* (ก) (ห้องเรียน, วัน) **หนักเกิน** ⇔ คาบหนักของวันนั้น > ⌈คาบหนักทั้งสัปดาห์ของห้องนั้น ÷ จำนวนวันที่มีคาบ⌉ (สูตรสัมพัทธ์ของ SA — design.md DES-019 BR-81a) · เพดาน T_c คำนวณ**ต่อห้องเรียน**จากกริดของห้องนั้นเองในตารางนั้น (ผู้ใช้ชี้แจง "ต่อตาราง" = ต่อห้อง, 2026-09-30) (ข) "คาบหนักติดกัน" (`ConsecutiveHeavy`) ชี้**เฉพาะตารางระดับ 2** (ค) ตารางระดับ 0 **ไม่แสดงข้อเสนอแนะ** (ต่างจากข้อเสนอเดิมของ SA ที่ให้แสดง) · จำนวนหนัก/เบาต่อวันของทุกห้องยังแสดงทุกระดับตามเดิม · *เพิ่ม 2026-09-30 (ผู้ใช้ยืนยัน design.md Rev 13 BR-81/BR-81a):* ข้อเสนอแนะ `ConsecutiveHeavy` **ไม่มีค่าเกณฑ์** (`nThreshold = null`) และ UI ไม่แสดงค่าเกณฑ์ (ค่าเกณฑ์ T_c มีเฉพาะ `HeavyDayOverThreshold`) · T_c **ไม่ถูกตรึงจากตอน Generate** — คำนวณใหม่จากกริดปัจจุบันทุกครั้งที่กริดเปลี่ยน · ตัวจัดตาราง, คำเตือนตอนวางมือ (AC-054) และสรุปนี้ใช้เกณฑ์เดียวกันจากฟังก์ชันเดียว (ห้ามมีสูตรซ้ำ — design.md BR-81a)

### REQ-003 — กติกาวิชา (ต่อเนื่อง + ตรึงวิชา)

(a) **Class Continuity** — วิชาต้องสอนต่อเนื่อง N คาบ: as-built **เก็บไว้เท่านั้น ตัวจัดตารางปัจจุบันไม่อ่านใช้** (BR-13, D12) · (b) **Link Subjects** — ตรึงวิชาไว้วัน/ลำดับคาบของกลุ่มห้อง: มี priority สูงสุดในการ Generate วางก่อนเสมอและเขียนทับการวางเดิมได้ ครู 1 คนสอนหลายห้องพร้อมกันได้เฉพาะในกลุ่มเดียวกัน (นับเป็นสล็อตเดียว) วันใดคาบไม่พอตามลำดับที่ตรึง → ข้ามวันนั้น (BR-11, BR-12) (design.md §5.3, §3.1)

**Acceptance criteria:**

- AC-005 — วิชาที่ตรึงไว้ถูกวางตามวัน/คาบที่กำหนดก่อนการวางอื่นเสมอ และเขียนทับช่องเดิมได้
- AC-006 — ครูสอนหลายห้องพร้อมกันได้เฉพาะวิชาตรึง (link subject) ในกลุ่มห้องเดียวกันเท่านั้น
- AC-007 — ค่า continuity บันทึกแล้วแสดงกลับมาถูกต้อง แต่**ไม่มีผลต่อการ Generate** (as-built D12 — การจะให้บังคับจริงเป็นคำถามเปิด OQ-2)

### REQ-004 — โครงคาบเรียน (Class Period Template)

สร้าง/แก้/ลบ template คาบเรียน 2 ชนิด: มาตรฐาน (ทุกวันใช้โครงเดียว) และกำหนดเอง (หลายกลุ่มวัน แต่ละกลุ่มมีโครงตัวเอง ห้ามวันซ้ำข้ามกลุ่ม) แต่ละคาบมีชื่อ/เวลาเริ่ม-จบ และเพิ่มคาบพักได้ · ช่วงเวลาห้ามเริ่ม ≥ จบ และห้ามทับกัน — ตรวจทั้ง UI และ backend (`OverlappedTimeRanges`, VR-1) · ชนิดของ template เปลี่ยนไม่ได้หลังสร้าง · `sWeekdays` เก็บชื่อวันภาษาอังกฤษ, `null` = ใช้ได้ทุกวัน · as-built: **ไม่มีการกันลบ template ที่ตารางกำลังใช้** และไม่มีกันชื่อซ้ำ (BR-5, BR-6, BR-7) (design.md §5.4, DES-002)

**Acceptance criteria:**

- AC-008 — backend ปฏิเสธ template ที่มีช่วงเวลาย้อน/ทับกันด้วย `status 0 OverlappedTimeRanges`
- AC-009 — ทุกหน้าที่อ้าง template ใช้โครงคาบชุดเดียวกันตาม `jPeriodConfig`; ชื่อวันเป็นภาษาอังกฤษเสมอ (เป็นคีย์ match ข้ามหน้า)

### REQ-005 — กลุ่มครู + เวลาไม่ว่าง

สร้างกลุ่มครูผูกกับ template คาบเรียน เพิ่ม/ถอดครูในกลุ่ม (บันทึก = แทนที่รายชื่อทั้งชุด — BR-14) และปิด/เปิดสล็อตเวลารายวันรายคาบ (`isOn=false` = ครูไม่รับงาน — กลไกหลัก "ครูลา/ติดธุระ" ที่ generator ใช้จริง) · เปลี่ยน template ของกลุ่ม = backend ล้างตารางเวลาทั้ง 7 วันทิ้ง (BR-15) (design.md §5.5, DES-007)

**Acceptance criteria:**

- AC-010 — สล็อตที่ปิด (`isOn=false`) ถูกถือเป็นครูไม่ว่าง ทั้งตอน Generate และตอนวางมือ — ไม่มีทางวางครูในสล็อตนั้นได้
- AC-011 — การบันทึกสมาชิกกลุ่มแทนที่รายชื่อทั้งชุดเสมอ และการเปลี่ยน template ของกลุ่มล้างเวลาไม่ว่างครบ 7 วัน

### REQ-006 — ครูที่ปรึกษาประจำระดับ/ห้อง

Wizard 3 ขั้น (ระดับ → ห้อง → ครูที่ปรึกษา) สร้าง assignment ที่เป็น**แหล่ง "คุณสมบัติครู"** (ครูคนใดมีสิทธิ์สอนห้องใด/รับผิดชอบวิชาใด) ให้ทั้ง Generate และการวางมือ · as-built: ยังไม่มีการกันสร้าง assignment ระดับซ้ำ (D7) (BR-16) (design.md §5.5 แท็บ 2)

**Acceptance criteria:**

- AC-012 — ครูที่ไม่อยู่ในรายชื่อผู้มีคุณสมบัติของห้องนั้น วางวิชาในห้องนั้นไม่ได้ (ทั้ง Generate และวางมือ)

### REQ-007 — รายการตารางของปี + สถานะการใช้งาน + การลบ

หน้า `/timetable/[year]` รวมตารางทุกชุดของปี แท็บ ทั้งหมด/ใช้งาน/ไม่ใช้งาน — "draft" ใน UI หมายถึง `isActive=false` เท่านั้น (ไม่มีสถานะ draft แยกในข้อมูล) · สร้างใหม่ `isActive=true` เสมอ (BR-19) · toggle เปิด/ปิดใช้งานได้ · ลบ = soft delete ทั้งพ่อ+ลูก กู้คืนไม่ได้ผ่าน API (BR-3) · การสร้าง/แก้ไขเข้าถึงได้ทางเดียวจากหน้านี้ (design.md §5.6, §9, DES-003)

**Acceptance criteria:**

- AC-013 — toggle สถานะแล้วตารางย้ายแท็บ (ใช้งาน ↔ ไม่ใช้งาน) ถูกต้องทันที
- AC-014 — ตารางที่ลบแล้วหายจากทุกมุมมองและกู้คืนไม่ได้ผ่านระบบ (UI ต้อง confirm ก่อนลบ)

### REQ-008 — การจัดตารางอัตโนมัติ (CP Solver ใน browser)

ปุ่ม "AI Generate" ใช้ constraint programming solver รันใน browser (MRV + forward checking + backtracking) บังคับ hard constraints: ครูไม่เกินเพดานคาบ/วัน (REQ-002), ไม่เกินคาบต่อเนื่อง, ไม่ชนตารางอื่นที่บันทึกแล้วของปีเดียวกัน (เทียบด้วยเวลาจริง start/end ข้าม template — BR-17; **ตัดสินใจ 2026-09-29 OQ-8: เมื่อ REQ-012 ใช้งาน เช็คเฉพาะตารางของ "เทอมเดียวกัน" — ตารางคนละเทอมไม่นับชน** design.md §34.3 BR-17a), ไม่สอนในสล็อตปิด (REQ-005), ไม่สอน 2 ห้องพร้อมกันยกเว้น link subject (REQ-003), วิชาไม่เกินโควตา periods/week · งบ 3,000 step ต่อ attempt × 5 attempts เลือกผลที่วิชาค้างน้อยสุด — **ไม่รับประกันวางครบ** ช่องว่างให้จัดมือ · วิชาที่ไม่มีครูผู้มีคุณสมบัติหรือโควตา 0 ถูกตัดจากการจัดอัตโนมัติ · ต้องรอ conflict data (ตารางอื่น + เวลาไม่ว่าง) โหลดเสร็จจึงกดได้ · as-built: ยังไม่มี UI แจ้งจำนวนวิชาค้าง · **target (ยืนยัน 2026-09-29 — OQ-6, design.md DES-020):** หลัง Generate ทุกครั้งต้องแจ้งรายการวิชา (ห้อง, วิชา) ที่วางไม่ได้และจำนวนรวม หรือแจ้งว่าวางครบ (ไม่ซ้อนกับการบล็อกก่อน Generate ของ REQ-014 — ครอบคลุมเฉพาะวิชาที่มีสิทธิ์จัดแต่ solver วางไม่ลง) (design.md §3.1, §28, DES-006)

**Acceptance criteria:**

- AC-015 — ผลลัพธ์การ Generate ไม่ละเมิด hard constraint ใดข้างต้น (ตรวจซ้ำได้จากกริดโดยไม่ต้องอ่าน code)
- AC-016 — วิชาที่ไม่มีครูผู้มีคุณสมบัติหรือโควตา 0 ไม่ถูกวางโดยอัตโนมัติ (วางมือเท่านั้น)
- AC-017 — เมื่อหมดงบ backtrack วิชาที่วางไม่ได้ถูกปล่อยว่าง และระบบใช้ผล attempt ที่วิชาค้างน้อยที่สุด
- AC-018 — การ Generate ต้องรอ conflict data โหลดเสร็จเสมอ (ห้ามจัดด้วยข้อมูลว่าง)
- AC-056 *(target — OQ-6)* — หลัง Generate เสร็จ ผู้ใช้เห็นรายการวิชาที่วางไม่ได้ (ห้อง, วิชา) พร้อมจำนวนรวม หรือข้อความว่าวางครบ ทุกครั้ง · รูปแบบ UI ให้ `uxui-designer`
- *หมายเหตุ AC-015 (target — OQ-8):* "ไม่ชนตารางอื่นของปีเดียวกัน" อ่านเป็น "ของเทอมเดียวกัน" เมื่อ REQ-012 ใช้งาน (ตารางเก่าที่ไม่มีเทอมใช้กติกาเดิมของปี — design.md BR-17a); AC-015 ฉบับ as-built คงไว้เป็นประวัติ

### REQ-009 — การปรับตารางด้วยมือ (ทุกการกระทำผ่านกติกา)

ลากวาง / กดค้าง 500 ms เพื่อสลับ / เพิ่มวิชาในช่องว่าง / ล็อกช่อง / ล้างทั้งหมด — ทุก move ผ่านการตรวจกติกาชุดเดียวกับ generator (ตรวจซ้ำ 2 ชั้น: ในกริด + ระดับหน้า) การเทียบเวลาใช้เวลาจริงของสล็อตรายห้องเสมอ (ห้ามเทียบ index — BR-17) · Regenerate สร้างกริดใหม่**คงช่องล็อกไว้** · as-built: สถานะล็อกไม่ถูก persist หายเมื่อปิดหน้า (D16) และ "ล้างทั้งหมด" ลบช่องล็อกด้วย (D34) (design.md §3.2, §28.4)

**Acceptance criteria:**

- AC-019 — การวาง/สลับที่ละเมิดกติกาถูกปฏิเสธพร้อมข้อความอธิบายเหตุผล (ทับซ้อนครู/เกินเพดาน/เกินต่อเนื่อง ฯลฯ)
- AC-020 — การสลับสองช่องสำเร็จได้เมื่อทั้งสองทิศผ่านกติกาเท่านั้น
- AC-021 — Regenerate คงช่องล็อกไว้ (as-built: ล็อกไม่ persist ข้าม session และ Clear All ลบล็อก — บันทึกตามข้อเท็จจริง D16/D34)
- AC-057 *(target — OQ-8)* — การวาง/สลับมือใช้กติกาชนของครูชุดเดียวกับ Generate: เช็คเฉพาะตารางของเทอมเดียวกัน (BR-17a)

### REQ-010 — การบันทึกและ restore ตาราง (snapshot)

บันทึกเป็น snapshot jsonb รายห้อง — เก็บทั้งโครงเวลาและข้อมูลวิชา/ครู/ห้อง/เครดิต ณ วินาทีบันทึก (BR-20) ตารางที่บันทึกแล้วจึง**ไม่ผูกกับข้อมูลหลักด้วย key** การแก้ชื่อวิชา/ย้ายครูทีหลังไม่กระทบตารางเก่า · บันทึกแบบ upsert ต่อห้อง ห้องที่หายจาก payload ถูก soft delete (BR-21) · การแก้ไขครั้งถัดไป restore จาก snapshot โดยจับคู่เซลล์ด้วยเวลาเริ่ม (sStartTime) รายวัน และเก็บฟิลด์ดิบครบเพื่อ round-trip · as-built: บันทึกไม่ตรวจความครบโควตา และ success modal แสดงเสมอโดยไม่อ่านผลจริง (D26 — จัด priority เป็น bug list แล้วตาม design.md §23) (design.md §3 Flow B/D, §27.3)

**Acceptance criteria:**

- AC-022 — ตารางที่บันทึกแล้วเปิดแก้ใหม่ได้ครบทุกเซลล์ (round-trip ตรงเดิม รวมรหัสวิชา/ห้อง/เครดิต)
- AC-023 — การแก้ข้อมูลหลัก (ย้ายครู/เปลี่ยนชื่อวิชา) หลังบันทึก ไม่เปลี่ยนตารางที่บันทึกไว้แล้ว
- AC-024 — ห้องที่ถูกถอดออกจาก payload ตอนบันทึก ถูก soft delete รายแถวของห้องนั้น

### REQ-011 — มุมมอง การกรอง และการส่งออก

กรองมุมมองตามห้อง/ระดับ/วิชา/ครู สลับมุมมองรายห้อง ↔ รายครู และส่งออก Excel/PDF — as-built ทำใน browser ทั้งหมด ไม่มี export API (design.md §5.7, §19-8)

### REQ-012 — รองรับภาคเรียน (Term) ทั้งโมดูล — **New requirement (ยืนยันธุรกิจแล้ว 2026-09-21 — ยังไม่ผ่านการออกแบบ schema)**

โมดูลเปลี่ยนหน่วยการทำงานจาก (โรงเรียน, ปี) เป็น **(โรงเรียน, ปี, เทอม) ทั้งโมดูล** — ไม่ใช่แค่หน้า `/timetable` (hub) — ทุกกติกาและตารางที่ปัจจุบันผูกกับ (nSchoolID, nYear) เพียงอย่างเดียวต้องผูกกับเทอมด้วย: เงื่อนไขระบบ (REQ-002), กติกาวิชา (REQ-003), โครงคาบเรียน (REQ-004), กลุ่มครู (REQ-005), ครูที่ปรึกษา (REQ-006), รายการตาราง (REQ-007), ตัวจัดอัตโนมัติ/วางมือ (REQ-008, REQ-009) และตารางที่บันทึกแล้ว (REQ-010) — คำขอนี้กลับสมมติฐาน as-built เดิมที่ว่าโมดูล "ไม่รองรับภาคเรียน" (ดู `## Constraints & Assumptions`)

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว (ผู้ใช้ — session 2026-09-21):**

- ขอบเขต: **ทั้งโมดูล** ไม่ใช่แค่หน้ารายการ
- จำนวนเทอมต่อปี: **ไม่กำหนดตายตัวในโมดูลนี้** — อ้างอิง master data `TTerm` ของ school DB ที่มีอยู่แล้ว (อ่านอย่างเดียว เช่นเดียวกับที่โมดูลอ่าน `TYear` ในปัจจุบัน — design.md §26, §27.4) โรงเรียนมีกี่เทอมก็ได้ตามที่ตั้งไว้ใน school DB
- Migration ข้อมูลเดิม: การตั้งค่าระดับปีและตารางที่สร้างไว้ก่อนมี term dimension ทั้งหมด **default เป็นเทอม 1 ของปีนั้นโดยอัตโนมัติ** — ผู้ใช้ไม่ต้องเลือก/ย้ายข้อมูลเอง · *2026-09-30:* ยกเว้นปีที่ไม่มีแถว `TTerm` — ไม่ต้องจัดการ (OQ-36/OQ-37) · cutover = ตั้งแต่ release ไม่มีช่วงผ่อนผัน, ไม่มีวันที่ตามปฏิทิน (SA-Q3 — AC-065)

**Acceptance criteria (ระดับ requirement — schema/implementation ให้ system-analyst ออกแบบต่อ):**

- AC-026 — ทุกหน้า/กติกา/ตารางที่ปัจจุบันอ่าน-เขียนภายใต้ (nSchoolID, nYear) ต้องอ่าน-เขียนภายใต้ (nSchoolID, nYear, nTermID) หลังการเปลี่ยนแปลง ไม่มีจุดใดตกหล่นยังทำงานข้ามเทอมโดยไม่ตั้งใจ
- AC-027 — รายชื่อ/ตัวเลือกเทอมที่แสดงในทุกหน้าต้องอ้างอิง `TTerm` ของปีนั้นจาก school DB เสมอ ห้าม hardcode จำนวน/รายชื่อเทอมในโมดูลนี้
- AC-028 — ข้อมูลที่มีอยู่ก่อนการเปลี่ยนแปลง (การตั้งค่า, กลุ่มครู, template, ตารางที่บันทึกแล้ว) ต้องเข้าถึงได้ปกติหลัง migrate โดยถูกจัดเป็นเทอม 1 ของปีเดิมโดยอัตโนมัติ ไม่มีข้อมูลสูญหายหรือกำพร้า (orphan) — **ยกเว้น** ข้อมูลของ (โรงเรียน, ปี) ที่ไม่มีแถว `TTerm` เลย: ไม่ต้องจัดการ (ผู้ใช้ยืนยัน 2026-09-30 — OQ-36/OQ-37)
  - *หมายเหตุ 2026-09-30 (OQ-36, OQ-37 / design.md SA-Q2):* ผู้ใช้ตอบ "ไม่ต้องสนใจข้อมูลเก่า เพราะอยู่ในขั้นตอน test อยู่" แล้วระบุต่อว่าหมายถึง**เฉพาะกรณีปีที่ไม่มีแถว `TTerm`** — migration ข้อมูลเดิมเข้าเทอม 1 ของ AC-028 **ยังคงอยู่** · ผู้ใช้ยืนยันด้วยว่า DB ที่โมดูลใช้อยู่ตอนนี้ (production frontend → backend dev, R32) **ไม่มีข้อมูลโรงเรียนจริง มีแต่ข้อมูลทดสอบ** · **ต้องยืนยันซ้ำก่อนมีข้อมูล production** (ยังไม่มีวันที่)
- AC-065 *(target — ผู้ใช้ตอบ 2026-09-30, design.md SA-Q3)* — การบังคับคีย์เทอมมีผล**ตั้งแต่ release ที่ออก REQ-012 (DES-009) ทันที ไม่มีช่วงผ่อนผัน**ให้ frontend เดิมที่ยังไม่ส่งคีย์เทอม (ผู้ใช้ตอบ "เริ่มเลย") · **ผู้ใช้ไม่ได้ให้วันที่ตามปฏิทิน** — ถ้าต้องการ cutover แบบกำหนดวัน ต้องให้คนระบุวันที่ ห้ามเดา

**หมายเหตุสำคัญ — ต้องส่งต่อ system-analyst ก่อน implement ใด ๆ:** REQ นี้กลับสมมติฐานสถาปัตยกรรมหลักของโมดูล (design.md DES-001 Fallback, §18.3) และกระทบ schema ของแทบทุกตารางฝั่งโมดูล (`Tbl_Setting`, `Tbl_ClassPeriod`, `Tbl_TeacherGroup`, `Tbl_TeacherClassAssignment`, `Tbl_Timetable`, `Tbl_TimetableClass`) — เข้าเงื่อนไข "Adds or alters a field/table/relation" ของ pipeline routing (ต้องผ่าน `system-analyst` amend → `test-planner` → engineer → `qa-engineer` +`security`) กฎการกันชนตาราง/conflict checking ข้ามเทอม (REQ-008 BR-17, REQ-009) ยังไม่มีนิยามธุรกิจ — ดู OQ-8

### REQ-013 — คัดลอกกติกา/ตารางไปยังเทอม-ปีที่ต้องการ — **New requirement (ยืนยันธุรกิจแล้ว 2026-09-21 — ยังไม่ผ่านการออกแบบ schema, ขึ้นกับ REQ-012)**

ปุ่มคัดลอกจากเทอม-ปีต้นทาง ไปยัง**เทอม-ปีปลายทางใดก็ได้ที่ผู้ใช้เลือกเอง** ไม่จำกัดว่าต้องเป็นปี/เทอมถัดไป — คำขอนี้กลับสมมติฐาน as-built เดิมที่ระบุว่าระบบยังไม่มี "copy ตารางจากปีก่อน" (ดู `## Declined / Not Pursuing`)

**กลไกการเข้าถึง — 5 จุดเข้า แยกตามหน้า (ยืนยันธุรกิจ 2026-09-23, แก้ไขจากฉบับ 2026-09-21 ที่เคยระบุเป็น "เลือกได้จากรายการเดียว"):** ปุ่ม Copy ปรากฏบน 5 หน้า list-page ของโมดูล (หน้าเดียวกับที่ใช้เลือกปีการศึกษา) แต่ละจุดคัดลอกขอบเขตต่างกันตามหน้าที่กด **ไม่ใช่ modal เดียวที่มี checkbox เลือก 4 เมนู**:

| หน้าที่กด Copy | ขอบเขตที่คัดลอก |
|---|---|
| `/timetable` (hub เลือกปี) | **ทั้งหมด** — เงื่อนไขระบบ + กติกาวิชา + โครงคาบเรียน + เงื่อนไขครู + ตารางสอนที่สร้างเสร็จแล้ว รวมเป็นชุดเดียวเสมอ (เลือกแยกเมนูจากจุดนี้ไม่ได้) |
| `/timetable/settings` | เฉพาะเงื่อนไขระบบ (System Conditions, REQ-002) |
| `/timetable/subject-settings` | เฉพาะกติกาวิชา (Subject Conditions, REQ-003) |
| `/timetable/create-class-period` | เฉพาะโครงคาบเรียน (Class Period templates, REQ-004) |
| `/timetable/manage-timetable` | เฉพาะเงื่อนไขครู (Teacher Conditions — กลุ่มครู+เวลาไม่ว่าง REQ-005) · *แก้ 2026-09-28:* ฉบับก่อนหน้ารวมครูที่ปรึกษาประจำระดับ/ห้อง (REQ-006) ไว้ในเมนูนี้ด้วย แต่ REQ-018 ยกเลิก REQ-006 แล้ว (ไม่มี UI และข้อมูล `Tbl_TeacherClassAssignment` ไม่ถูกอ่านใช้ต่อ — AC-046a) จึงไม่อยู่ในขอบเขตคัดลอกนี้อีก |

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว:**

- เป้าหมายคัดลอก: เทอม/ปีใดก็ได้ที่ผู้ใช้เลือกเอง ไม่จำกัดเงื่อนไข (ทุกจุดเข้า)
- **"เลือกคัดลอกเป็นรายเมนู" ทำโดยเลือกว่าจะกดปุ่ม Copy จากหน้าไหน** ไม่ใช่ติ๊กเลือกในฟอร์มเดียว — ต้องการคัดลอกเฉพาะโครงคาบเรียน ให้ไปกด Copy ที่ `/timetable/create-class-period`; ต้องการคัดลอกทุกอย่างพร้อมตารางสอน ให้กด Copy ที่ `/timetable`
- **การตั้งค่า "ครูสอนเฉพาะห้องที่รับผิดชอบ" ของ REQ-018 คัดลอกไปกับเมนู "เงื่อนไขระบบ" (`/timetable/settings`)** (ยืนยันธุรกิจ 2026-09-28, ปิด OQ-20 (ข)) — ไม่ใช่เมนูเงื่อนไขครู
- Conflict handling: หากเทอม-ปีปลายทางมีข้อมูลในขอบเขตที่กำลังคัดลอกอยู่แล้ว **ต้องเตือนและให้ผู้ใช้ยืนยันก่อนเขียนทับ แล้วแทนที่ทั้งหมด (ไม่ใช่เพิ่มซ้อน)** (ยืนยันธุรกิจ 2026-09-28, ปิด OQ-22) — ที่ `/timetable` ตรวจครอบคลุมทุกเมนู+ตาราง, ที่อีก 4 หน้าตรวจเฉพาะเมนูของหน้านั้น
- **ปลายทางไม่มี template คาบที่ link subject/กลุ่มครูอ้างอิง → บล็อกการคัดลอกทั้งหมด** (ยืนยันธุรกิจ 2026-09-28, ปิด OQ-20 (ก)) ไม่ใช่ข้ามพร้อมรายงานหรือนำ template มาด้วย
- **ห้อง/หลักสูตร/แผนที่ปลายทางจับคู่ไม่ได้ (เช่น ไม่มีชื่อห้องเดิม) → เตือนผู้ใช้ก่อน ถ้าผู้ใช้ยืนยันให้คัดลอกต่อตามที่จับคู่ได้** (ยืนยันธุรกิจ 2026-09-28, ปิด OQ-23) — ไม่บล็อกทั้งหมดเหมือน OQ-20(ก) เพราะเป็นคนละสถานการณ์ (นี่คือ "ข้อมูลบางส่วนจับคู่ไม่ได้" ไม่ใช่ "template หลักหายไปทั้งอัน")

**Acceptance criteria (ระดับ requirement — schema/implementation ให้ system-analyst ออกแบบต่อ):**

- AC-029 — ผู้ใช้เลือกเทอม-ปีต้นทางและปลายทางได้อิสระ (รวมข้ามปี) ก่อนคัดลอก ที่ทุกจุดเข้าทั้ง 5 จุด
- AC-030 — ปุ่ม Copy บน `/timetable` คัดลอกทั้ง 4 เมนู + ตารางสอนเป็นชุดเดียวเสมอ **แต่เลือกได้ว่าจะคัดลอกตารางสอนชุดใดบ้าง** (ไม่บังคับคัดลอกทุกชุดที่ `isActive` — ยืนยันธุรกิจ 2026-09-28, ปิด OQ-20 (ค)); ปุ่ม Copy บนอีก 4 หน้าคัดลอกเฉพาะเมนูของหน้านั้นหน้าเดียว — ไม่มี UI ให้เลือกเมนูแบบผสมเอง · flag ของ REQ-018 อยู่ในเมนู "เงื่อนไขระบบ"
- AC-031 — หากปลายทางมีข้อมูลอยู่แล้วในขอบเขตที่กำลังคัดลอก (ตามจุดเข้าที่กด) ระบบต้องแสดงคำเตือนและรอการยืนยันจากผู้ใช้ก่อนเขียนทับเสมอ แล้ว**แทนที่ทั้งหมด** — ห้ามคัดลอกทับโดยไม่แจ้ง ห้ามเพิ่มซ้อน
- AC-032 — ข้อมูลที่คัดลอกแล้วเป็นอิสระจากต้นทาง (แก้ปลายทางไม่กระทบต้นทาง) สอดคล้องกับหลัก snapshot ของ REQ-010
- **AC-050 (ใหม่, 2026-09-28)** — ปลายทางไม่มี template คาบที่กติกาที่จะคัดลอกอ้างอิง → บล็อกการคัดลอกทั้งหมด พร้อมข้อความอธิบายว่าเป็น template ใดที่ขาด · *หมายเหตุ 2026-09-29:* กติกาจับคู่ template และกรณีคัดลอกโครงคาบเรียนทับขณะที่ข้อมูลปลายทางอื่นยังอ้าง template เดิม **ยังเปิดอยู่ที่ OQ-28** (design.md Rev 6 §35.8)
- **AC-051 (ใหม่, 2026-09-28)** — ห้อง/หลักสูตร/แผนบางรายการที่ปลายทางจับคู่ไม่ได้ (ไม่ใช่ template หลักที่ขาดทั้งหมด) → แสดงคำเตือนรายการที่จับคู่ไม่ได้ รอผู้ใช้ยืนยัน แล้วคัดลอกส่วนที่จับคู่ได้ตามที่ยืนยัน

**หมายเหตุสำคัญ — ต้องส่งต่อ system-analyst ก่อน implement ใด ๆ:** REQ-013 ขึ้นกับ REQ-012 (ต้องมี term dimension ก่อนจึงจะมี "เทอม-ปีปลายทาง" ให้เลือก) และเพิ่ม endpoint/flow ใหม่ (copy) ที่ไม่มีอยู่ใน as-built ปัจจุบัน — เข้าเงื่อนไข schema/feature-change routing เดียวกับ REQ-012 (system-analyst amend → test-planner → engineer → qa-engineer +security)

### REQ-014 — บล็อกการ Generate เมื่อพบวิชาไม่มีครู/โควตา 0 (แก้ REQ-008)

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว:** เปลี่ยนจาก as-built เดิม (AC-016 — ตัดวิชาที่ไม่มีครูผู้มีคุณสมบัติหรือโควตา 0 ทิ้งเงียบ ๆ ก่อน Generate) เป็น **บล็อกไม่ให้กด Generate จนกว่าผู้ใช้จะแก้ไขให้ครบ** — ระบบต้องแสดงรายการวิชาที่มีปัญหา (ไม่มีครูประจำวิชา / โควตาคาบ-สัปดาห์ = 0) พร้อมทางลัดไปหน้าจัดการรายวิชา/หลักสูตรที่เกี่ยวข้อง ก่อนอนุญาตให้กดปุ่ม "จัดตารางสอนด้วย AI"

**Acceptance criteria:**

- AC-033 — ระบบตรวจพบวิชาที่ไม่มีครูผู้มีคุณสมบัติหรือโควตาคาบ/สัปดาห์ = 0 **ก่อน**เรียก Generate เสมอ (ไม่ใช่หลัง Generate เสร็จ) · **แก้ 2026-09-28 (ปิด OQ-19):** ตรวจ**ทุกวิชาของแผนที่เลือก** ไม่ใช่แค่วิชาที่ผู้ใช้ติ๊กเลือกใน Schedule Summary · ทางลัดพาไปหน้า**จัดการหลักสูตร/แผน (นอกโมดูลนี้)** ซึ่งเป็นจุดเดียวที่แก้ `TPlanCourseTeacher`/โควตาคาบต่อสัปดาห์ได้
- AC-034 — พบปัญหาแม้แต่ 1 รายการ → บล็อกปุ่ม Generate และแสดงรายการปัญหาทั้งหมด (ไม่ใช่แค่รายการแรก) พร้อมทางลัดไปแก้
- AC-035 — แก้ปัญหาครบทุกรายการแล้ว ปุ่ม Generate กลับมากดได้โดยไม่ต้องปิด-เปิดหน้าใหม่
- **ยกเลิก AC-016 เดิม** (ตัดวิชาทิ้งเงียบ ๆ) — พฤติกรรมใหม่คือบล็อกแทนการตัด

**ข้อผูกพันกับ REQ-018 — ปิดแล้ว 2026-09-28 (เดิมเป็น blocker, ยืนยันธุรกิจแล้วที่ OQ-17 (ง)):** "ครูผู้มีคุณสมบัติสอนห้องนั้น" ใน as-built มาจาก `Tbl_TeacherClassAssignment` แหล่งเดียว ซึ่ง REQ-018/AC-046a เลิกอ่าน — ผู้ใช้ยืนยันกติกาทดแทนแล้ว: **ครูที่มีชื่อใน `TPlanCourseTeacher` ของวิชานั้นสอนได้ทุกห้องของแผน (Plan) นั้น** (ดู REQ-018 AC-045 แก้ใหม่, BR-41) — REQ-014 จึงตรวจ "ไม่มีครูผู้มีคุณสมบัติ" จากแหล่งใหม่นี้แทน ไม่ใช่ `Tbl_TeacherClassAssignment` อีกต่อไป · *แก้ 2026-09-29:* ขอบเขตวิชาที่ตรวจและปลายทางทางลัด **ปิดแล้ว 2026-09-28 (OQ-19)** — ตรวจทุกวิชาของแผนที่เลือก, ทางลัดไปหน้าจัดการหลักสูตร/แผน (นอกโมดูล) ดู AC-033 (ฉบับก่อนหน้าเขียนว่ายังเปิดอยู่ที่ OQ-19)

### REQ-015 — วิชาคาบต่อเนื่อง (Class Continuity) เป็น hard constraint บังคับจริง (แก้ REQ-003(a), ปิด OQ-2 **บางส่วน — เฉพาะ Class Continuity**; ส่วน `nCourseIntensity` ของ OQ-2 ยังเปิด)

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว:** ค่า "คาบต่อเนื่อง N คาบ" ของวิชา (REQ-003(a)) เปลี่ยนจาก as-built เดิมที่ **เก็บไว้เฉยๆ ไม่มีผลต่อการจัด** (D12, AC-007) เป็น **hard constraint ที่ตัวจัดตารางต้องบังคับจริง** — วางวิชานั้นต้องต่อเนื่องกัน N คาบเสมอทั้งตอน Generate อัตโนมัติและตอนวางมือ/สลับมือ ถ้าวางแล้วทำให้ไม่ต่อเนื่องครบ N คาบต้องถูกปฏิเสธเหมือนกติกาอื่น (เทียบ AC-019)

**Acceptance criteria:**

- AC-036 — วิชาที่ตั้งค่าคาบต่อเนื่อง N คาบ ถูกวางติดกัน N คาบเสมอ ทั้งจาก Generate อัตโนมัติและวางมือ · **แก้ 2026-09-28 (ปิด OQ-14 (ก)):** ต้องติดกันจริงตามเวลา ห้ามข้ามคอลัมน์พัก/lunch — ถ้าคาบก่อน/หลังพักไม่ติดกันจริง ไม่นับเป็นคาบต่อเนื่อง
- AC-037 — การวาง/สลับมือที่ทำให้วิชาคาบต่อเนื่องไม่ครบ N คาบ (หรือแยกวัน) ถูกปฏิเสธพร้อมข้อความอธิบายเหตุผล เช่นเดียวกับ AC-019
- **AC-037a (ใหม่, ปิด OQ-14 (ข))** — ถ้าโควตาคาบ/สัปดาห์ของวิชาไม่ลงตัวกับ N (เช่น โควตา 3 คาบ/สัปดาห์ แต่ N=2) ระบบถือเป็น**การตั้งค่าผิด** ต้องแสดงคำเตือนให้ผู้ใช้แก้ค่าใดค่าหนึ่ง — ไม่ auto-split เป็น 1 บล็อก + 1 คาบเดี่ยว
- **AC-037b (ใหม่, ปิด OQ-14 (ค))** — ถ้า N (คาบต่อเนื่องของวิชา) มากกว่าเพดาน "คาบต่อเนื่องไม่พัก" ของครูคนที่สอน (BR-9) **เพดานของครูชนะเสมอ** ห้ามวางเกินเพดานครูแม้จะทำให้วิชาวางไม่ครบ N คาบ
- **AC-037c (ใหม่, ปิด OQ-14 (ง))** — บล็อกคาบต่อเนื่องที่วางแล้ว **ลบได้เฉพาะทั้งบล็อกพร้อมกันเท่านั้น** ห้ามลบทีละช่องเดียวของบล็อก

### REQ-016 — ห้องเรียนประจำวิชา (Subject Room) + กันห้องชนเวลาเดียวกัน — **ใหม่**

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว:** UI ใหม่แสดงห้อง (เช่น "ห้องทดลองวิทยาศาสตร์ 1") ต่อเซลล์วิชาบนกริด ซึ่งเป็นข้อมูลที่ระบบ as-built เดิมไม่มี — ผู้ใช้ยืนยันว่านี่คือข้อกำหนดใหม่ในขอบเขตของโมดูลนี้ **พร้อมกติกากันห้องชน** (คล้ายกติกากันครูชนของ REQ-008 BR-17 แต่เป็นมิติ "ห้อง" แทน "ครู")

- *ถ้อยคำฉบับ 2026-09-23 (เก็บไว้เป็นประวัติ — ถูกแทนแล้ว ไม่ใช่กติกาปัจจุบัน):* "ห้องเรียนพิเศษ/ห้องปฏิบัติการหนึ่งห้อง ต้องไม่ถูกใช้สอนวิชาอื่นซ้อนเวลาเดียวกัน" (แบบไบนารี — 1 ห้อง 1 การสอนต่อช่วงเวลา)
- **กติกาปัจจุบัน (ยืนยันธุรกิจ 2026-09-28, ปิด OQ-15 (ก)(ง); แก้ข้อความให้ตรง 2026-09-29):** ห้องมี **ความจุ (capacity)** — ห้องหนึ่งใช้พร้อมกันได้หลายวิชา/กลุ่มห้องเรียน **ตราบที่ไม่เกิน capacity ของห้องนั้น** ในเวลาเดียวกัน โดยนับรวมทุกตารางสอนของปีเดียวกัน และการใช้ห้องในระบบ `/academic` — รายละเอียดดู AC-038a และ AC-039 · ห้องมี "ครูผู้ดูแลห้อง" ด้วย ผลของครูผู้ดูแลต่อการจัดตารางและที่ตั้งค่า capacity/ครูผู้ดูแล **ยังเปิดอยู่ที่ OQ-26**

- AC-040 — วิชาที่ไม่ได้กำหนดห้อง (เช่น สอนในห้องเรียนประจำของนักเรียนเอง) ไม่ถูกบังคับกติกานี้

### REQ-017 — เพดานการสอนของครู: หน่วยเป็นชั่วโมงจริง + เพดานรายสัปดาห์เป็น hard constraint (แก้ REQ-002)

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว 3 ข้อ:**

1. **หน่วยของเพดาน "ไม่เกิน N/วัน" และ "ไม่เกิน N/สัปดาห์" คือชั่วโมงสอนจริง** (นับตามความยาวเวลาจริงของคาบ) ไม่ใช่จำนวนคาบ (as-built เดิมนับเป็นคาบ, `nMaxTeachingPeriodPerDay/Week`) — ต้องแก้ตรรกะการนับใน generator และตอนวางมือให้แปลงเป็นชั่วโมงจริงตามความยาวคาบของ template ที่ใช้ ไม่ใช่นับหัวคาบ
2. **เพดาน "ไม่เกิน N/สัปดาห์" ต้องบังคับจริงเป็น hard constraint** เทียบเท่าเพดานรายวันเดิม ทั้ง Generate และวางมือ · *แก้ข้อเท็จจริง 2026-09-28 (ผลตรวจโค้ดของ SA — design.md §39.2, D38, EVD-054/EVD-055):* ฉบับก่อนหน้าเขียนว่าค่านี้ "บันทึกได้แต่ยังไม่มีใครอ่านใช้" ซึ่งไม่ตรง — ค่ารวม /สัปดาห์ **ไม่เคยถูกบันทึกเลย** เพราะ frontend ส่ง `nMaxTeachingPeriodPerWeek` แต่ backend (`RequestSetting`) ไม่มีฟิลด์นี้และทิ้งค่าเงียบ ๆ ตั้งแต่ต้น จึงไม่มีค่าเดิมของ /สัปดาห์ให้ย้ายข้อมูล (ค่าเดิมที่ต้องตัดสินเรื่อง migration มีเฉพาะ /วัน — OQ-16)
3. **ลำดับความสำคัญเปลี่ยน:** UI ใหม่เอา checkbox "ใช้กับครูทุกคน / ยกเว้นครูที่เลือก" ออก — ลำดับที่ถูกต้องคือ **"กำหนดเวลาการสอนรายบุคคล" (ค่ารายคน) ชนะ "กำหนดเวลาการสอนใช้สำหรับครูทุกคน" (ค่ารวม) เสมอ** เมื่อครูคนนั้นมีค่ารายคนตั้งไว้ —ไม่มีขั้น "ยกเว้น" แยกอีกต่อไป (ต่างจาก BR-8 เดิมที่มี 3 ระดับ: รายคน > รวม-หักยกเว้น > ไม่จำกัด)

**Acceptance criteria:**

- AC-041 — เพดาน/วันและ/สัปดาห์ถูกคำนวณและบังคับเป็น**ชั่วโมงสอนจริง** ไม่ใช่จำนวนคาบ ทั้ง Generate และวางมือ · **แก้ 2026-09-28 (ปิด OQ-16 (ก)):** ผู้ใช้กรอกเพดานเป็น**จำนวนเต็มชั่วโมงเท่านั้น** ไม่รับทศนิยม/เศษนาที
- AC-042 — เพดาน/สัปดาห์ถูกบังคับเป็น hard constraint เทียบเท่า AC-003 เดิม (ที่เดิมมีแค่/วัน)
- AC-043 — ครูที่มีค่ารายบุคคลตั้งไว้ ใช้ค่ารายบุคคลเสมอ โดยไม่ต้องพึ่ง flag "ยกเว้น" ใด ๆ — ครูที่ไม่มีค่ารายบุคคลใช้ค่ารวมของทุกคน · **AC-043a (ใหม่, ปิด OQ-16 (ค)):** ครูที่ตั้งค่ารายบุคคลเฉพาะ "/วัน" (ไม่ได้ตั้ง "/สัปดาห์") — เพดาน/สัปดาห์ของครูคนนั้น**ใช้ค่ารวมของทุกคนแทน** ไม่ใช่ถือว่าไม่จำกัด
- **แก้ BR-8 / AC-003 เดิม**: ลำดับความสำคัญใหม่คือ **รายคน > รวม** (2 ระดับ) แทน **รายคน > รวม-หักยกเว้น > ไม่จำกัด** (3 ระดับ)
- **AC-043b (ใหม่, migration gate — ปิด OQ-16 (ข)):** ค่าเพดาน/วันเดิมที่โรงเรียนบันทึกไว้แล้ว (หน่วย "คาบ") **ไม่แปลงเป็นชั่วโมงอัตโนมัติ (M1)** — ถือว่าไม่จำกัดจนกว่าผู้ใช้จะกรอกค่าใหม่เป็นชั่วโมงเอง ไม่มีการคำนวณแปลงจากความยาวคาบของ template (M2) หรือการตีความเลขเดิมตรงๆ เป็นชั่วโมง (M3) — ค่ารวม/สัปดาห์ไม่มีข้อมูลเดิมอยู่แล้ว (ดูข้อ 2 ด้านบน) จึงไม่ต้องตัดสิน migration ส่วนนั้น

**หมายเหตุสำคัญ — ต้องส่งต่อ system-analyst:** การแปลง "คาบ" เป็น "ชั่วโมงจริง" กระทบตรรกะ hard constraint หลักของ REQ-008/REQ-009 โดยตรง (BR-8, BR-9) — ต้องออกแบบว่าจะเก็บค่าที่ผู้ใช้กรอกเป็นหน่วยชั่วโมงในฐานข้อมูล (schema change) หรือเก็บเป็นคาบแล้วแปลงตอนคำนวณ (logic-only) — เป็นการตัดสินใจทางเทคนิคที่ระบบ (ไม่ใช่ BA) ต้องเลือก · migration ของค่า/วันเดิมปิดแล้ว (M1, AC-043b) ไม่ต้องรอคำตอบเพิ่ม

### REQ-018 — ครูประจำชั้นสอนเฉพาะห้องที่รับผิดชอบ (Homeroom-restricted Teaching) — แก้ REQ-006

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว:** UI ใหม่เอาแท็บ "ครูที่ปรึกษาประจำระดับ/ห้อง" (Main Teaching Grade, REQ-006 เดิม) และ checkbox กติกาครูที่ปรึกษาของ REQ-002 (ใช้ทุกคน/ยกเว้น/เฉพาะระดับ) ออก แทนด้วยแนวคิดใหม่ **"ครูประจำชั้นสอนเฉพาะห้องที่รับผิดชอบ"**:

- ครูประจำวิชายังคงถูกกำหนดสิทธิ์สอนแต่ละวิชาแยกตามแผน/ห้องได้ตามปกติ (เทียบเท่า `TPlanCourseTeacher` เดิม — REQ-005/REQ-006 พื้นฐานยังใช้ได้)
- เพิ่มตัวเลือกใหม่ **ระดับครูรายบุคคล**: ตั้งค่าให้ครูคนหนึ่ง **"สอนได้เฉพาะห้องที่ตนรับผิดชอบ (ห้องประจำ) เท่านั้น ห้ามไปสอนห้องอื่น"** — ออกแบบมาให้โรงเรียนขนาดเล็ก หรือครูอนุบาล/ประถมที่สอนหลายวิชาให้ห้องเดียวใช้งาน (ครูประจำชั้นคนหนึ่งสอนได้ทุกวิชาของห้องตัวเอง แต่สอนห้องอื่นไม่ได้)
- ครูที่ไม่ได้ตั้งค่านี้ ยังคงสอนได้ตามสิทธิ์รายวิชา/แผนตามปกติ (ไม่ถูกจำกัดห้อง)

### REQ-019 — ส่งตารางสอนเข้าระบบตารางสอนหลักของ SB System (ปุ่ม "ใช้งานตารางสอน") — **ใหม่**

**การตัดสินใจทางธุรกิจที่ยืนยันแล้ว:** ปุ่ม "ใช้งานตารางสอน" ใน UI ใหม่ (แทนที่แท็บ ใช้งาน/ไม่ใช้งาน ของ REQ-007 เดิม) หมายถึง **ส่งตารางสอนที่สร้าง/บันทึกแล้วเข้าระบบตารางสอนหลักของ School Bright System** — ไม่ใช่แค่ toggle `isActive` ภายในโมดูลเหมือนเดิม

**ระบบปลายทาง (ยืนยันธุรกิจ 2026-09-23, ปิด OQ-11): `/academic` (TSchedule + Service Academic เดิม)** — คือระบบตารางสอนเก่าที่ design.md §22 เคยบันทึกไว้ว่า**นอกขอบเขต**และ**ไม่เคย sync กับโมดูลนี้มาก่อน** (เทียบ OQ-7) การยืนยันนี้พลิกสมมติฐานเดิม: `/academic` **กลายเป็นปลายทาง sync ของโมดูลนี้แล้ว** แม้ยังคงเป็นระบบ/backend คนละตัว (Service Academic คนละ backend จาก AITimeTableBackend — design.md §12)

**การตัดสินใจทางธุรกิจที่ยืนยันเพิ่ม 2026-09-28 (ปิด OQ-12, OQ-13):**

- **ทิศทาง sync เป็นทางเดียวเท่านั้น** (timetableai → academic) — ไม่มีข้อมูลย้อนกลับมาที่โมดูลนี้ ไม่ต้องออกแบบ read-back
- **ไม่มี publish/lock** — ส่ง "ใช้งานตารางสอน" ซ้ำได้เรื่อย ๆ ไม่จำกัดจำนวนครั้ง และยังแก้ไขตารางในโมดูลนี้ต่อได้ตามปกติหลังส่งแล้ว แต่ **การส่งซ้ำแต่ละครั้งต้องแสดงคำเตือนว่าจะวางทับข้อมูลเดิมใน `/academic` และรอผู้ใช้ยืนยันก่อนทุกครั้ง** (เทียบรูปแบบ conflict-warning เดียวกับ AC-031 ของ REQ-013)

**การตัดสินใจทางธุรกิจที่ยืนยันเพิ่ม 2026-09-28 (ปิด OQ-18 (ก)(ข)(ค)(ง)):**

- **(ก) Conflict handling — แทนที่ทั้งหมดเสมอ:** ถ้าปลายทาง (ห้อง, เทอม) ใน `/academic` มีตารางอยู่แล้ว การส่งจะ**แทนที่ข้อมูลเดิมทั้งหมด** (ไม่ merge บางส่วน) — คู่กับ AC-049 ที่ต้องเตือน+รอยืนยันก่อนทุกครั้งที่จะแทนที่
- **(ข) ฟิลด์ที่โมดูลนี้ไม่มีแต่ `/academic` ต้องการ:** ส่ง **`calculate = true`** เสมอ ส่วนฟิลด์อื่นที่ไม่มีข้อมูล (เวลาเช็คชื่อ IN/OUT, `nTimeLate`, ตัวย่อวิชา ฯลฯ) **ส่งเป็นค่า default หรือ `null`** — system-analyst กำหนดค่า default ที่สมเหตุสมผลต่อฟิลด์
- **(ค) หลายตารางสอนพร้อมกัน:** ปีการศึกษาเดียวอาจมีตารางที่ `isActive=true` หลายชุด (REQ-007) — **ส่งเข้า `/academic` ได้หลายชุดพร้อมกัน ไม่จำกัดจำนวน** ไม่ต้องเลือกทีละชุด
- **(ง) ความหมายของ `isActive`/REQ-007 หลังมี REQ-019:** `isActive` **ยังมีความหมาย** และกลายเป็น **gate ของการส่ง** — ต้อง `isActive=true` ก่อนจึงจะกดปุ่ม "ใช้งานตารางสอน" ส่งเข้า `/academic` ได้ (ตารางที่ปิดใช้งานอยู่ส่งไม่ได้)

**Acceptance criteria:**

- AC-047 — กดปุ่ม "ใช้งานตารางสอน" แล้วตารางสอนที่เลือกถูกส่งเข้า `/academic` (TSchedule + Service Academic) ทิศทางเดียว ไม่มี read-back กลับมาที่โมดูลนี้ — **กดได้เฉพาะตารางที่ `isActive=true` เท่านั้น**
- AC-048 — ระบบต้องแจ้งผลสำเร็จ/ล้มเหลวของการส่งจริง (ไม่ใช่ success modal ลวงแบบ D26 ของ REQ-010 เดิม)
- **AC-049 (ใหม่, 2026-09-28)** — ส่งซ้ำ (ตารางที่เคยส่งไปแล้ว) ต้องแสดงคำเตือนว่าจะ**แทนที่ข้อมูลเดิมทั้งหมด**ใน `/academic` และรอผู้ใช้ยืนยันก่อนทุกครั้ง ห้ามเขียนทับเงียบ ๆ — ไม่มีสถานะ publish/lock ที่ปิดกั้นการส่งซ้ำ
- **AC-052 (ใหม่, 2026-09-28)** — payload ที่ส่งไป `/academic` ต้องมี `calculate = true` เสมอ ฟิลด์อื่นที่โมดูลนี้ไม่มีข้อมูลส่งเป็น default/`null` ตาม schema ที่ system-analyst กำหนด
- **AC-053 (ใหม่, 2026-09-28)** — ผู้ใช้ส่งตารางสอนหลายชุดของปีเดียวกันเข้า `/academic` พร้อมกันได้ ไม่ถูกจำกัดเหลือ 1 ชุด/ปี

**หมายเหตุสำคัญ — ต้องส่งต่อ system-analyst ก่อน implement ใด ๆ:** นี่คือ **integration ใหม่ข้ามระบบ ข้าม backend** (AITimeTableBackend → Service Academic) ที่ design.md ยังไม่เคยวิเคราะห์มาก่อน (`/academic` ถูกกันไว้นอกขอบเขตมาตลอด — §22) เข้าเงื่อนไข "เพิ่ม module/feature ใหม่" ของ pipeline routing เต็มรูปแบบ ไม่ใช่แค่ schema change เดียว — **ปิดครบทุก OQ ของ REQ-019 แล้ว (OQ-12, OQ-13, OQ-18 ก-ง) ณ 2026-09-28** พร้อมส่งต่อ system-analyst ออกแบบ mapping/transaction boundary ข้ามระบบได้เต็มที่ — ยังต้องยืนยัน schema จริงของ `/academic` (`calculate`, ฟิลด์ default อื่นๆ) กับเจ้าของระบบนั้นในขั้นตอน SA ต่อไป

**หมายเหตุข้อเท็จจริงจากการออกแบบ (design.md Rev 6 §41 DES-016, D46, D47, EVD-076..EVD-078 — ไม่ใช่ requirement ใหม่ ไม่เปลี่ยน AC ใด):**

- endpoint `timetables/import` ของ Service Academic (all-or-nothing) **ไม่รองรับ `calculate`/`roomId`** ตามเอกสาร spec (EVD-077 — สถานะ `inferred` จาก spec-doc ยังไม่ยืนยันกับเจ้าของ) ขณะที่ upsert รายแถวแบกฟิลด์ได้แต่ไม่ atomic (EVD-076) → การ "แทนที่ทั้งหมดต่อ (ห้องเรียน, เทอม)" ของ OQ-18 (ก) + AC-052 (`calculate = true`) ยังไม่มีวิธี atomic บนสัญญาที่มีอยู่ — transaction boundary เป็นคำถามของเจ้าของ Service Academic (SA-Q6, SA-Q12) ไม่ใช่การตัดสินใจของ BA
- `TSchedule` ไม่มีคอลัมน์ห้อง (D46) และไม่มี endpoint อ่านการใช้ห้อง (D47) — กระทบการกันนับห้องซ้ำกับแถวที่โมดูลส่งเอง (REQ-016/AC-039) ซึ่ง design.md ใช้บันทึกผลการส่งเป็นกลไก (BR-56)
- ค่า default ต่อฟิลด์ของ payload (AC-052) เป็นข้อเสนอ SA ที่รอเจ้าของ `/academic`/ระบบเช็คชื่อยืนยัน (SA-Q11)

## Constraints & Assumptions

- โมดูลทำงาน**รายปีการศึกษาเท่านั้น** ไม่รองรับภาคเรียน — โครงสร้างข้อมูลฝั่งโมดูลไม่มี term (design.md §18.3) — **as-built fact ณ 2026-09-21; อยู่ระหว่างเปลี่ยนแปลงตาม REQ-012 (ยืนยันธุรกิจแล้ว รอ system-analyst amend design.md)**
- ทุกกติกาถูกบังคับที่ app layer เท่านั้น (ฐานข้อมูลฝั่งโมดูลไม่มี FK/unique/check) — การแก้กติกาใด ๆ ต้องคงจุดบังคับเดิม ห้ามย้ายไปพึ่ง constraint ระดับฐานข้อมูลโดยไม่แก้ design ประกอบ (design.md DES-001 Fallback)
- การคำนวณทั้งหมดอยู่ฝั่ง client (browser, main thread) — backend เป็น CRUD ล้วน ไม่มี solver/AI/job ฝั่ง server (DES-005, DES-006)
- การบันทึกไม่เป็น atomic (ไม่มี DB transaction — D29) และ save ตารางแจ้งผลเท็จ (D26) — เป็นข้อเท็จจริง as-built ที่บันทึกไว้ การแก้เป็นการตัดสินใจตาม design.md §32.1 ข้อ 2–3
- **Auth (ยืนยัน 2026-09-29 — OQ-1):** ~~สมมติฐานว่ามี gateway คุม auth~~ ถูกแทนที่ด้วยการตัดสินใจ: API ของโมดูลต้องมี `[Authorize]` ด้วยวิธีเดียวกับ `BypassAcademic.aspx.cs` (JWT + `token_secret`) · ก่อนมี design + implement, backend as-built ยังไม่มี authorization ใด ๆ (D1) — **ยังเป็น blocker ก่อน production** · กลไกปิดแล้ว (OQ-29, 2026-09-29): Bearer JWT + `token_secret` เดียวกับ SB + สิทธิ์ตามเมนูและ `TMenuPermission` (MenuID 401/402/403/404/422) ไม่มี endpoint ยกเว้น · ผู้ใช้อนุมัติ breaking change 401 · *2026-10-02:* กติกาสถานะ admin/โรงเรียน (AC-071/AC-072) ขยายขอบเขต breaking เกินการอนุมัติ 2026-09-29 — **ยังไม่ได้รับทราบ (OQ-40)** · คอลัมน์และความหมาย null ของ "active"/"ถูกลบ" ยังไม่ยืนยัน (OQ-39) — ระหว่างรอ design.md ใช้คอลัมน์ที่ resolver ใช้อยู่เป็น fallback เชิงเทคนิค (สมมติฐาน — ยังไม่ยืนยัน)
- **`token_secret` (ความเสี่ยงที่ผู้ใช้รับ 2026-09-29):** SA รายงาน (D49) และผมยืนยันว่ามีคีย์ `Token_Secret` ใน `sb-api-academic-timetable-ai/AITimeTableBackend/appsettings.json` บรรทัด 13 (ไม่ได้บันทึกค่า) — ผู้ใช้ตัดสินใจ **"ปล่อยไว้แบบนี้"** ไม่ rotate/ย้ายไป secret store: ใครอ่าน repo ได้ปลอม token ของ SB ได้ · ผู้ใช้ไม่มีสิทธิ์ rotate เอง (เป็นการกระทำของเจ้าของระบบ SB) · ความเสี่ยงนี้เป็นของ DES-018 และยังต้องผ่านรอบ `security` (Critical/Important = ประตูมนุษย์)
- **`BACKEND_URL` (ตัดสินใจชั่วคราว 2026-09-29 — OQ-4):** production ชี้โดเมน dev (`dev-service-academic-timetable-ai.schoolbright.co` — D17) ต่อไปก่อน ไม่ต้องมีวิธี override ในตอนนี้ · ความเสี่ยง: production ใช้ backend/ข้อมูลของ dev · ต้องทบทวนเมื่อมี prod backend · **ข้อมูลใน DB (ผู้ใช้ยืนยัน 2026-09-30):** DB ที่โมดูลใช้อยู่ตอนนี้ (production frontend → backend dev, R32) **ไม่มีข้อมูลโรงเรียนจริง มีแต่ข้อมูลทดสอบ** · ต้องยืนยันซ้ำก่อนมีข้อมูล production (ยังไม่มีวันที่)
- **`nCourseIntensity` (ยืนยันเจตนา 2026-09-29 — OQ-2):** ต้องบังคับใช้จริง (ปัจจุบัน as-built เก็บอย่างเดียว — D12) · ระดับ 0/1/2 และสูตรหนัก/เบายืนยันแล้ว (OQ-30 ปิด 2026-09-29, design.md DES-019) · **เกณฑ์ "หนักเกิน" (ผู้ใช้ยืนยัน 2026-09-30 — OQ-34):** class-day ที่จำนวนคาบหนักเกิน ⌈คาบหนักทั้งสัปดาห์ ÷ วันที่มีคาบ⌉ ของห้องนั้น — T_c คำนวณต่อห้องเรียนจากกริดของห้องนั้นเองในตารางนั้น (ผู้ใช้ชี้แจง 2026-09-30) · `ConsecutiveHeavy` เฉพาะระดับ 2 · ระดับ 0 ไม่แสดงข้อเสนอแนะ · (design.md BR-78 ใช้เกณฑ์เดียวกันเป็นเป้าหมาย L1 ของ solver — การผูกนั้นเป็นการตีความเชิงเทคนิคของ SA) · หมวด {พื้นฐาน, เพิ่มเติม} = `TCourseGroup` (ผู้ใช้ตอบ 2026-09-29 — design.md Rev 10 SA-Q16) · ส่วน Class Continuity ยืนยันแล้วว่าต้องบังคับจริง (REQ-015, 2026-09-23)
- เอกสารนี้ครอบคลุมโมดูล timetableai (7 routes) **บวก integration ขาออกไป `/academic` ตาม REQ-019** (ส่งตารางผ่าน API ของ Service Academic — design.md §41) · ส่วนอื่นของระบบ `/academic` (หน้าจอ/ข้อมูลของระบบนั้นเอง), OCR/kruai import และ menu/notification service ยังอยู่นอกขอบเขต (design.md §22 — หมายเหตุ Rev 5)
