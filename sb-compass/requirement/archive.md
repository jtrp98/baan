## Overview

SB Compass คือฟีเจอร์ในระบบ ClassOnlineWeb (โปรเจกต์ `sb-web-student`) ที่นำ **คะแนนสอบจริง
รายวิชา 0-100 ของนักเรียน** ที่ครูกรอกไว้ในระบบเกรด มาแปลงเป็นคำแนะนำด้านการเรียนและอาชีพ:
บอกว่าเด็กเก่งวิชาไหน ควรเสริมวิชาไหน เทียบกับเพื่อนรุ่นเดียวกันทั่วเครือข่ายอยู่อันดับไหน
และสายการเรียน/อาชีพใดเข้ากับเด็กมากที่สุด พร้อมบอกว่าต้องพัฒนาอีกกี่คะแนนถึงจะถึงเกณฑ์ของสายนั้น

ผู้ใช้ปลายทางคือ **นักเรียนเจ้าของบัญชีเท่านั้น** — ผู้ใช้ยืนยัน (2026-08-24) ว่ารอบนี้
**ไม่เพิ่ม role ผู้ปกครอง / ครู / ผู้บริหาร** ถ้าผู้ปกครองจะดู ก็ดูผ่านการล็อกอินด้วยบัญชีของลูกเอง
เหมือนพฤติกรรมปัจจุบัน (ปิด OQ-01, OQ-02)
คำว่า "AI" ในหน้าจอเป็นการนำเสนอ: ตัวคำนวณจริงเป็น rule-based engine ในระบบเราเอง
**ไม่มีการส่งข้อมูลออกไปให้ LLM หรือบริการภายนอกใด ๆ** (ยืนยันจากโค้ด — `CompassApiController.cs`
บรรทัด 12-19 และไม่พบการเรียก HTTP ออกนอกระบบใน flow นี้)

การปลดล็อก Premium ถือเป็น **กลไกภายนอก** ที่ Compass แค่เชื่อ/ตรวจผลลัพธ์ — ไม่อยู่ในขอบเขต
เอกสารนี้ (ยกเว้นประเด็นความปลอดภัยใน OQ-06)

## Core Features

### REQ-001 — จุดแข็ง/จุดอ่อนรายวิชา (ฟรี)
อ่านคะแนนจริงรายคอร์สจาก grade DB (`PGTGrade ⋈ PGTGradeDetail` และทับด้วย `PGTGradeEdit`
ถ้าครูแก้เกรดไว้) แล้วยุบรวมเป็นค่าเฉลี่ยต่อ "วิชาหลัก" 8 กลุ่ม: คณิตศาสตร์ · วิทยาศาสตร์ ·
ภาษาอังกฤษ · ภาษาไทย · สังคมศึกษา · สุขศึกษาและพลศึกษา · ศิลปะ · การงานอาชีพและเทคโนโลยี
- การจับคอร์สเข้ากลุ่มวิชาใช้ **การจับคำในชื่อวิชา** (keyword heuristic) คอร์สที่จับกลุ่มไม่ได้
  (ชุมนุม กิจกรรม สอนซ่อมเสริม) จะถูก **ตัดออก** ไม่นำมาคิดเลย
- คอร์สที่ยังไม่มีคะแนนเป็นตัวเลข ถูกตัดออกจากค่าเฉลี่ย
- **ไม่รอให้ผลการเรียนถูกอนุมัติ** (ไม่เช็ค `IsTermApproved`) — มีคะแนนเท่าไหร่ใช้เท่านั้น
  เพื่อให้เด็กที่เรียนมาครึ่งปีก็ยังใช้งานได้
- **การรวมคะแนนวิชาย่อย → กลุ่มสาระ: คงของเดิม = ค่าเฉลี่ยดิบธรรมดา (simple average)**
  ผู้ใช้ยืนยันเมื่อ 2026-08-24 ว่า **ฟีเจอร์นี้เป็นของฟรี จึงไม่ต้องเปลี่ยนสูตร** — เอาตามเดิม
  (เป็นการ **กลับคำ** จากที่ตกลงไว้ก่อนหน้าในวันเดียวกันว่าจะถ่วงน้ำหนักด้วยหน่วยกิตที่นี่
  เหตุผลที่ผู้ใช้ให้: ลืมไปว่าจุดแข็ง/จุดอ่อนเป็นฟีเจอร์ฟรี · ดู REQ-012 และ OQ-13)
- เกณฑ์ตัดระดับ (ค่าที่ hardcode อยู่จริงใน `CompassApiController.Analyst` และผู้ใช้ **ยืนยันให้คงไว้**
  เมื่อ 2026-08-24): **≥ 80 = จุดแข็ง · < 60 = ควรเสริม · 60-79 = ปานกลาง**
  ใช้ **ค่าเดียวกันทุกกลุ่มสาระ** — ผู้ใช้ปฏิเสธแนวทาง "เกณฑ์ต่างกันตามกลุ่มสาระ" อย่างชัดเจน
  เพราะซับซ้อนและเป็นอัตวิสัยเกินไป (ปิด OQ-04)

**Acceptance criteria (ทดสอบได้)**
1. (AC-001.1) คะแนนที่ใช้อ่านจาก grade DB จริง (`PGTGrade ⋈ PGTGradeDetail` ทับด้วย `PGTGradeEdit` ถ้าครูแก้เกรดไว้) โดยไม่รอให้ผลการเรียนถูกอนุมัติ (ไม่เช็ค `IsTermApproved`) — มีคะแนนเท่าไหร่ใช้เท่านั้น
2. (AC-001.2) คอร์สที่จับกลุ่มวิชาไม่ได้ (ไม่ match keyword ในชื่อวิชา) และคอร์สที่ไม่มีคะแนนเป็นตัวเลข ถูกตัดออกจากค่าเฉลี่ยทั้งหมด
3. (AC-001.3) การรวมคะแนนวิชาย่อยเป็นกลุ่มสาระใช้ค่าเฉลี่ยดิบธรรมดา (simple average) และจัดระดับด้วยเกณฑ์เดียวกันทุกกลุ่มสาระ: ≥80 = จุดแข็ง · <60 = ควรเสริม · 60-79 = ปานกลาง

### REQ-002 — ข้อความสรุปแบบ AI (ฟรี)
สรุปหนึ่งบรรทัดจากผลของ REQ-001 (รายชื่อวิชาจุดแข็ง / วิชาที่ควรเสริม / เกณฑ์ผ่าน)
ถ้ายังไม่มีคะแนนในระบบเลย ต้องแสดงข้อความว่ารอครูกรอกผลสอบ ไม่ใช่แสดงหน้าว่างหรือ error
หน้าจอมีการหน่วงเวลาแบบ "กำลังคิด" เพื่อการนำเสนอ — ไม่ใช่การประมวลผลจริง

**Acceptance criteria (ทดสอบได้)**
1. (AC-002.1) ข้อความสรุปหนึ่งบรรทัดสร้างจากผลของ REQ-001 (รายชื่อวิชาจุดแข็ง / วิชาที่ควรเสริม / เกณฑ์ผ่าน)
2. (AC-002.2) ถ้ายังไม่มีคะแนนในระบบเลย แสดงข้อความว่ารอครูกรอกผลสอบ — ไม่แสดงหน้าว่างหรือ error

### REQ-003 — คำแนะนำเชิงลึกต่อวิชาที่ควรเสริม (Premium)
สำหรับวิชาที่ถูกจัดเป็น "ควรเสริม" แสดงการ์ดบอกว่าจุดอ่อนนี้กระทบอาชีพอะไร และมี 3 วิธีพัฒนา
เนื้อหาทั้งหมดเป็น **ข้อความที่เขียนไว้ล่วงหน้าต่อ (วิชา × ระดับ)** ไม่ได้มาจากข้อมูลระดับหัวข้อย่อยจริง
ถ้าไม่มีวิชาที่ควรเสริมเลย ให้ซ่อนส่วนนี้ทั้งบล็อก

**Acceptance criteria (ทดสอบได้)**
1. (AC-003.1) สำหรับวิชาที่ถูกจัด "ควรเสริม" แสดงการ์ดบอกว่าจุดอ่อนนี้กระทบอาชีพอะไร พร้อม 3 วิธีพัฒนา จากเนื้อหาที่เขียนไว้ล่วงหน้าต่อ (วิชา × ระดับ)
2. (AC-003.2) ถ้าไม่มีวิชาที่ควรเสริมเลย ซ่อนส่วนนี้ทั้งบล็อก

### REQ-004 — สถิติเทียบเครือข่ายทั่วประเทศ + อันดับ (Premium)
เทียบคะแนนเด็กกับ **ค่าเฉลี่ยของนักเรียนระดับชั้นเดียวกันทั้งเครือข่าย** และบอกอันดับ
- ระดับชั้นของเด็กตัดสินจาก **ห้องที่คะแนนของเด็กกระจุกอยู่มากที่สุด** และเทียบข้ามโรงเรียนด้วย
  รหัสระดับชั้นกลาง (`MasterCode` → `mc:XXX`; ถ้าโรงเรียนไม่ได้กรอก จะถอดจากชื่อชั้นภาษาไทย

### REQ-012 — ค่าเฉลี่ยถ่วงน้ำหนักด้วยหน่วยกิต

> **สถานะข้อนี้ (อัปเดต 2026-08-24)**: **ยังใช้กับ REQ-001/REQ-002 (ฟีเจอร์ฟรี) ไม่ได้** —
> ผู้ใช้กลับคำในวันเดียวกันว่าฟีเจอร์จุดแข็ง/จุดอ่อนเป็นของฟรี จึงให้คงค่าเฉลี่ยดิบธรรมดาไว้
> **แต่ตัวข้อ REQ-012 ไม่ถูกยกเลิก (ปิด OQ-13 เมื่อ 2026-08-24)** — สูตรถ่วงน้ำหนักยังใช้กับ
> consumer อื่นของค่าคะแนนกลุ่มสาระตามที่ระบุใน `## ขอบเขตที่ยืนยันแล้ว` ด้านล่าง
> business rule ของข้อนี้ **ยืนยันครบแล้ว** เหลือเพียงเงื่อนไข feasibility OQ-12 (schema หน่วยกิต)

**สูตร (ยืนยันแล้ว)**: ก่อนจะยุบคะแนนวิชาย่อยหลายวิชาให้เป็นคะแนน
ของกลุ่มสาระ (canonical subject) เดียว ต้อง **ถ่วงน้ำหนักคะแนนแต่ละวิชาด้วยหน่วยกิตของวิชานั้น**

```
คะแนนกลุ่มสาระ = Σ(คะแนนวิชา_i × หน่วยกิตวิชา_i) / Σ(หน่วยกิตวิชา_i)
                  โดย i = ทุกวิชาที่ถูก map เข้ากลุ่มสาระเดียวกัน และมีคะแนนเป็นตัวเลข
```

เหตุผลเชิงธุรกิจ: วิชาที่หน่วยกิตมากกว่าคือวิชาที่เด็กเรียนหนักกว่า จึงควรมีน้ำหนักต่อการตัดสินว่า
เด็ก "เก่ง/อ่อน" กลุ่มสาระนั้นมากกว่าวิชาที่หน่วยกิตน้อย การเฉลี่ยแบบธรรมดาทำให้วิชาเล็กมีน้ำหนัก
เท่าวิชาหลัก ซึ่งบิดเบือนผลวิเคราะห์

**ขอบเขตที่ยืนยันแล้ว (ห้ามขยายเอง)**
- เกณฑ์ตัด 60 / 80 ยังเป็นค่าเดิม และ **เท่ากันทุกกลุ่มสาระ** (ดู REQ-001)
- **fallback เมื่อหน่วยกิตรวม = 0 เป็นกติกาเดียวกันทุกที่ที่สูตรนี้ถูกใช้** ไม่ใช่กฎเฉพาะจุด —
  ไม่ว่าค่าคะแนนกลุ่มสาระนั้นจะถูกใช้ที่ Analytics (`analyst/{sID}`), Fit Score (REQ-005/REQ-006),
  หรือ consumer อื่นใดที่ REQ-012 ผูกไว้ ทุกจุดต้องได้ค่าเดียวกันจาก fallback เดียวกัน
  (ดู Acceptance criteria ข้อ 4)
- **ฝั่งฟรี (REQ-001/REQ-002) ยังแสดงค่าเฉลี่ยดิบธรรมดาตามเดิม** — ไม่ต้องนำค่าถ่วงน้ำหนักไป
  แสดงเพิ่มบนหน้าจอให้เด็กเห็นเป็นเลขชุดที่สอง ถ้าอนาคตจะแสดง ต้องกลับมา amend requirement นี้ก่อน
- **ห้ามนำปัจจัยขนาด/ชื่อเสียงโรงเรียนมาปนในสูตรนี้** ผู้ใช้ปฏิเสธชัดเจน เหตุผลที่ให้บันทึกไว้:
  (1) ไม่มีตัวเลขมาตรฐานอ้างอิง ต้องพึ่งการ tag เอง ซึ่งเป็นอัตวิสัย
  (2) จะทำให้จุดแข็ง/จุดอ่อนของ *ตัวเด็ก* ถูกปนเปื้อนด้วยปัจจัยที่ไม่ใช่ตัวเด็กเอง
  (3) ระบบมี "เทียบทั่วประเทศ" (REQ-004) อยู่แล้ว ซึ่งเป็นที่ที่เหมาะกับบริบทโรงเรียนมากกว่า

**Acceptance criteria (ทดสอบได้)**
1. (AC-012.1) กลุ่มสาระ "คณิตศาสตร์" มี 2 วิชา: คณิตพื้นฐาน คะแนน 60 หน่วยกิต 1.5 · คณิตเพิ่มเติม คะแนน 90
   หน่วยกิต 0.5 → คะแนนกลุ่มสาระ = (60×1.5 + 90×0.5) / (1.5+0.5) = 120/2 = **67.5** → จัดเป็น
   "ปานกลาง" (ไม่ใช่ 75 แบบเฉลี่ยธรรมดา ซึ่งก็ยังปานกลาง แต่ตัวเลขที่แสดงต้องเป็น 67.5)

   **"จุดแข็ง"** ยืนยันว่าหน่วยกิตเปลี่ยนผลการจัดระดับได้จริง

   คะแนนไม่มีข้อมูลหน่วยกิตกำกับ — ระบบต้อง **fallback กลับไปใช้กฎเดิมแบบไม่ถ่วงน้ำหนัก คือ
   ค่าเฉลี่ยคะแนนดิบธรรมดา (simple average) ของทุกวิชาที่มีคะแนนเป็นตัวเลขในกลุ่มสาระนั้น**

   - **fallback นี้ใช้สม่ำเสมอทุกที่ที่สูตรถ่วงน้ำหนักถูกใช้** ไม่ใช่แค่ที่ Analytics

### REQ-017 — เพิ่มคอลัมน์ `stddev_score` ใน `compass_level_subject_stat` (รองรับ T-Score ของ `sb-compass-faculty-match REQ-013`)
(ยืนยันโดยผู้ใช้ — ส่งต่อผ่าน coordinator relay ในรอบ `business-analyst` นี้, 2026-08-31)

**เหตุผลเชิงธุรกิจ**: `sb-compass-faculty-match REQ-013` ต้องคำนวณ **T-Score** ของคะแนนกลุ่มสาระ
ของเด็กเทียบกับฐานนักเรียนทั้งประเทศ ซึ่งต้องใช้ **ส่วนเบี่ยงเบนมาตรฐานระดับประเทศต่อ
(ระดับชั้น × กลุ่มสาระ)** แต่ตาราง `compass_level_subject_stat` ปัจจุบันเก็บแค่ `mean_score`
ไม่มีค่าเบี่ยงเบนมาตรฐาน — โมดูลนี้ (`sb-compass`) เป็นเจ้าของตารางนี้ จึงต้องมาเปิด requirement
ที่นี่แทน `sb-compass-faculty-match` ที่ไม่มีสิทธิ์แก้ schema ของโมดูลนี้เอง

- **เพิ่มคอลัมน์ `stddev_score`** ในตาราง `compass_level_subject_stat` แบบ **additive เท่านั้น** —
  ไม่แก้/ไม่ลบคอลัมน์เดิม (`mean_score`, `student_count`, `school_count`, `updated_at`, ฯลฯ
  คงเดิมทุกตัว) ไม่กระทบ consumer เดิมที่อ่านแค่ `mean_score` (REQ-004, REQ-005/REQ-006 — แม้
  REQ-005 จะถูกแทนที่แล้วตาม REQ-011 ข้างต้น แต่ตารางนี้ยังใช้ร่วมกับ REQ-004 ที่ยังทำงานอยู่)
- **รูปแบบการคำนวณ: ใช้ pattern เดียวกับ `mean_score` ที่มีอยู่แล้วในโค้ดจริง** — ยืนยันจาก
  `Helper/CompassRankingService.cs` (บรรทัด ~401 `TRUNCATE compass_level_subject_stat` และ
  ~411 `INSERT INTO compass_level_subject_stat (...)`) ว่าปัจจุบัน `mean_score` **ไม่ได้อัปเดตทีละ
  คะแนนแบบ incremental** แต่ถูกคำนวณใหม่ทั้งหมดในรอบ batch เดียวกันของ `recompute/national-stats`
  (REQ-010/REQ-014) แบบ **ล้างตารางทั้งหมดแล้วเขียนใหม่ทุกครั้งที่รัน** — `stddev_score` ต้อง
  คำนวณและเขียนพร้อมกันในรอบ batch เดียวกันนี้ ด้วยพฤติกรรมเดียวกันทุกประการ **ไม่ใช่ backfill
  ครั้งเดียวแยกต่างหาก และไม่ใช่การอัปเดตต่อเนื่องทุกครั้งที่มีคะแนนใหม่เข้ามา** — นี่เป็นข้อสรุป
  จากการอ่านโค้ดจริง ไม่ใช่คำถามที่ต้องรอผู้ใช้ตอบ
- **ผู้ใช้ปัจจุบันของค่านี้คือ `sb-compass-faculty-match REQ-013` เท่านั้น** — `sb-compass` เอง
  ยังไม่มีหน้าจอ/ฟีเจอร์ใดที่ต้องแสดงหรือใช้ `stddev_score` โดยตรงในรอบนี้ ถ้าต้องการในอนาคตต้อง
  กลับมา amend ข้อนี้เพิ่ม
- **ไม่กระทบพฤติกรรมอื่นของ REQ-010** (สถานะ `idle`/`running`/`done`/`failed`, กันสั่งซ้อน,
  โรงเรียนที่คำนวณพลาดไม่ทำให้ทั้ง batch ล้ม) — เพิ่มแค่คอลัมน์และค่าที่คำนวณเพิ่มในรอบเดิม

**ยังไม่ปิด (feasibility — ไม่บล็อกการส่งต่อ)**: สูตร stddev ที่แน่นอน (population stddev หรือ
sample stddev, และวิธีจัดการกลุ่มตัวอย่างเล็ก — REQ-004 ยืนยันแล้วว่าไม่มี minimum sample size
สำหรับ mean แต่ stddev ของกลุ่มตัวอย่าง 1 คนไม่มีความหมายทางสถิติ) **ยังไม่มีคำตอบจากผู้ใช้**
บันทึกเป็น **OQ-14** ให้ `system-analyst` เสนอแนวทางและตรวจ feasibility ก่อน implement จริง

**Acceptance criteria (ทดสอบได้)**
1. (AC-017.1) ตาราง `compass_level_subject_stat` มีคอลัมน์ `stddev_score` เพิ่มแบบ additive เท่านั้น — คอลัมน์เดิมทุกคอลัมน์คงเดิม และ consumer เดิมที่อ่านแค่ `mean_score` (REQ-004) ทำงานเหมือนเดิม

3. (AC-017.3) การเพิ่ม `stddev_score` ไม่กระทบพฤติกรรมเดิมของ REQ-010 (สถานะ `idle`/`running`/`done`/`failed`, กันสั่งซ้อน, โรงเรียนที่คำนวณพลาดไม่ทำให้ทั้ง batch ล้ม)

## Constraints & Assumptions

- คะแนนที่ใช้เป็น **คะแนนที่ครูกรอกจริงในระบบเกรด** อ่านจาก read replica และเคารพการแก้เกรดของครู
- **ตั้งใจไม่รอการอนุมัติผลการเรียน** — เพื่อให้เด็กที่เรียนไม่จบเทอมก็ใช้งานได้ (ยืนยันจาก
  comment ในโค้ดว่าเป็นการตัดสินใจ ไม่ใช่ bug) `system-analyst`/`qa-engineer` ไม่ต้องยกเรื่องนี้
  ขึ้นมาอีกว่าเป็นข้อผิดพลาด
- **"AI" ในหน้าจอเป็น rule-based ทั้งหมด ไม่มี LLM และไม่มีการส่งข้อมูลออกนอกระบบ** — เป็นข้อจำกัด
  ที่ต้องคงไว้ ถ้าจะเปลี่ยนต้องกลับมาแก้ requirement นี้ก่อน (มีผลตรงกับเรื่อง consent, OQ-09)
- การปลดล็อก Premium เป็นกลไกภายนอก Compass แค่เชื่อ/เช็คผลลัพธ์ — ไม่คุยเรื่องราคา/การจ่ายเงิน
  ในเอกสารนี้
- สถิติเครือข่ายคำนวณล่วงหน้า **ไม่ใช่ข้อมูลสด** — ตัวเลขที่เด็กเห็นเก่าเท่ากับรอบ batch ล่าสุด
- ตารางสถิติสองตัวถูกสร้างโดยโค้ด batch เอง ไม่ได้อยู่ใน migration ปกติ
- **ไม่ต้องมี consent gate เพิ่มก่อนประมวลผลข้อมูลเด็กใน Compass** (ยืนยัน 2026-08-24, ปิด OQ-09)
  เหตุผลที่ผู้ใช้ให้: การประมวลผลทั้งหมดเป็น rule-based ในระบบเราเอง **ไม่มีการส่งข้อมูลออกนอกระบบ
  และไม่มี third-party AI** จึงถือเป็นส่วนหนึ่งของบริการโรงเรียนที่ผู้ใช้คุ้นเคยอยู่แล้ว
  `system-analyst`/`qa-engineer`/`security` ไม่ต้องยกเรื่อง consent gate ขึ้นมาอีกในขอบเขตนี้
  — แต่ข้อจำกัด "ไม่ส่งข้อมูลออกนอกระบบ" คือเงื่อนไขที่ทำให้ข้อนี้เป็นจริง ถ้าวันใดมีการส่งออก
  (เช่นเพิ่ม LLM ภายนอก) ต้องกลับมาเปิดคำถาม consent ใหม่ทันที
- **ไม่นำปัจจัยขนาด/ชื่อเสียงโรงเรียนมาปนในสูตรจุดแข็ง/จุดอ่อน** (ยืนยัน 2026-08-24 — เหตุผลเต็ม
  อยู่ที่ REQ-012) เป็นการตัดสินใจของผู้ใช้ ไม่ใช่ข้อที่มองข้าม — ห้ามยกขึ้นมาเสนออีก
- **เกณฑ์ 60/80 ใช้เท่ากันทุกกลุ่มสาระโดยเจตนา** ผู้ใช้ปฏิเสธเกณฑ์แยกตามกลุ่มสาระเพราะซับซ้อนและ
  อัตวิสัยเกินไป — เป็นการตัดสินใจ ไม่ใช่ความไม่รอบคอบ
- **ไม่มี minimum sample size สำหรับสถิติ "ทั่วประเทศ"** ยอมรับความคลาดเคลื่อนเมื่อกลุ่มตัวอย่างเล็ก
  แลกกับความเรียบง่ายและการที่เด็กเห็นข้อมูลได้เสมอ (ยืนยัน 2026-08-24)

### กลไก matching รายวิชา → กลุ่มสาระ (ยืนยันจากการอ่านโค้ดจริง 2026-08-24 — `system-analyst` ใช้อ้างอิงได้เลย ไม่ต้องวิเคราะห์ใหม่)

บันทึกนี้มีไว้เพื่อให้ `system-analyst` ไม่ต้องเปิดคำถาม "โรงเรียนต่างกันตั้งชื่อวิชาไม่ตรงกันจะเทียบ
กันได้ไหม" ขึ้นมาใหม่ — ตรวจแล้วว่าระบบรองรับอยู่แล้ว:

- `CompassScoreService.MapCanonicalSubject` (`ClassOnlineWeb/Helper/CompassScoreService.cs:245-267`)
  จับรายวิชาเข้ากลุ่มสาระด้วย **keyword ในชื่อวิชา** (substring ภาษาไทย/อังกฤษ) **ไม่ใช่รหัสวิชา**
  จึง **รองรับกรณีที่โรงเรียนต่างกันตั้งชื่อ/ตั้งรหัสวิชาไม่ตรงกันอยู่แล้ว** เช่น "คณิตศาสตร์" และ
  "คณิตศาสตร์เพิ่มเติม" ต่างก็ match คำว่า "คณิต" → เข้ากลุ่มสาระ "คณิตศาสตร์" เดียวกัน
  (บรรทัด 249) โดยไม่ต้องพึ่งรหัสวิชาที่ตรงกัน
- **ความเสี่ยงที่เหลืออยู่ (เป็นพฤติกรรมเดิมของระบบ ไม่ใช่ปัญหาใหม่ที่ REQ-012/REQ-016 สร้างขึ้น)**:
  ชื่อวิชาที่ **ไม่มี keyword ที่ระบบรู้จักเลย** จะได้ค่า `null` (บรรทัด 266) = ถูกจัดเป็น non-core
  และ **ไม่ถูกนับในกลุ่มสาระใดเลย** ทั้งใน REQ-001, REQ-012 และ breakdown ของ REQ-016
  → บันทึกเป็น **observation** ไม่ได้เปิดเป็น REQ ใหม่ เพราะ **ผู้ใช้ยังไม่ได้สั่งให้แก้** และ
  ทางแก้ระยะยาว (เปลี่ยนเป็นตาราง mapping ที่ตั้งค่าได้ต่อโรงเรียน) อยู่ใน Scope → Later อยู่แล้ว
