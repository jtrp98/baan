## Test Strategy Summary

- **ไม่มี automated test framework ในโปรเจกต์นี้** (`.claude/agents/backend-engineer.md`: "Testing:
  none") — ทุก verification step ด้านล่างเป็น **code reading + manual/exploratory testing +
  acceptance-criteria worked examples** ที่มีอยู่แล้วใน `requirement.md`/`design.md` ไม่ใช่ automated
  test suite ที่ `qa-engineer` จะรัน
- **ไม่พบ `test-pyramid.yaml`** ในเรโปนี้ (`Glob **/test-pyramid.yaml` ไม่เจอไฟล์) — จึงไม่มี floor
  ที่กำหนดสัดส่วน unit/integration/E2E ให้เทียบ บันทึกเป็นช่องว่างใน `## Unresolved Open Questions`
  ด้านล่างแทนการเดา floor เอง คำว่า "Level" ในเอกสารนี้หมายถึง **ชั้นของระบบที่ต้องตรวจ** (หน่วยคำนวณ
  ในโค้ด / endpoint เดี่ยว / end-to-end ผ่านหน้าจอ) ไม่ใช่ automated test level เพราะไม่มีสิ่งนั้นให้เขียน
- ทุก test item ผูกกับ `REQ-NNN` และ phase ของ `plan.md` (Contract Version 11 ของ `design.md`) — Phase
  ที่ `plan.md` เขียนไว้ว่ายัง "ไม่ planned" (เนื้อหาส่วนใหญ่ของ REQ-019 นอกเหนือ WORD-01, REQ-018)
  **ไม่มี test item** ในเอกสารนี้เช่นกัน เพราะไม่มี `DES-NNN` contract รองรับให้ตรวจตาม — ระบุไว้ใน
  `## Unresolved Open Questions`

## Phase 1: Module A — Score Aggregation (REQ-012)

**Contract**: `design.md` → `## Subject Score Aggregation Rules` · **Tasks**: BE-001, BE-002, BE-003

### REQ-012 — ค่าเฉลี่ยถ่วงน้ำหนักด้วยหน่วยกิต

**Level**: หน่วยคำนวณ (`AggregateByCanonicalSubjectWeighted`) ผ่าน code reading + เรียกจริงผ่าน
endpoint Premium (`calculate/score`) แบบ manual/exploratory ด้วยข้อมูลนักเรียนทดสอบ

**Verification method**: อ่านโค้ด `CompassScoreService.AggregateByCanonicalSubjectWeighted` เทียบกับ
กฎข้อ 0-5 ทีละข้อ + ตั้งข้อมูลนักเรียนทดสอบ (คะแนน/หน่วยกิตตามตัวอย่าง) แล้วยิง `calculate/score`
จริงเทียบค่าที่ได้กับตัวเลขที่ acceptance criteria กำหนดไว้เป๊ะ

**Test cases** (ตรงกับ acceptance criteria ของ REQ-012 ใน `requirement.md`):

1. **ถ่วงน้ำหนักปกติ** — คณิตพื้นฐาน คะแนน 60 หน่วยกิต 1.5 · คณิตเพิ่มเติม คะแนน 90 หน่วยกิต 0.5 →
   ต้องได้ **67.5** พอดี (ไม่ใช่ 75 แบบเฉลี่ยธรรมดา) จัดระดับเป็น `normal`
2. **สลับหน่วยกิต** — คณิตพื้นฐาน 60 (0.5) · คณิตเพิ่มเติม 90 (1.5) → ต้องได้ **82.5** จัดระดับเป็น
   `strong` — ยืนยันว่าหน่วยกิตเปลี่ยนผลการจัดระดับได้จริง ไม่ใช่แค่เปลี่ยนตัวเลขทศนิยม
3. **fallback หน่วยกิตรวม = 0** — กลุ่มสาระศิลปะมี 2 วิชา (70, 80) ที่ไม่มีข้อมูลหน่วยกิตทั้งคู่ →
   ต้องได้ **75** (ค่าเฉลี่ยดิบธรรมดา) ห้ามหารด้วยศูนย์ ห้าม error ห้ามคืน 0
4. **ไม่มีคะแนนเลยในกลุ่มสาระ** — กลุ่มสาระที่ไม่มีวิชาใดมีคะแนนเป็นตัวเลขเลย → ต้อง**ไม่มีค่า**
   (กลุ่มถูกตัดออกจากผลลัพธ์ทั้งหมด) ไม่ใช่ 0 และไม่ใช่ error
5. **บางวิชามีหน่วยกิต บางวิชาไม่มี** — ต้อง**ไม่**เข้า fallback (หน่วยกิตรวม ≠ 0) ต้องใช้สูตร
   ถ่วงน้ำหนักกับเฉพาะวิชาที่มีหน่วยกิตใช้ได้เท่านั้น ไม่ปนวิชาที่ไม่มีหน่วยกิตเข้าไปเป็น 0
6. **วิชาที่หน่วยกิต ≤ 0 หรือ null** — ต้องถูกตัดออกจากทั้งตัวตั้งและตัวหาร ไม่ใช่นับเป็น 0 แล้วยังอยู่
   ในตัวตั้ง (กฎข้อ 2 — ต่างจากโค้ดเดิม `TotalCredit = gr.Sum(x => x.Credit ?? 0)`)
7. **วิชาที่ไม่มีคะแนนเป็นตัวเลข** — ต้องถูกตัดออกทั้งตัวตั้งและตัวหารเสมอ ไม่ว่าจะมีหน่วยกิตหรือไม่
8. **การปัดเศษ** — ค่าที่ส่ง API ฝั่ง Premium (`calculate/score`) ต้องเป็นทศนิยม 2 ตำแหน่ง (เช่น 67.5
   ไม่ใช่ 68 ที่ `Math.Round(x, 0)` เดิมจะให้) การตัดระดับ strong/normal/weak ใช้ค่า**หลังปัด** 2
   ตำแหน่งเทียบกับเกณฑ์ ≥80/<60/60-79.99
9. **ฝั่งฟรี (REQ-001/REQ-002, `analyst/{sID}`) ต้องไม่เปลี่ยนแปลง** — ยังเป็นค่าเฉลี่ยดิบธรรมดา
   (ไม่เรียก `AggregateByCanonicalSubjectWeighted`) และยังปัดเป็นจำนวนเต็มเหมือนเดิม — ทดสอบด้วยชุด
   ข้อมูลเดียวกับ case 1-2 แล้วยิง `analyst/{sID}` เทียบว่ายังได้เลขแบบเฉลี่ยธรรมดา ไม่ใช่ 67.5/82.5
10. **ความสม่ำเสมอข้าม consumer** — ด้วยชุดข้อมูลเดียวกัน (เช่น กรณี fallback ข้อ 3) ค่าที่ได้จาก
    `calculate/score`, `GetSubjectAveragesAsync` (ผ่าน Fit Score ฝั่งที่ยังทำงาน), และ batch
    (`CompassRankingService.RecomputeAsync`, ดู Phase 3) ต้องเป็น**เลขเดียวกันทุกจุด** — ตรวจโดยอ่าน
    โค้ดว่าทุก caller เรียกเมธอดเดียวกัน ไม่มี caller ใดคัดลอกสูตร/ทำ fallback เอง (ตาราง Caller ใน
    `## Subject Score Aggregation Rules` กฎข้อ 0)
11. `CompassScoreService.AggregateByCanonicalSubject` (เมธอดเดิม) ต้อง**ไม่ถูกแก้ทับ** — ยังคงพฤติกรรม
    ค่าเฉลี่ยดิบเดิมไว้ (ตรวจโดยอ่าน diff/โค้ดว่ามีเมธอดใหม่แยกต่างหาก ไม่ใช่แก้เมธอดเดิม)

## Phase 2: Module B — Premium Entitlement & API Authorization (REQ-013, REQ-014, REQ-015) 🔒 Security gate

**Contract**: `design.md` → `## Premium Entitlement Rules`, `## Identity & Scope Rules` · **Tasks**:
BE-004 ถึง BE-012 · **Security-critical — ทุกข้อต้องมีขั้นตอนตรวจที่ชัดเจน ไม่ใช่แค่ code review ผ่าน ๆ**

### REQ-013 — Premium ต้องถูกกั้นสิทธิ์ที่ฝั่ง API

**Level**: endpoint เดี่ยว (manual — เรียก API ตรงโดยข้าม UI) + code reading ของ `CheckEntitlement`

**Verification method**: สำหรับผู้ใช้ที่ไม่มีสิทธิ์ Premium (ไม่มี record ใน `TSubscription`/หมดอายุ)
ยิง API ตรงด้วยเครื่องมือ (Postman/curl) ข้าม UI ทั้งหมด แล้วตรวจ response — **ไม่ใช่ตรวจว่า UI ซ่อน
ปุ่มหรือไม่**

**Test cases**:

1. ผู้ใช้ไม่มีสิทธิ์ยิง `calculate/score` (REQ-004/016) ตรง → ต้องได้ **HTTP 403** พร้อม `Data = null`
   ไม่ใช่ 200 พร้อมข้อมูล Premium ที่ให้ UI ซ่อนเอง
2. เช่นเดียวกันกับ `AI_calculate/path` (REQ-005), `AI_advice/path` (REQ-006), `AI_mbti/questions`,
   `AI_mbti/answer`, `AI_mbti/latest` (REQ-007), `AI_exercise/path`, `AI_exercise/submit` (REQ-008),
   `certificate/issue` (REQ-011) — **ต้องกั้นทั้ง endpoint** ครบทุกตัวตามตาราง endpoint ที่ต้องกั้นใน
   `## Premium Entitlement Rules`
3. **กรณีพิเศษ `analyst/{sID}`** (ให้บริการทั้งฟรีและ Premium ในตัวเดียว) — ผู้ใช้ไม่มีสิทธิ์ Premium
   ยิง endpoint นี้ → ต้องได้ **200 ตามปกติ** (ฟีเจอร์ฟรีต้องยังทำงาน) แต่ `Subjects[].Boost` ต้องเป็น
   `null` **ทุกวิชา** — ต้อง**ไม่ใช่** 403 ทั้ง endpoint (ผิด REQ-016 AC6 ถ้าทำแบบนั้น)
4. localStorage-based gating เดิม (`compass.js:60`, `localStorage['compass_premium']`) ต้องเลิกใช้เป็น
   แหล่งความจริงแล้ว — แก้ค่านี้ผ่าน browser devtools แล้วยืนยันว่า API ยังคง 403 ผู้ใช้ที่ไม่มีสิทธิ์
   จริง (ไม่ถูกหลอกด้วยค่า client-side)
5. entitlement source ตรวจจาก `TSubscription`/`TPlan_Feature` จริง — `status IN ('Active',
   'PendingCancel')` ทั้งสองค่าต้องผ่าน, `expire_at >= NOW()` ต้องถูกเช็คคู่กับ `status` เสมอ
6. `expire_at IS NULL` → ต้องถือว่า**ไม่มีสิทธิ์** (ไม่ใช่ "ไม่มีวันหมดอายุ") — ทดสอบด้วยแถวทดสอบที่ตั้ง
   `expire_at = NULL` แล้วยิง API ตรง ต้องได้ 403
7. **DB entitlement query ล่ม → fail-closed (403)** — จุดนี้ตรวจได้จาก **code review เท่านั้น**
   (จำลอง DB failure จริงทำได้ยากในสภาพแวดล้อม manual — ทำเครื่องหมายเป็น code-review-only ใน
   handoff ให้ `qa-engineer`) ตรวจว่า exception path คืน 403 ไม่ใช่ fail-open
8. นักเรียนมีหลาย subscription แถว → ต้องใช้ `ORDER BY subscription_id DESC LIMIT 1` (แถวล่าสุด)
9. **ขั้นตอนที่ 4 ของ `CheckEntitlement` — ตรวจ `"FeatureCode"` จริง (ปลดบล็อก PRE-06/OQ-15 แล้ว 2026-09-15)**:
   - สำหรับ endpoints ฝั่ง Premium (`calculate/score`, `AI_*`, `certificate/issue`): ต้องมีแถวใน `TPlan_Feature` ที่ `"FeatureCode" = 'compass_premium'` เท่านั้น หาก subscription มีเพียง code อื่นหรือไม่พบ `compass_premium` → ต้องได้ **403 Forbidden**
   - สำหรับ endpoints ฝั่ง recompute admin (`recompute/national-stats`, `recompute/status`): ต้องมีแถวที่ `"FeatureCode" = 'compass_admin_ops'` เท่านั้น (มีเพียง `compass_premium` ไม่เพียงพอ ต้องได้ 403 ตาม REQ-014 case 2)
   - หากไม่มีแถว `TPlan_Feature` ที่ match FeatureCode ที่ระบุ (หรือ `"FeatureCode"` เป็นค่าอื่น) → fail-closed (403)

### REQ-014 — จำกัดสิทธิ์ `recompute/national-stats`

**Level**: endpoint เดี่ยว (manual, สอง layer แยกกัน)

**Verification method**: ทดสอบสอง layer แยกกันชัดเจน เพราะ design บังคับว่าห้ามตัดชั้นใดชั้นหนึ่งออก

**Test cases**:

1. นักเรียนทั่วไปที่ล็อกอินอยู่ (ไม่มีสิทธิ์ `compass_admin_ops`) ยิง `recompute/national-stats` ตรง →
   ต้องถูกปฏิเสธ (403 หรือ 404 จาก layer IP ถ้าไม่ผ่านตั้งแต่ชั้นนั้น)
2. **แยก feature key** — ยืนยันว่า `compass_admin_ops` เป็นคนละ key จาก `compass_premium` โดยตรวจ
   โค้ด/configuration ว่านักเรียนที่จ่ายเงิน Premium (มี `compass_premium`) ยิง `recompute/*` ต้องยัง
   ถูกปฏิเสธ (มี Premium ไม่ได้แปลว่ามี admin ops)
3. **layer IP allowlist** — request จาก IP ที่ไม่อยู่ใน allowlist ต้องถูกปฏิเสธ**ก่อน**ถึงชั้น
   entitlement เลย (404/403 โดยไม่เปิดเผยว่ามี endpoint นี้อยู่) — ถ้าไม่ได้ตั้งค่า allowlist เลย
   ต้องปฏิเสธทุก request (fail-closed) — ทดสอบโดยไม่ตั้งค่า config แล้วยิงจาก IP ใด ๆ
4. `recompute/status` ต้องถูกกั้นด้วยกติกาเดียวกัน (ไม่ใช่แค่ `recompute/national-stats`)
5. **จุดที่ตรวจยากด้วย manual test** — การจำลอง "ทีม SB PLUS ผูก `compass_admin_ops` เข้าแพ็กเกจที่
   ขายให้นักเรียนโดยไม่ตั้งใจ" เป็น configuration error ฝั่งข้อมูลจริง ไม่ใช่โค้ด — ตรวจได้จาก
   **การอ่าน record จริงใน `TPlan_Feature`** ตอน deploy (ส่วนหนึ่งของ PRE-02) ไม่ใช่ code test

### REQ-015 — ปิดช่องโหว่ `SID` จาก client

**Level**: endpoint เดี่ยว (manual — ส่ง SID ปลอมในตัว payload)

**Verification method**: ส่ง request จริงที่มี `SID` เป็นเลขนักเรียนคนอื่น (ไม่ใช่ของบัญชีที่ล็อกอิน)
แล้วตรวจว่า response สะท้อนเลขของบัญชีที่ล็อกอินจริง ไม่ใช่เลขที่ส่งมา

**Test cases**:

1. `AI_exercise/path` (`CompassApiController.cs:643`) — ส่ง `SID` ปลอมใน body → response ต้องใช้
   `UserData.UserID` ของบัญชีที่ล็อกอินจริง ไม่ใช่ค่าที่ส่งมา — ยืนยันว่าข้อมูลที่ได้กลับเป็นของบัญชี
   ตัวเอง ไม่ใช่ของเลขปลอมที่ส่งไป
2. เช่นเดียวกันกับ `AI_exercise/submit` (บรรทัด 675) และ `certificate/issue` (บรรทัด 729)
3. ทั้งสามจุด — request ที่ไม่มี token/session ที่ถูกต้อง (`ud == null`) ต้องได้ **401** (จุดนี้เดิม
   ไม่มีการเช็คเลย ต้องเพิ่มใหม่)
4. `certificate/issue` — ยืนยันว่าการแก้ครั้งนี้**ไม่กระทบ business logic การออกใบรับรอง** (ยังคง
   stub เดิม ไม่มีการตรวจสอบว่าสอบผ่านจริง — เป็นขอบเขตของ module `sb-compass-certificate` แยก
   ไม่ใช่สิ่งที่ REQ-015 แก้) — ตรวจโดย diff โค้ดว่าแก้เฉพาะส่วน identity เท่านั้น

### REQ-004/REQ-012 (batch alignment) — ใช้สูตรถ่วงน้ำหนักทั้ง batch และ request-time

**Level**: batch job (manual trigger + ตรวจผลในตาราง) + code reading

**Test cases**:

1. หลังรัน `RecomputeAsync` (`?limit=0`) ค่า `"MeanScore"` ต่อ (ระดับชั้น × กลุ่มสาระ) ต้องคำนวณจาก
   ค่าที่**ถ่วงน้ำหนักแล้ว** ไม่ใช่ค่าเฉลี่ยดิบ — เทียบด้วยชุดข้อมูลทดสอบเดียวกับ Phase 1 case 1-2
2. `"OverallAvg"` ต่อนักเรียน = ค่าเฉลี่ยธรรมดาของคะแนนกลุ่มสาระที่ถ่วงน้ำหนักมาแล้ว **ไม่ถ่วงน้ำหนักซ้ำ
   อีกชั้น** — ตรวจสูตรจากโค้ดว่าไม่มีการคูณหน่วยกิตซ้ำ
3. `GetStudentNationalStatsAsync` (คำนวณสดตอน request สำหรับ `overall`) ต้องใช้สูตรเดียวกับ batch —
   ทดสอบด้วยนักเรียนที่มีข้อมูลใน batch แล้ว เทียบค่าที่ endpoint นี้คืนกับค่าที่อยู่ในตาราง
   `TCompassStudentLevelScore` ว่าตรงกัน (ไม่ใช่เอาค่าถ่วงน้ำหนักไปเทียบกับกองเลขไม่ถ่วงน้ำหนัก
   ซึ่งจะทำให้อันดับเพี้ยนอย่างเป็นระบบ)
4. batch ยังคงพฤติกรรมเดิมของ REQ-010: สถานะ `idle`/`running`/`done`/`failed`, กันสั่งซ้อน, โรงเรียน
   ที่คำนวณพลาดไม่ทำให้ทั้ง batch ล้ม (นับ failed แล้วไปต่อ), ตารางยังไม่เคยคำนวณ → ไม่ error
5. **`limit` default** — ยืนยันว่า default ยังเป็น 10 โรงเรียน และ deploy step ต้องใช้ `?limit=0`
   อย่างจงใจ (ตรวจ config/runbook ไม่ใช่โค้ด — เป็นรายการของ `devops` ที่ `qa-engineer` ควรยืนยันว่า
   runbook เขียนไว้ถูกต้อง)

### REQ-017 — `"StddevScore"` ในตาราง `TCompassLevelSubjectStat`

**Level**: batch job (manual trigger + ตรวจค่าในตาราง) + code reading ของสูตร

**Test cases** (อิง `## National Stats Batch Rules` § `"StddevScore"`):

1. **สูตร population stddev** — สร้างชุดข้อมูลทดสอบที่รู้ค่าคาดหวังล่วงหน้า (เช่น คะแนนกลุ่มสาระของ
   นักเรียน n=30+ คนในระดับชั้น×กลุ่มสาระเดียวกัน) คำนวณ `sqrt(Σ(x_i − mean)² / n)` ด้วยมือ/สเปรดชีต
   แล้วเทียบกับค่าที่ batch เขียนลงตาราง — ต้องหารด้วย `n` **ไม่ใช่** `n−1` (ระวัง PostgreSQL
   `stddev()` default คือ `stddev_samp` ซึ่งผิด ต้องเรียก `stddev_pop()` ชัดเจนถ้าใช้ SQL)
2. **`n < 30` (`MIN_N_FOR_STDDEV`)** — (ระดับชั้น × กลุ่มสาระ) ที่มีนักเรียนน้อยกว่า 30 คน →
   `"StddevScore"` ต้องเป็น **`NULL`** ไม่ใช่ค่าที่คำนวณได้จริง
3. **`n = 1`** — ต้องเป็น `NULL` เช่นกัน (ครอบด้วยเกณฑ์ `n < 30` อยู่แล้ว) — ทดสอบแยกเพื่อยืนยันว่า
   ไม่ได้เขียนโค้ดพิเศษที่ให้ค่า 0 สำหรับกรณีนี้
4. **`n ≥ 30` ที่ทุกคนได้คะแนนเท่ากันจริง** — ต้องได้ **`0`** (ค่าจริง ไม่ใช่ `NULL`) — สร้างชุดทดสอบ
   ที่ตั้งใจให้คะแนนทุกคนเท่ากันเพื่อยืนยันกรณีนี้แยกจากกรณี `NULL`
5. **`n ≥ 30` ปกติ** — ค่าที่คำนวณได้ต้องไม่ใช่ `NULL`/`0` (นอกจากกรณีคะแนนเท่ากันจริงตาม case 4)
6. **ประชากรที่ใช้คำนวณ `"StddevScore"` ต้องเป็นชุดเดียวกับที่ใช้คำนวณ `"MeanScore"` ของแถวเดียวกัน**
   — ค่าคะแนนรายนักเรียนที่เข้าสูตรต้องเป็นค่าถ่วงน้ำหนักหน่วยกิตแล้ว (ไม่ใช่ค่าเฉลี่ยดิบ) ตรวจโดย
   อ่านโค้ดว่า `"StddevScore"`/`"MeanScore"` ดึงข้อมูลจากแหล่งเดียวกันในรอบ batch เดียวกัน
7. **ตาราง `TCompassLevelSubjectStat` ต้องมีคอลัมน์ `"StddevScore"` ตั้งแต่ `CREATE TABLE IF NOT
   EXISTS`** ไม่ใช่ `ALTER TABLE ... ADD COLUMN` แยกทีหลัง — ตรวจ DDL ในโค้ด `EnsureTables` ว่า
   ลืมคอลัมน์นี้หรือไม่ (ถ้าลืม batch จะล้มตอน `INSERT` — เป็นความเสี่ยงที่ชัดเจนจาก `design.md`)
8. **ไม่ใช่ backfill แยก ไม่ใช่ incremental update** — ตรวจว่า `"StddevScore"` ถูกคำนวณในรอบ
   `TRUNCATE` + เขียนใหม่เดียวกับ `"MeanScore"` เท่านั้น ไม่มี code path แยกที่อัปเดตทีละคะแนน
9. **ไม่กระทบ REQ-004 เดิม** — ยืนยันว่า `"MeanScore"` และการจัดอันดับยังไม่มี minimum sample size
   (ไม่ใช้เกณฑ์ `MIN_N_FOR_STDDEV` กับ `"MeanScore"`) — ทดสอบด้วยกลุ่มที่มีนักเรียน < 30 คนว่ายังแสดง
   `"MeanScore"`/อันดับตามปกติ แม้ `"StddevScore"` จะเป็น `NULL`
